# 角色权限与数据范围改造方案

编写日期：2026-10-21；2026-10-25 清理过时状态。本文维护角色、数据范围与职责设计，实际实施和发布统一查[项目核心](./00_项目核心.md)。审批基础授权、组织范围、有效权限与总经理显式清单已有实现，不再沿用早期“尚未部署”结论；库存专用权限仍随库存链路验收。财务职责拆分等业务选择见第 10 节，未读取线上账号或完成在线岗位验收。

## 1. 目标与边界

以“收货／备料 → 母单拆分 → 标签 → 工序交付 → 质检和返工 → 发货／退货 → 结算与追溯”为主线，让每个岗位只取得所需的操作和数据。桌面、手机与以后安卓端使用同一服务端授权；菜单和按钮只反映授权结果，不能充当授权依据。

本方案覆盖现有十种角色、业务管理顶岗权限、客户与工序范围、审批、库存和财务职责分离，以及账号授权迁移。方案不新增完整客户订单、自有产品销售或正式报工工序；库存独立备料和公司料的新增动作与[库存管理与母单加工要求模板改造方案](./库存管理与母单加工要求模板改造方案.md)协同实施。账号管理当前采用“管理员直接保存并审计”，历史前置申请接口保留兼容；本方案不把它描述为已启用的强制审批，也不在未确定业务流程前改变这一策略。

## 2. 已实施边界与待收口事项

| 位置 | 当前事实 | 改造原因 |
|---|---|---|
| `security/app/PermissionGuard.java` | 总经理权限使用显式清单；管理员拥有系统维护权限；业务管理顶岗按勾选取有效权限。 | 财务职责拆分、总经理日常写权限及代办审计仍需业务定案。 |
| `security/web/PermissionGuardInterceptor.java` | 写接口和财务读取按路径拦截；审批决策先检查 `APPROVAL_DECISION`，服务层再核对场景、任务和业务范围。 | 新接口仍需逐项核对请求方法与对象范围，不能只靠路径或菜单。 |
| `approval/web/ApprovalController.java`、`approval/app/ApprovalService.java` | 审批查询按会话和任务过滤；损耗组长核对指定审批人及工单范围，决策人取会话。 | 账号管理审批仍为记录，不是强制复核流程；其他新增场景需单独定义资源级授权。 |
| `business/app/BusinessDataAccess.java` | `SELF` 依经手关联，`TEAM`、`DEPARTMENT` 核对稳定组织编号，`CUSTOMER_RANGE` 核对客户名单。 | 线上账号的真实组织映射仍需人工核对；空组织不能扩大同事单据范围。 |
| `security/infra/InMemoryNavigationMenuRepository.java`、`security/app/AuthSessionService.java`、`frontend/src/App.vue` | 导航按服务端菜单，手机现场操作按会话有效权限过滤。 | 其他业务页面的动作按钮仍需逐页核对；入口隐藏不替代接口鉴权。 |
| `finance/app/FinanceReadAuthorizer.java` | 客户财务与公司财务读取已分开，公司财务要求 `ALL`。 | 保留这一边界，同时细分定价、账单、收款、付款和工资的写权限。 |

已有的客户稳定 ID 授权、工序绑定、受保护单据读取和 MySQL 环境禁用开发请求头身份继续保留。`CUSTOMER_RANGE` 客户名单为空、历史名称歧义或单据归属冲突时，应拒绝扩大访问；其他数据范围的空客户名单不构成额外客户限制。历史账号、审批、库存和财务记录均保留，不因角色调整改写事实。

## 3. 授权模型

一次访问同时满足四项条件：**有效登录身份、动作权限、业务对象范围、业务状态与职责分离规则**。读取列表、数量、详情、扫码、附件、导出和签名取址使用同一对象可见性；写命令在服务端重新核对对象、版本和授权，不沿用页面先前的判断。

1. **动作权限。** 沿用 `PermissionCode`，将权限细化到可审计的业务动作。菜单权限与动作权限分开；角色提供默认模板，业务管理顶岗和以后确有需要的个人授权只在模板允许的范围内取舍。任何显式拒绝优先于菜单展示。
2. **对象范围。** 客户单据以稳定客户 ID 和真实母单归属判断；工序以账号绑定工序判断；库存同时核对权属、批次、仓库、状态、来源单据和客户；公司级工资、成本、资产及备份数据另设公司读取能力。不能仅靠客户端提交的客户名、单号前缀或运单号授权。
3. **组织范围。** `SELF` 指本人创建、接手或被明确分配的对象；`TEAM` 指账号所属班组／工位；`DEPARTMENT` 指账号所属部门；`CUSTOMER_RANGE` 指明确授权的客户集合；`ALL` 仅作为公司范围，不自动赋予任何写动作。班组、部门归属须有稳定标识和成员关系，未配置时拒绝按这两种范围扩大可见性。
4. **决策分离。** 对审批、财务支付、导入入账、库存冲正等高风险事实，记录申请人、执行人、复核人和证据。需要复核的场景，提交人不能自行批准；重复决策和并发决策只能成功一次。
5. **顶岗。** `BUSINESS_MANAGER` 保留按人勾选机制，但每项顶岗应只映射对应动作；默认授权应逐步收窄为实际岗位需求。顶岗不自动获得公司财务、任意库存转移、账号管理或其他客户数据。

## 4. 建议目标角色矩阵

表中“可做”均仍受数据范围、工序及单据状态限制；“申请”是提出业务请求，不等同于直接过账。新增申请流程仅在对应业务功能实施时启用。

| 角色 | 默认可做 | 需剥离或单独授权 |
|---|---|---|
| 系统管理员 `ADMIN` | 账号、客户授权、菜单配置、系统维护、审计与故障处理。 | 日常收货、报工、质检、库存和财务记账改为受控代办；紧急代办须原因、对象、时限和审计。既有维护／回收能力按原规则保留，另行评估其敏感边界。 |
| 总经理 `GENERAL_MANAGER` | 公司经营汇总、授权业务详情、指定场景审批。 | 不再因 `allow` 自动得到全部写权限；具体业务代办和财务写入单独授权。 |
| 业务管理 `BUSINESS_MANAGER` | 按人勾选收货、拆单、报工、质检、标签、档案等确需顶岗动作。 | 发货、退货、导入入账、损耗决策默认不勾；单项顶岗不推导出相邻动作。 |
| 业务员 `SALES` | 授权客户档案、订单进度、对客信息；需要时提交发货或退货申请。 | 直接完成实物出库、客户退货入库；财务金额读取另行授权。 |
| 收货员 `RECEIVER` | 收货、拆包证据、授权母单查询和按职责拆单。 | 登记导入复核与入账不得默认同时完成；客户／材质档案维护可另授。 |
| 车间组长 `WORKSHOP_LEADER` | 派工、交接、授权工序报工、返工安排和进度查询。 | 日常质检最终放行、导入复核加入账、损耗最终批准与本人提交应分离。 |
| 操作工 `OPERATOR` | 本人任务及绑定工序报工、相关证据采集。 | 不取得其他工序、整部门订单、库存或财务写权限。 |
| 质检员 `QUALITY_INSPECTOR` | 质量判定、冻结、返工复检与按规则放行。 | 不直接完成客户退货的实物入库；自身提交的例外放行按场景复核。 |
| 库管员 `WAREHOUSE_KEEPER` | 按单据处理实物收发、备料及公司料的明确动作，查看授权库存和台账。 | 不授任意库存维度转移；发货需有效业务依据，冲正、冻结解除和异常退料单独授权。 |
| 财务统计 `FINANCE_STATISTICIAN` | 依据实际分工取得客户价、账单、收款、应付、工资及公司财务读取能力。 | 不再由一个角色默认包揽全部财务写动作；至少区分定价／计费、收付款、工资确认及公司数据读取。 |

首期不必新增大量角色。可先以现有 `PermissionCode` 和少量明确的新动作权限实现按账号分配，待实际人员分工稳定后再决定是否固化“出纳”“计薪”等角色。用户管理页应展示**账号最终有效权限**、数据范围、客户清单、工序和顶岗来源，不能只展示角色全集。

## 5. 按业务链的关键动作

| 环节 | 执行人及校验 | 需要分离的动作 |
|---|---|---|
| 收货与建母单 | 收货员或获 `INTAKE` 顶岗者；校验客户 ID、来源单及幂等请求。 | 客户／材质档案变更与收货确认独立审计；历史收货数量冲正维持管理员专门能力。 |
| 拆单与标签 | 授权收货、库管或组长依母单及来源行拆单；打印按单据和工位授权。 | 标签改派、出纸不明核纸及实际换贴按现有任务状态和证据处理，不能只凭打印权限覆盖旧快照。 |
| 工序与质检 | 操作工只报绑定工序；质检员处理判定和复检；返工交付仍沿正式工序。 | 同一人做生产交付和例外质量放行时留下冲突并要求独立复核；普通质量放行是否双人复核按现场风险确定。 |
| 库存与发货 | 库管依据明确来源单、批次和权属执行；业务员只负责业务申请或通知。 | 通用 `INVENTORY_LEDGER_TRANSFER` 保持管理员专用；新增备料／公司料动作各自授权，冻结、实物退还和冲正分别定义。 |
| 财务 | 客户价、改单费用确认、账单、收款、应付付款、工资确认分别授权并保留快照。 | 已确认金额不可由改单直接覆盖；收款和付款不能因拥有财务菜单而互通。 |
| 登记导入 | 预检、补录、复核、显式入账留人员和批次证据。 | 同一批次的复核人与入账人原则上不同；小团队例外须主管批准并标明原因。 |

## 6. 审批接口与决策规则

审批按 `scene` 定义允许的角色、个人或组织范围，不使用一个通用 `APPROVAL_DECISION` 放行所有任务。服务端先验证真实会话，再按任务查询可见性；列表、待办、详情、计数均只返回该人可见的任务和必要字段。决策时校验任务状态、审批人／角色、申请人与审批人不同、关联业务对象的范围、必要证据和版本。决策人取登录会话，请求体中的 `operator` 不作为身份来源；旧客户端字段可兼容接收但不能信任。

审批状态修改与其驱动的业务生效要有明确事务边界和幂等键；不能出现“任务已批准但业务未生效”却被页面显示为完成。历史审批只读保留。账号管理继续按当前管理员直接保存并审计执行；若以后决定将敏感授权改为双人复核，须先确定审批人、紧急恢复方式和线上账号迁移，再启用强制校验。

## 7. 数据模型、接口和界面实施点

- `security/domain`：增加稳定的组织归属及按账号授予的动作权限／有效期模型；区分角色模板、个人授权和业务管理顶岗。旧账号未迁移前不能把空组织解释为全组织。
- `security/app`：集中计算有效权限和资源范围；统一授权结果供菜单、按钮和服务端校验使用。对 `PermissionGuard` 中总经理自动加权改为显式矩阵，不改变 `ADMIN` 专属账号管理和工单维护边界。
- `security/web` 与各业务 `web/app`：逐一核对 `App.vue` 实际调用接口及 GET、POST、PATCH、DELETE 等方法；读取、导出、附件签名与写命令分别核对身份和对象范围。为审批增加任务级守卫，财务和库存动作使用专用权限码。
- `frontend/src/features/m1/UserManagementWorkspace.vue`：展示有效权限、授权来源和超范围提示；高风险勾选给出业务说明；保存后的会话失效与权限变化沿用既有机制。
- `frontend/src/App.vue` 及业务页面：导航由服务端有效菜单决定，动作按钮依据有效能力与对象状态显示；403 明确提示无权限，不退回演示数据或空列表。审批入口与服务端待办范围一致。
- JDBC／内存仓储保持同一授权语义。若增加组织、个人授权或审批字段，仅追加新迁移 `V{n}__m3_xxx.sql`；历史迁移不修改、不删表、不清理历史记录。

## 8. 迁移与实施顺序

| 增量 | 交付范围 | 完成条件 |
|---|---|---|
| P0：审批接口收口 | 登录与任务级读取、决策身份、本人申请限制、并发和审计；界面菜单对齐。 | 匿名、越权、跨场景、伪造操作人均拒绝；允许的审批可正常完成一次。 |
| P1：权限盘点与数据范围 | 形成线上账号的**脱敏**角色、数据范围、客户及工序清单；补组织归属和有效权限查询。 | 每个 `TEAM`／`DEPARTMENT` 账号有明确映射；未知归属不扩大访问；历史客户授权歧义仍拒绝。 |
| P2：角色与动作收紧 | 显式总经理权限、业务管理顶岗、导入双人分工、发货／退货与质检的执行边界；财务动作按人授权。 | 现有岗位正常流程通过，越权动作拒绝；账号迁移差异有人工核对记录。 |
| P3：库存专用权限 | 随独立备料与公司料增量提供专用读取、入库、领用、退回、实物退还和冲正授权。 | 库管能完成日常动作，通用任意转移仍不可用；库存正常、失败、重复和越权测试通过。 |
| P4：桌面／手机一致性 | 按有效权限调整菜单、按钮和扫码详情字段，复核附件与财务数据遮蔽。 | 同一账号跨桌面和手机得到相同授权结果；隐藏按钮对应接口仍拒绝越权。 |

每个增量先做账号与接口差异清单，再迁移授权配置，最后切换读写路径。保留必要的兼容读取但不兼容放宽写权限；上线前备份账号授权、审批和审计数据。若需回退，回退代码和授权配置快照，不通过清表或修改旧迁移回退。现有在线会话在角色、数据范围或个人权限变化后应失效。

## 9. 验证清单

- 角色矩阵：十种角色逐个核对允许与拒绝的关键动作；业务管理逐项取消顶岗后，桌面、手机和直接 HTTP 请求都不能执行。
- 数据范围：本人、班组、部门、授权客户和全部数据分别覆盖列表、计数、详情、扫码、附件、导出；跨客户、空授权、历史名称歧义、子母单客户冲突均不扩大可见性。
- 审批：匿名读取、非指定审批人、申请人自批、跨场景批准、伪造 `operator`、并发双击、重试及失败回滚。
- 业务链：收货→拆单→报工→质检→发货→账单的正常链路，以及库存不足、单据版本变化、财务拒绝、退货和返工场景。
- 持久化：内存与 JDBC 同口径；新增迁移在空库和升级库可执行，旧授权、审批与审计可查，停用或改权后旧会话失效。

按项目统一验证策略，对每个增量执行直接调用链和必要的正常、失败、越权及并发测试；不把全仓测试、镜像或打包作为文档和局部改动的默认门禁。

## 10. 实施前需业务确认

1. 总经理是否仍需日常直接收货、质检、发货或记账；若需要，列出具体动作和代办人，而非保留全部操作。
2. 业务员负责提交发货申请还是只通知库管；库管实际依据哪张单据出库。
3. 质检常规放行是否允许原判定人完成；哪些例外必须由另一人复核。
4. 现有财务人员是否兼任定价、账单、收款、付款和工资；不能分人时采用何种事后复核。
5. 登记导入和库存冲正的小团队例外由谁批准、需要哪些证据。
6. 账号升权是否继续管理员直接保存并审计，还是仅对 `ALL`、管理员和敏感财务授权增加双人复核。

上述选择只影响对应的敏感动作与验收口径；P0 的审批接口身份与任务范围收口可以先行实施。
