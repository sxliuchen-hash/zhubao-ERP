# 收货建单、主数据与工位打印开发方案

**形成日期：2026-10-15；状态：主要流程已编码，现场设备尚未验收。** 本文依据当前 `App.vue` 的来料、标签、手机作业入口及其服务端调用链整理。现行交付事实以[项目核心](./00_项目核心.md)为准；本文中的业务设计已按 V58—V61 分步实现，未部署到测试或正式环境。

## 1. 目标与业务身份

本次要解决五件相互关联的事：让一次打印可明确选择多个工位及其打印队列；让子单标签能直接看出所属母单；让收货选择已有客户和多种材质并可维护档案；创建订单不强制填写快递公司；客户送货上门、厂内接收等无快递场景也能直接建母单。**已确认：同一运单允许关联多张母单和多种材质；一次打印允许选择多个工位及打印队列。**

**母单号和子单号是现场业务对象的唯一身份。** 母单、子单分别有自己的单号；子单另存不可随意改写的 `motherOrderCode`，形成一母多子的关系。查询、扫码、标签、库存、附件、工序、质检和发货均以真实单号定位，再经服务端核对母子关系。运单号、客户名称、材质名称、手机号、验证码和打印任务号不能代替订单号。系统仍需保留数据库主键、客户／材质编码、请求幂等键、库存流水号和打印任务号等技术标识；“唯一业务身份是订单号”不等于取消这些保证事务和审计所需的标识。

新母单号沿用 `MD-年月日-四位流水`，新子单号沿用 `ZD-年月日-四位流水`；旧单号原样保留。当前两张业务表分别对 `code` 做唯一约束，服务内的同步锁不能单独保证多实例发号。建议在同一业务事务内使用数据库唯一约束保护的订单号登记表／原子序列，登记单号及母单或子单类型；内存实现提供等价的原子保留语义。上线前核查旧号是否跨表重复，不能在有冲突时盲目回填登记表。不要让用户自行用运单号或客户号充当母单号。

## 2. 当前实现与差距

| 事项 | 已有事实 | 与需求的差距 |
|---|---|---|
| 收货入口 | 桌面来料和手机作业复用 `IntakePanel.vue`；只有识别到新运单后才展示建母单表单 | 无快递、上门送货、内部交接不能直接从该入口建单 |
| 收货字段 | 页面手输客户名称、货品名称、数量、重量、要求和期限；快递公司默认“顺丰” | 没有客户和材质的可选档案；快递公司虽后端非必填，页面仍出现且默认值会写成快递事实 |
| 客户身份 | 母单存 `customerId` 与名称快照；手机收货未传客户 ID 时，后端按名称映射已知客户或计算散列 ID | 同名、改名和散列碰撞会影响授权、库存与财务；`sys_customer_authorization` 是用户授权关系，不是客户档案 |
| 材质 | 母单／子单和库存有单个 `materialCode`；手机表单不选材质，后端缺省为 `MAT-MOBILE` | 同一运单可含多种材质，单个编码和占位编码都无法准确记录各材质数量、重量与库存 |
| 运单 | 当前非空运单通过 `courier_identity` 唯一索引绑定一张母单，收货超时按运单找原单 | 已确认同一运单可关联多张母单，单结果查询和唯一索引均需调整 |
| 子单标签 | `ChildWorkOrderRecord` 已有 `motherOrderCode`；二维码和首行使用子单号 | 标签字段来源与默认模板没有母单号，纸面无法直接识别母子关系 |
| 集中打印 | 服务端已有打印任务、租约、补打和状态；厂内程序以配置的 `stationId` 领取，用本机单个 `printerName` 找 Windows 队列 | 创建任务无目标工位和队列字段；仓储领取任意 `PENDING` 任务；程序仅配置一条队列，当前只校验一把共享工位令牌 |

上述“差距”是代码核对结果。现有厂内打印程序尚未安装更新，佳博实机出纸、纸张间隙、二维码可扫性仍需现场验证。

## 3. 建单流程：先选来源，再生成订单号

### 3.1 建议的统一入口

收货页和手机收货页提供明确的来源选择：**快递寄来、客户送达、厂内接收／其他**。这些选项只决定需录入的收货来源信息，最终都调用同一母单创建与入库业务服务，生成母单号并进入现有“预览母单标签 → 不拆或拆子单”流程。不要为无快递场景另造一套工单或绕过库存入账。

| 来源 | 必填 | 可选 | 提交后 |
|---|---|---|---|
| 快递寄来 | 客户、至少一条货品／材质明细、各行数量和重量、加工要求、期限 | 运单号、快递公司、交件人、现场证据 | 生成母单号；有运单则作为来源线索保存，同一运单可继续建其他母单 |
| 客户送达 | 同上 | 交件人、交接时间、交接备注、现场证据 | 直接生成母单号；不造虚构运单或“快递”公司 |
| 厂内接收／其他 | 同上 | 来源说明、经手人、交接备注、现场证据 | 直接生成母单号；保留真实来源和操作人 |

快递公司在所有来源下均非必填；仅快递来源显示运单和公司输入，不预填“顺丰”或“快递”。如果现场希望快递来源必须有运单，应单独作为操作规则确认，不能据此禁止无快递建单。无运单时提交超时应保留原 `requestId` 重试，并可用返回的母单号或按客户、时间、操作人筛查；不能生成新请求后盲目再建。提交成功后只显示已保存母单号，单号由服务端生成。

建议将现有 `MobileIntakeCommand` 扩为来源类型、可空运单、客户 ID、物料明细行及交接信息；桌面和手机共用同一契约。服务端以 `requestId + 操作人 + 规范化业务内容` 做幂等，一次建母单及其全部明细、来料事实和逐材质库存台账同一次提交；不同客户、明细、来源或数量不得复用同一请求号。**一张运单下新建第二张母单必须使用新的请求号**，原请求号只用于重试第一张母单。运单查询返回候选列表，不再静默取第一条。来源字段与原运单字段都保留历史记录，旧单号及旧运单不改写。

### 3.2 运单与订单号的关系

运单是**可空、可重复的外部参考**，订单号是系统生成的业务主键。关系为“一个运单号对应零到多张母单”，每张母单再有一到多条材质明细；这两个“一对多”关系互不替代。用户按运单检索时返回全部可见母单，展示母单号、客户、收货时间及材质摘要；点开某张母单或继续用同一运单建新母单均为显式操作。扫码、证据关联、打印和库存操作若需要确定业务对象，必须选中具体母单号，不能靠运单自动取第一张。已有候选时可提示核对重复风险，但不阻止同运单新建。

当前收货页可按已识别的运单列出全部可见母单，并按母单分组只读查看各自已关联及历史证据。证据仍归属其正式母单，运单仅提供汇总检索；上传或绑定证据时仍须指定具体母单，不能自动复制到同运单下的其他母单。页面通过现有逐母单证据接口查询，每次查询继续执行原有数据范围校验。

落地时需要同步调整 `findMotherOrderByCourierNo` 的单结果契约、扫码上下文、重复校验、超时核对、页面提示和测试，再在**新迁移**中移除 `courier_identity` 的唯一索引并建立普通检索索引。不能直接删索引而继续使用 `findFirst()`，也不能把同运单多母单判作幂等回放。历史数据的运单及其原始证据继续保留。

## 4. 客户档案与材质选项

### 4.1 客户档案

在现有业务域内增加轻量客户档案，不把账号授权表当成客户表。建议字段为稳定 `customerId`、客户编码、显示名称、别名／曾用名、启用状态、联系人与电话（可选）、备注、创建及修改人和时间。编码与名称的规范化去重规则由服务端执行；同名疑似重复需提示核对，不自动合并历史客户。停用客户仍可查看旧订单，但不能用于新单；重命名只改档案展示，订单保留创建时的名称快照。

收货表单提供可搜索、可勾选确认的**单选客户下拉**，展示编码与名称；提交稳定 `customerId`，服务端读取当前有效档案并保存名称快照。新建母单时，收货员、库管员、车间组长、总经理和管理员可直接新增客户档案并选中，不在普通录入框中自由写一个未经登记的客户名称。授权客户范围的账号新建客户后，该客户进入本人范围。用户管理里的客户范围改为档案 ID 选择；历史名称授权在会话中仅唯一映射到档案 ID 时生效，改名保留旧名称别称，歧义值不扩大权限。已有按名称或散列 ID 创建的母单、库存、财务和授权仍需在现场做只读盘点及映射清单；未能确认归属的记录保留原值供人工核对，不按名字批量猜测。

### 4.2 材质目录

材质与货品名称分开维护。建议目录字段为 `materialCode`、材质名称、常用别名、启用状态、排序、创建及修改人和时间；收货时在可搜索下拉中勾选多个材质，形成可编辑的物料明细行，并提供“新增材质”入口。收货员在新建母单时可以直接新增，服务端按名称去重后保存为可复用选项，不能把未入库的自由文本写成库存编码。停用材质可查旧单，不能新选。

**一张母单支持多条材质明细，每条明细只对应一种材质。** 每行保存稳定行号、材质编码与名称快照、货品名称、数量、单位和重量；同一材质如需分批或分别称重，可以保留多行，不自动合并。母单汇总数量、重量只由明细计算，逐行校验正数、单位及合计，库存按明细逐材质记账；不能把多个材质编码拼进现有单个 `materialCode`。拆成子单时须为每张子单选择来源明细和分配数量／重量，在同一事务内校验每行剩余，不允许某材质超领或只核总量。子单如跨多种材质，同样保存多条来源明细及分配量；标签可显示简短材质摘要，完整明细靠扫码查单。旧母单／子单的单个 `materialCode` 作为一条历史明细兼容读取，回填需核实库存流水，不能重复入账。`MAT-MOBILE` 仅作为历史占位值保留，新增收货不得再自动写入。

## 5. 子单标签上的母单号

子单的主识别号仍是 `ZD-…`，二维码仍指向子单；标签另显示一行 **“母单：MD-…”**，值只能从已保存的 `ChildWorkOrderRecord.motherOrderCode` 读取，不能由打印者手填。若另需自由备注，单独设计备注字段，不能拿自由文本替代母子单关系。

在标签字段来源中增加 `motherOrderCode`，默认子单模板把该行设为必显；母单模板不显示。40×30 mm 紧凑版需要给子单号、二维码、验证码和母单号保留空间，其他次要字段按版面优先级缩减，母单号不得截断成不可辨认文本。浏览器预览、浏览器打印、服务端打印任务快照及 `print-agent` 绘制必须使用同一字段与版式。模板管理中的自定义子单模板也应始终保留母单号的固定关系区，避免模板误删后现场失去关联信息。

已排队任务的快照保持原样；新任务使用新模板。旧版同版补打沿用原快照，若现场必须补出带母单号的新标签，应作为**新标签版次／换贴**按现有追溯规则处理，不能悄悄覆盖原任务内容。扫码结果继续由服务端返回真实母子关系，纸面展示仅方便人眼核对。

## 6. 多工位、多队列打印

### 6.1 路由规则

打印页允许用户勾选多个**“工位＋打印队列”目标**：可同时选不同工位，也可选同一工位的不同队列。只选工位而该工位有多个队列时，必须明确具体队列或使用已显示的默认队列；至少选中一个有效目标。页面提交前展示“目标数 × 每目标份数＝预计总张数”，由用户明确确认，防止误把多选当作备用工位。服务端核对标签业务单、打印权限、客户范围、工位及队列启用状态、模板／纸张能力，不接受客户端上传任意标签 HTML 或 Windows 驱动名。

工位档案至少有工位 ID、名称、启用状态和备注；队列档案以“工位 ID＋队列 ID”标识，记录显示名、可打印标签类型、纸张规格、启用状态和默认标记。每个厂内打印程序持有该工位独立且可撤销轮换的凭据，本机配置多个 `queueId → Windows 队列名` 映射；服务端只保存可选择的逻辑队列，不远程调用厂内打印机。领取接口按目标工位原子选取最早待打印任务，返回目标队列 ID，由该工位程序映射到本机 Windows 队列；未分配到该工位的程序绝不能领取。队列不存在、停用或纸张不符时，明确报失败，不能悄悄转到系统默认打印机。

一次提交形成一个**打印批次**，服务端冻结一次标签内容快照，为每个去重后的“工位＋队列”目标创建一条独立打印任务；各任务各有 `targetStationId`、`targetQueueId`、状态、领取工位、失败原因及出纸核实。批次 `requestId` 与目标集合、模板、版本、每目标份数一起参与幂等，同一请求重试返回原批次及原任务列表，目标改变必须换请求号。创建批次和全部任务应在同一事务提交，避免只登记部分目标。多目标表示**每个目标都打印**，不是任选其一；一处失败不自动让另一处加印。任务已领取后不允许静默改目标；转工位或队列须显式取消确定未出纸的目标任务并新建关联任务，记录原因和操作人。现行实现中未领取的 `PENDING` 可直接改派，其他可改派状态须先记录精确核纸结果 `确认未出纸`；旧目标取消与保留原快照、份数的新关联批次同事务提交。`LEASED` 禁止改派，`UNCERTAIN` 必须先人工核纸，不自动重试或改投。

现有 `PrintJob.stationId` 表示**领取后的工位**，创建时为空，不能直接拿它充当目标工位。实施时在 V61 新建批次和目标任务表，批次快照使用 `LONGTEXT`，原任务快照列与内容不改写。旧任务没有可靠的目标工位和队列，原 `PENDING`／`LEASED` 统一转为 `UNCERTAIN` 供人工核纸，旧版接单与领取入口返回升级提示；新工位程序仅使用 v2 领取接口。领取、回报继续区分 `PENDING`、`LEASED`、`SPOOLED`、`FAILED`、`UNCERTAIN`；`SPOOLED` 只代表送入 Windows 队列，出纸仍需现场核实。

### 6.2 页面与权限

标签页按工位分组展示可选队列，支持多选、逐目标份数和提交前总张数核对；提交后展示批次号及每个目标的任务号、队列状态、失败原因和出纸核实结果，不能以一个“批次成功”掩盖部分目标失败。手机和桌面共用接口。工位及队列维护入口放在现有配置／标签管理中，按权限显示；普通打印者只看到可用目标，不看到凭据或本机队列路径。工位离线时可排队，但页面要明确提示“待工位上线”；是否允许向离线工位提交由现场流程确定。打印程序启动时逐队列检查本机映射，缺失队列不可领取其任务并须报告错误。

## 7. 拟议数据与接口改动

| 范围 | 拟议改动 | 兼容与约束 |
|---|---|---|
| 客户 | 增加客户档案仓储及列表、创建、修改、停用接口；订单继续存 ID 和名称快照 | 先盘点历史 ID；客户授权和财务引用稳定 ID |

| 工位 | 增加工位与队列档案、独立凭据、打印批次、任务 `targetStationId`／`targetQueueId`、按工位领取和可选目标查询 | 一次多目标提交生成多条任务；旧单目标需盘点；程序按队列 ID 映射本机队列 |

已实施的接口见[API 契约](./16_字段字典与API契约.md)。持久化沿用本地默认内存、MySQL 切换 JDBC；迁移按 V58—V61 追加，未修改已发布迁移。目录、订单、任务、授权和证据都要纳入既有备份与恢复范围。

## 8. 实施顺序与最小验收

1. **主数据与历史盘点：**盘点客户名称／ID、占位材质、运单重复情况和待处理打印任务；确定映射及旧客户端兼容策略。新增客户、材质目录与权限、下拉选择。
2. **统一收货：**完成来源类型、无运单建单、订单号幂等、逐材质明细和库存原子入账；再调整运单多结果查询及唯一索引。拆单按来源明细分配并核对库存。桌面、手机共用页面和服务。
3. **子单标签：**从子单事实带出母单号，更新默认模板、40×30 版式、浏览器与打印程序快照。
4. **多目标打印：**建立工位及队列档案和独立凭据，批次原子生成每目标任务，按工位领取并按队列发送；补齐页面多选、总张数提示、离线提示和人工转目标记录。
5. **现场验收：**在目标电脑和标签机上验证指定工位隔离、纸张尺寸、二维码扫码、断网／卡纸／租约超时与补打核纸。现场结果再写回[项目核心](./00_项目核心.md)。

必要验证覆盖：不同来源每次提交只生成一张母单，按明细生成对应库存事实；重复 `requestId` 返回同一单，内容变更拒绝；同运单新请求能建多张母单，扫码必须选择具体母单；同母单多材质逐行入账、拆单和退回不串材质、不超剩余；客户改名不改变历史快照和权限；材质自定义去重；拆单后标签准确显示所属母单；多工位和同工位多队列提交生成正确任务数，批次重试不增单，两个工位并发领取不串目标，缺失队列不能打到默认队列；离线、租约到期和补打不能自动重复出纸。按改动阶段执行定向测试和现场检查，不把全仓测试与打包作为每一步默认门禁。

## 9. 待用现场样单确认的规则

1. “厂内接收／其他”具体包括客户上门、业务员带回和内部转交中的哪些情形？交接人、照片和签收是否有强制要求？
2. 同一材质分批称重时是否需要保留批次号；跨材质子单如何在纸面显示简短材质摘要，以真实样单确定。
3. 现场工位与队列清单、默认队列、可选权限及离线排队规则；多目标打印默认份数，以实物流程确定。
4. 子单 40×30 mm 标签上，母单号与加工要求、期限的优先级及最小可读字号，以实物样张确认。

同运单多母单、多材质明细和多工位／多队列打印已经确认，不再作为待决策范围；其明细核算与实物出纸仍须按真实样单和设备验证。

## 10. 当前实现边界

收货明细、逐材质库存及按来源行拆单已实现。现行工序交付、质检及后续单据仍以单个 `materialCode` 处理一张子单，因此一张子单跨多种材质时服务端明确拒绝，不能把首条材质误当整张子单；要实现第 4.2 节所述跨材质子单，仍须把后续工序与质检库存转移改成逐材质明细并完成失败回滚验证。母单汇总和既有工序契约只支持一种数量单位，当前同一母单的明细须使用相同数量单位；混合单位需另行扩展汇总及拆单契约。上述两项是尚未完成的功能边界，不属于设备现场验收。
