## 1. 目标与执行原则

目标是让实际岗位人员用少量真实业务资料，连续完成：

**扫快递收货 → 母单／拆单 → 打印标签 → 工序交付 → 质检／返工复检／放行 → 发货 → 库存与证据追溯。**

- 本轮先盘点并归档可证明无运行消费者的实现；仍可达的业务功能先列证据与去留建议。瘦身后再按本计划的场景清单完成闭环测试，按失败证据修复。
- 暂停扩展外围能力；现有财务、审批、导入、设备等功能继续保留，按主线实际需要使用。
- 保持模块化单体及现有分层，复用桌面／手机共享面板，不新建 APP、微服务、通用引擎或另一套业务框架。
- 行数只用于观察规模；不设强制删减比例，不通过删测试、缩写代码、合并大文件制造瘦身结果。
- 每次只处理一个业务动作或明确问题，提交后即可核对结果，避免连续大改后集中验收。

## 3. 分批计划与进入条件

| 批次 | 进入条件 | 工作内容 | 交付与完成标准 |
|---|---|---|---|
| A：闭环测试与必要修复 | 当前代码可启动，试用岗位和资料已限定 | 固定环境；先跑正常单，再跑拆单、返工、部分发货和失败重试；发现阻断就修复受影响路径 | 每个场景都有单据编号、结果和证据；数据、权限及重复提交问题得到处理 |
| B：业务写入路径收口 | 测试或调用分析证明存在重复规则、事务差异或兼容路径风险 | 逐个动作盘点页面、API、应用服务、仓储及脚本消费者；迁移到同一业务校验和提交逻辑 | 启用入口职责清楚；正常、失败、重试及必要并发／越权验证通过；旧入口有明确去向 |
| C：代码与文档瘦身 | 替代路径验证通过，候选代码的消费者查清 | 归档无消费者代码及专属测试；消除已证明有害的重复；精简过时专题片段 | 现行功能保持；归档可恢复、不参与构建；搜索和文档入口保持清楚 |
| D：回归与试用复盘 | 实际形成可试用版本或完成一组影响主线的改动 | 在目标数据库及实际设备上重验受影响场景；正式版本发布时按规则扩大验收；复盘维护成本 | 主线场景通过，严重问题关闭；备份恢复可查；留下实际版本和环境记录 |

A 不等待全仓重构。B 可作为 A 中某个缺陷的必要修复提前执行；无证据的整理进入后续候选。C 按功能分批推进，不一次清空兼容代码或演示仓储。D 的现场结果不能由自动化测试、截图或包结构检查替代。

## 4. 第一批闭环验收清单

以下是待执行清单，未勾选即未完成，不代表本次已验收。

- [ ] 固定代码版本、环境、账号角色、目标数据库、附件存储及试用资料；演示模式与试用数据边界明确。
- [ ] 正常单：收货到发货全部完成；单据、库存台账和页面显示相符。
- [ ] 拆单：子单合计与母单一致；中途失败无半完成状态；重复操作不重复生成库存。
- [ ] 质检：不合格冻结、返工、复检、放行符合限定规则；冻结期间不能绕过限制发货。
- [ ] 部分发货：只扣本次数量和重量；剩余库存及后续发货正确。
- [ ] 重试与权限：重复点击、请求超时和必要并发不重复入账；无权账号不能跨客户查单或办理操作。
- [ ] 现场采集：实际快递一维条码可识别；照片／视频上传、关联、回看及失败补传可用。
- [ ] 标签：实际打印后能在 ERP 内扫码查到对应母单／子单、要求、进度和允许办理的操作；补打不改变身份。
- [ ] 持久化与恢复：重启后单据和证据仍可查；隔离恢复数据库及附件后关键记录可核对。

可以先用内存快速检查页面流程。持久化、事务、安装和恢复结论必须在目标数据库与实际存储上验证；已知安装阻断不能被内存测试通过掩盖。核心文档中的已知数据风险要有定向验证，不能仅凭正常单通过就判定关闭。

## 5. 发现问题后的取舍

| 问题 | 处理方式 |
|---|---|
| 无法启动、安装失败、主线操作阻断 | 优先处理到能够继续测试，限制在实际影响范围 |
| 库存／金额错误、权限绕过、重复入账、部分提交 | 停止受影响业务试用，定位并修复，补相关失败及必要并发／越权验证后继续 |
| 操作容易误解、现场步骤过多、反馈缺失 | 若影响岗位完成任务，在当前业务动作内改善并定向检查 |
| 录像、跨软件扫码、打印方式等现有能力缺口 | 记录触发场景；先确认现有方式能否完成作业，再决定补齐最小功能 |
| 命名不一致、目录不美观、一般重复、文件偏大 | 记录为后续候选，不阻断闭环测试，不顺带全仓整理 |
| 完整主数据、扩展财务、自有销售、新客户端、新硬件 | 留在本轮范围之外，另行决定，不混入缺陷修复 |

缺陷记录最少包含：场景与步骤、期望／实际结果、单据或操作编号、环境／版本、影响等级、修复提交及复验结果。不要保存账号密码或完整客户敏感资料。记录可放在任务或问题跟踪中，核心文档只保留当前阻断和验证摘要。

## 6. 架构收口与归档规则

每次收口一个动作时，只整理这一条调用链：

`页面／共享面板 → API → 应用服务 → 领域规则 → 工作单元／仓储 → 事实与台账`

1. 列出实际消费者，包括页面、导入、设备、脚本、测试及条件装配；区分已有生产调用和纯历史说明。
2. 指定保留的业务动作实现；输入校验、状态转换、权限、幂等和事务归属明确，多个入口可以消费同一实现。
3. 保持前后端契约一致；明确旧入口直接迁移还是暂时适配，不新增一条长期平行路径。
4. 验证正常提交、中途失败及重试；涉及库存、金额或权限时增加对应必要检查。
5. 确认旧消费者迁移完成，连同专属测试归档；共享类型、公共能力和有效行为测试保留。

归档按日期保存原目录结构，写明原因、替代实现、消费者检查和验证依据。历史迁移 append-only，归档业务代码不删表、不清客户数据。内存／JDBC 切换、LIVE／显式 DEMO 等当前配置能力遵守项目规则，不能当作重复代码直接移除。

大服务只在相关职责已经明确、拆分能降低修改影响时拆分；不以创建更多类代替减少重复规则。前端优先复用现有共享面板，后端优先复用已有业务动作和工作单元。

## 7. 上下文、验证与效果衡量

- 默认上下文仍是根 AGENTS＋项目核心；本计划、业务规则、API 和部署专题按任务读取必要章节。
- 当前状态只更新核心文档；本计划只在方法、范围或阶段标准变化时调整，不逐次追加开发流水。
- 本地默认搜索排除归档；显式追历史时读取，不把旧提示词当现行命令。
- 每个增量执行 AGENTS 规定的最小充分验证；文档变更只查差异、链接和格式。局部修复不自动联跑前后端全量测试或打包。
- 正式版本发布验收、公共改动影响广泛或定向验证不能合理覆盖时，再扩大检查；记录实际执行结果。

| 观察项 | 衡量方法 |
|---|---|
| 业务闭环 | 已通过的现场场景／本批计划场景；失败项说明阻断原因 |
| 数据可靠性 | 重复入账、部分提交、越权等问题的复验结果 |
| 重复实现 | 同一业务动作有几套独立规则和提交逻辑；以调用链盘点为准 |
| 修改影响 | 一个局部需求需改哪些模块／文件，为什么需要跨模块 |
| 代码规模 | 运行源码、测试、第三方代码、SQL／脚本分别统计；同口径比较 |
| 上下文成本 | 完成一个具体任务实际需要读哪些文件，是否仍被迫通读历史 |

首次执行时再记录重复入口数、现场场景结果和修改影响等基线；尚未测量的指标标为未测，不预填完成比例。治理是否有效由业务通过、错误减少及修改范围收敛共同判断。
