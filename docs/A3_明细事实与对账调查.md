# A3 明细事实与对账调查

> 2026-10-19 首个只读增量。测试服务器运行库为 V63；本次仅执行只读事务和源码核对，没有写入、迁移或清理业务数据。完整资产来源见[A0 固定基线与资产清单](./A0_固定基线与资产清单.md)。

## 1. 当前写入与读取链

| 动作 | 当前代码路径 | 事实表及兼容语义 |
|---|---|---|
| 收货建母单 | [MobileIntakeService](../backend/src/main/java/com/zhubao/erp/business/app/MobileIntakeService.java) → [BusinessOperationService](../backend/src/main/java/com/zhubao/erp/business/app/BusinessOperationService.java) → [JdbcBusinessDocumentRepository](../backend/src/main/java/com/zhubao/erp/business/infra/JdbcBusinessDocumentRepository.java)、库存服务 | 母单、`biz_mother_order_item` 与 `inv_stock_ledger` 同次写入。显式逐行收货才标记 `INTAKE_LINES:` 并写 `biz_receipt_line`，随后更新母单汇总；旧单读取明细时从母单合成一条只读行。 |
| 拆单 | [MotherOrderSplitService](../backend/src/main/java/com/zhubao/erp/business/app/MotherOrderSplitService.java) → 单据仓储、库存服务 | 旧路径写子单和库存流水，不写来源分配；`INTAKE_LINES:` 路径核对每条来源余额，为子单写 `biz_child_line_allocation` 和逐来源库存流水。 |
| 发货 | BusinessOperationService → JdbcBusinessDocumentRepository、库存服务 | 出库主单、`biz_outbound_order_item` 与库存流水同次写入；当前 Java 读取出库主单及台账，未发现读取旧出库明细的 SQL。 |

两张旧明细表来自[V14 迁移](../backend/src/main/resources/db/mysql/V14__m3_business_document_contract.sql)，当前 Java 只执行插入；逐行收货与来源分配来自[V60 迁移](../backend/src/main/resources/db/mysql/V60__m3_receipt_line_allocation.sql)，已有读写消费者。仓库外报表、导出和打印程序是否直接查询旧明细仍未核实，不能把当前 Java 的“只写”解释为整个系统不再需要这些表。

## 2. 测试库只读结果

使用[可复跑 SQL](../scripts/a3-readonly-audit.sql)在测试服务器 MySQL 执行 `START TRANSACTION READ ONLY`；脚本只输出聚合数量和异常计数，不输出客户或单据明细。

| 对象 | 行数 | 已核对关系 |
|---|---:|---|
| `biz_mother_order`／`biz_mother_order_item` | 3／3 | 每张母单恰有一条旧明细；材质、数量、单位、重量和流水号与母单一致；母单流水的数量、重量和来源维度一致。相关异常计数均为 0。 |
| `biz_receipt_line` | 0 | 没有 V60 逐行收货样本，不能验证新旧明细共存与母单汇总。 |
| `biz_work_order`／`biz_child_line_allocation` | 2／0 | 两张子单均属非 `INTAKE_LINES:` 的旧路径；子单及流水的数量、重量和来源维度一致，子单合计未超过母单。逐行拆单无样本。 |
| `biz_outbound_order`／`biz_outbound_order_item` | 0／0 | 没有发货样本，零行不是停写依据。 |
| `inv_stock_ledger`／`inv_stock_balance` | 5／5 | 流水为 `inbound_confirm` 3 条、`work_order_split` 2 条；母单和子单引用的流水均存在。余额表仅核行数，本轮没有把余额与全部维度重算。 |

拆单决定另有 `KEEP` 2 条、`SPLIT` 1 条；未发现逐行来源子单缺分配、子单无母单、出库无旧明细或主单缺引用流水，但后两类检查因没有出库数据而**不具备证明力**。上述结论只覆盖这一个 3 张母单的测试库，不代表客户库或新流程已通过对账。

在测试机 Linux shell 中复核时，可将 SQL 文件复制到测试机，再于运行目录执行：

```sh
sudo docker compose exec -T mysql sh -c 'mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" --batch "$MYSQL_DATABASE"' < /path/to/a3-readonly-audit.sql
```

## 3. 收口判定与下一增量

| 候选 | 当前判定 | 进入实现的条件 |
|---|---|---|
| V14 两张旧明细停止写入 | 待收口，暂保持写入；旧母单明细在现有样本与母单重复，旧出库明细无样本 | 取得逐行收货与拆单、发货各至少一条可核样本，核对旧新明细、台账和旧单兼容读取；确认仓库外消费者，再决定兼容期及停写位置。 |
| V60 逐行收货和来源分配 | 保留；代码已有余额与来源校验 | 在隔离 MySQL 或经许可的测试数据中验证多来源、部分拆分、失败回滚及重复请求；真实库出现样本后用本脚本复核。 |
| V14／V60 历史表和迁移 | 保留 | 迁移 append-only；本轮没有删表或改已发布脚本的依据。 |

2026-10-19 已补充 H2 MySQL 模式的 JDBC 定向用例：两条来源收货后，第二条来源分配的数据库约束故意失败，子单、来源分配、拆单决定和库存流水均回滚；解除约束后沿用同一请求编号成功拆单，再回放不重复写入。`IntakeReceivingTest` 4 项通过。它验证 JDBC 工作单元，不代表真实 MySQL 的迁移和锁行为已验收。

下一小增量优先在隔离 MySQL 建立“逐行收货 → 多来源拆单 → 库存流水”对账样本，再处理发货链；在有实际数据和外部消费者结论前不停止旧明细写入。
