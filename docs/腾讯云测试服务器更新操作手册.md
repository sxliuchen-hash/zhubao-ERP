# 腾讯云测试服务器更新操作手册

本手册供接手本项目的开发者和 AI 助手更新**腾讯云测试服务器**使用。客户现场与正式生产环境按[部署专题](./19_Docker一键部署与离线交付.md)执行，不能把测试服务器的地址、证书和 SSH 别名照搬过去。

状态核对日期：2026-10-16。后续执行前须重新核对仓库与服务器，不能把本页的“当前”视为永久事实。

## 1. 固定边界与当前状态

| 项目 | 当前事实 |
|---|---|
| 测试入口 | `https://106.55.226.166/`；以[项目核心](./00_项目核心.md)的最新部署记录和服务器现状再次核对 |
| 本机 SSH 别名 | `zhubao-cloud`；只使用已有 SSH 配置，不在文档或命令输出中记录私钥、密码 |
| 服务器运行目录 | `/opt/zhubao-erp/runtime/`；`.env`、Compose 配置和 `DEPLOYMENT.json` 是运行状态资料 |
| 发布目录 | `/opt/zhubao-erp/releases/<版本>/`；保留上一版镜像、配置与回滚资料 |
| 数据 | MySQL 数据卷、附件卷和备份卷独立于代码；更新容器不等于升级数据库 |

`scripts/update-cloud-test.ps1` 和 `scripts/apply-cloud-test.sh` 目前是**未提交、未完成验证的工作区草稿**，不能仅因文件存在就直接执行。现行 `deploy/docker-compose.yml` 的前后端镜像共用 `ZHUBAO_IMAGE_TAG`。草稿脚本的 `-Part frontend` 或 `-Part backend` 会改写这个共同标签，却只构建并重建一侧，导致另一侧的配置目标与实际运行镜像不一致。草稿还没有完整的数据库／附件备份、前端版本核对和单侧回滚验证，部署备注仍写死为旧标签需求。

**用户明确要求更新测试服务器时，可以在完成本手册检查后执行；仅要求开发代码或写文档时，不要自行切换服务器。** 不上传 `backend/src`、`frontend/src`、`.git`、依赖目录或凭据；只上传需要的编译产物或经门禁验证的运行包。不执行 `docker compose down -v`，不删除 MySQL、附件或备份卷。

## 2. 先确定更新范围

1. 在仓库根目录读取 `AGENTS.md`、[项目核心](./00_项目核心.md)和本手册，检查 `git status --short`、`git rev-parse HEAD`。列出本次要发布的提交、工作区改动及与已部署版本的差异。未明确纳入的未提交改动不得顺带发布。
2. 对照 `frontend/src/App.vue` 的实际调用链，判断是仅前端、仅后端、前后端、数据库迁移，还是安卓 APK。前后端接口同时变化时必须部署相互兼容的两侧。
3. 检查 `backend/src/main/resources/db/mysql/V*.sql` 是否比测试服当前版本新增迁移。新增迁移走第 5 节的受控流程；不得把“容器已启动”当作“数据库已升级”。安卓壳代码变化需要另行制作和安装 APK，网页更新不会更新已安装的 APK。
4. 依据 `AGENTS.md` 只执行本次变更所需的定向测试。打包时若同一代码状态已通过相关测试，可用 `-SkipTests` 复用结果，并记录实际复用的测试。

当前脚本尚未修复时，**不要使用 `-Part frontend` 或 `-Part backend` 直接切换**。需要快速更新单侧时，应先修复并验证独立镜像标签与回滚逻辑；无法确认时，按完整运行包流程更新两侧。

## 3. 更新前的只读核对

在本机记录版本、改动和验证结果；登录服务器后先核对运行状态，不修改配置：

```powershell
git status --short
git rev-parse HEAD
ssh zhubao-cloud
```

在服务器终端执行：

```bash
cd /opt/zhubao-erp/runtime
sudo docker compose ps
sudo docker ps --format '{{.Names}} {{.Image}} {{.Status}}'
cat DEPLOYMENT.json
curl -kfsS https://127.0.0.1/actuator/health
```

只在此测试服务器的自签证书场景使用 `curl -k`。确认实际 Compose 项目、容器镜像、持久化卷、数据库版本和回滚资料；不要仅凭 `DEPLOYMENT.json` 推断运行版本。记录预更新首页和健康检查结果。若服务器状态与文档不符、备份不可用、已存在失败迁移，先定位原因，不继续切换。

## 4. 当前可执行的完整运行包路径

需要在草稿脚本修复前更新测试服务器时，使用[部署专题第 9 节](./19_Docker一键部署与离线交付.md#9-更新与回滚)的完整运行包流程。构建命令示例：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/docker-build-package.ps1 -Version <本次唯一版本> -SkipTests
powershell -ExecutionPolicy Bypass -File scripts/verify-runtime-package.ps1 -PackagePath .deploy-artifacts/zhubao-erp-runtime-<本次唯一版本>.zip
```

`-SkipTests` 仅在本次实际相关测试已通过时使用。完整包会包含前后端镜像，适合当前共用镜像标签的 Compose 配置。上传前核对 ZIP 与 `.sha256`，服务器上解压到新的发布目录，保留旧目录和旧镜像。包内 `.env` 来源于示例文件，**必须沿用并核对当前运行配置，不能用包内默认值覆盖数据库密码、签名密钥或证书设置**。从新目录启动前，确认 Compose 项目名与现有运行环境相同，且卷映射仍指向原数据卷；项目名变化会创建另一组卷，不能据此误认为数据丢失或空库可初始化。

切换前保存当前 `.env`、Compose 配置、`DEPLOYMENT.json`、前后端镜像身份及回滚命令。实际切换应只重建本次需要的前端／后端容器，不重建 MySQL。数据库备份与迁移按第 5 节执行。若这些条件无法核实，停止部署，不猜测旧镜像标签或卷名。

## 5. 数据库与附件

任何涉及新增 `V*.sql`、持久化结构或升级装配的版本，在切换前按部署专题的[备份](./19_Docker一键部署与离线交付.md#7-持久化与备份)和[数据库升级](./19_Docker一键部署与离线交付.md#8-数据库初始化与升级)章节完成数据库和附件备份，校验备份文件及 `.sha256`，必要时先在隔离库恢复演练。已有库只通过显式的 `upgrade-database.sh plan` 查看待执行版本；核对后才可执行 `upgrade --backup-confirmed`。普通容器启动不会自动升级已有库。

迁移一旦处于 `FAILED` 或 `APPLYING`，停止后续切换并检查结构与备份。MySQL DDL 不能依靠回滚镜像撤销；恢复数据库应使用升级前的完整备份，不能删除迁移记录后盲目重试。附件文件和元数据需要一起保全。

## 6. 切换后的验收与失败处理

1. 核对 `docker compose ps`，确认 MySQL 未被意外重建；前后端镜像身份与本次计划一致。
2. 确认 `/actuator/health` 返回 `UP`，公网首页和必要 API 可访问。前端更新时比较本机构建 `frontend/dist/index.html` 与公网首页 SHA-256，并核对首页缓存响应、`manifest.webmanifest` 和 `sw.js`。仅健康接口为 `UP` 不代表新前端已经生效。
3. 针对本次功能执行一条正常操作和必要的失败／越权检查。涉及附件时检查预览与下载，涉及安卓壳时另在目标 APK 上检查；不要把模拟测试写成现场验收。
4. 更新 `DEPLOYMENT.json` 与[项目核心](./00_项目核心.md)中的实际部署事实：提交、镜像标签、数据库版本、备份与回滚位置、验证结果。记录的是服务器实际状态，不能沿用草稿脚本的固定备注。
5. 健康、版本或关键业务检查失败时，按保存的旧配置和旧镜像恢复容器，再重新核对健康与业务。若执行过数据库迁移，按升级前备份恢复数据库；仅恢复镜像不足以完成回滚。保留失败日志与产物，不覆盖证据。

## 7. 一键脚本转为可用前的修复条件

后续可以把草稿收敛为一条本机命令，例如 `powershell -ExecutionPolicy Bypass -File scripts/update-cloud-test.ps1 -Part both -Tag <版本>`，但须先完成以下事项并验证：

- 前后端使用独立的镜像标签和部署记录；单侧更新后的 `docker compose config`、实际容器与下一次启动均一致。
- 发布前检查工作区范围、迁移、必要测试、备份与产物哈希；不再无条件宣称已通过测试。
- 服务端先保存旧配置与镜像身份，切换后检查健康、前端资源版本和本次关键 API；失败时按更新范围恢复。
- 数据库迁移保持显式独立步骤，不能被“快速更新”隐式跳过或自动执行。
- 脚本进入版本控制，至少在测试服务器完成一次前端、一次前后端和一次失败回滚演练，再将命令标为日常可用。

每次交接给其他模型时，提供本次目标提交、期望更新范围、是否含迁移及测试服务器身份；模型应先报告核对结果和实际执行记录，不能只回复“部署成功”。
