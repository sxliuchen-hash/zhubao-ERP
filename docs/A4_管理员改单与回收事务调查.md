# A4 管理员改单与回收事务调查

> 2026-10-19 起分步处理。测试服务器 V63 运行库仅执行只读聚合 SQL；本地补充改单原子性实现与 H2 MySQL 模式定向测试，没有修改测试服务器业务数据。A4 全部动作范围和验收条件见[架构升级总方案](./架构升级总方案.md)。

## 1. 页面到写入的链路

| 动作 | 页面／API → 服务 → 仓储 | 当前边界 |
|---|---|---|
| 母单、子单改正 | [运维页改单面板](../frontend/src/features/m1/OrderMaintenancePanel.vue) → [前端 API](../frontend/src/services/orderMaintenanceApi.ts) → [控制器](../backend/src/main/java/com/zhubao/erp/business/web/OrderMaintenanceController.java) → [OrderMaintenanceService](../backend/src/main/java/com/zhubao/erp/business/app/OrderMaintenanceService.java) → 单据仓储 | 要求管理员和原因，但请求没有 request ID、版本或预期值。原实现先覆盖主单字段，再独立写 `biz_order_adjustment` 文本记录；本地首个修复已让母／子单字段与调整记录共用一个 JDBC 事务。 |
| 回收母单／子单 | 同一页面、API、服务 → 单据仓储、旧打印仓储、目标打印仓储 | 母单回收依次标记母单、子单和相关打印任务；恢复按批次依次清标记。各仓储新开连接并各自提交，某一步失败会留下部分回收或恢复状态。库存流水、余额、财务记录和附件没有同步冲正。 |
| 打印任务改正 | 同一页面、API、服务 → 旧打印仓储或目标打印仓储、单据调整仓储 | 打印份数、工位或队列覆盖写入后再记文本调整；两次写入无共享事务。已领取目标任务也允许改目标，出纸及队列侧状态需要单独确认。 |

V62 迁移仅追加回收标记与 `biz_order_adjustment`；不提供业务版本或幂等约束。`BusinessWorkUnit` 能处理采用 `WorkSession` 的命令，但此服务目前不使用它；给服务外层增加普通事务注解也无法自动接管仓储内新开的 JDBC 连接。现有[单元测试](../backend/src/test/java/com/zhubao/erp/business/app/OrderMaintenanceServiceTest.java)覆盖管理员权限、成功改正及回收恢复。新增[JDBC 失败注入测试](../backend/src/test/java/com/zhubao/erp/business/infra/JdbcOrderCorrectionTest.java)覆盖审计写入失败回滚；跨仓储中途失败、重复或并发提交仍未覆盖。

运行[可复跑聚合 SQL](../scripts/a4-maintenance-readonly-audit.sql)，`START TRANSACTION READ ONLY`；只输出计数，不输出客户或单据内容。

| 调整记录／四类回收标记 | 0／均为 0 | 测试库尚无真实改单或回收动作，无法从当前数据证明成功或失败路径。 |

## 3. 已证实风险与下一步

| 发现 | 证据级别及数据影响 | 建议顺序／进入实现条件 |
|---|---|---|
| 改单覆盖字段与审计记录非原子 | 原源码已证实两次独立提交风险；本地已修复母／子单路径。H2 MySQL 模式故意拒绝母／子单调整记录，真实 MySQL 8.4 拒绝代表性母单记录后，字段覆盖均回滚；测试服务器当前无改单实例。打印任务改正仍分两步。 | **母／子单 P0 原子性增量已本地完成。**请求编号、内容冲突和并发策略仍待后续验证与设计；打印任务另列增量。 |
| 已入账数量、重量、材质、客户可直接覆盖 | 源码已证实覆盖，不修改引用的库存流水、余额、财务和来源分配；造成何种差额取决于具体单据，当前测试库无改单样本。 | **P0 设计与保护。**按是否已入账区分允许的描述改正和需差额／冲正的事实调整；明确历史兼容及页面提示，再放行金额或库存字段的实作。 |
| 整单回收跨三仓储非原子 | 源码已证实逐步独立提交；失败后可能只隐藏部分单据或打印任务。当前测试库无回收样本。 | **P0 后续独立增量。**设计共享会话、批次幂等及可恢复补偿，注入各阶段失败，核对库存／财务仍留存时的用户可见性。 |
| 外部打印设备状态 | 当前只核代码与数据库，未实测设备队列及纸张。 | **待现场决定。**以实际打印批次核对领取、排队、出纸和改派；数据库状态不能代替纸张验收。 |

## 4. 本地首个修复增量

母单和子单改单现由单据仓储同次写入业务字段与 `biz_order_adjustment`。JDBC 连接关闭前统一提交；调整记录因约束失败则回滚字段覆盖。内存仓储也在一个同步方法中写入这两个对象；普通的单独替换与调整记录方法保留给既有调用。`JdbcOrderCorrectionTest` 2 项及 `OrderMaintenanceServiceTest` 4 项通过，覆盖母／子单成功路径、调整记录失败回滚和既有管理员行为。[隔离 MySQL 测试](../backend/src/test/java/com/zhubao/erp/business/infra/A4MysqlOrderCorrectionIntegrationTest.java) 1 项也通过：经现有收货入口产生母单，故意拒绝调整记录后原货品字段未改变，解除约束后字段与记录同次保存。该测试仅在显式设置本机 `a3_verify_` 独立库连接变量时运行；没有执行真实 MySQL 子单、并发或重复请求验证。

该增量不改变页面允许的字段，已入账事实仍可能被直接覆盖，不能将“A4 改单一致性”整体标为完成。后续按独立增量处理业务版本与重试、入账差额／冲正、打印任务改正及整单回收恢复。
