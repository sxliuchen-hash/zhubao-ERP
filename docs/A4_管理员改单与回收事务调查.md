## 4. 本地首个修复增量

母单和子单改单现由单据仓储同次写入业务字段与 `biz_order_adjustment`。JDBC 连接关闭前统一提交；调整记录因约束失败则回滚字段覆盖。内存仓储也在一个同步方法中写入这两个对象；普通的单独替换与调整记录方法保留给既有调用。`JdbcOrderCorrectionTest` 2 项及 `OrderMaintenanceServiceTest` 4 项通过，覆盖母／子单成功路径、调整记录失败回滚和既有管理员行为。[隔离 MySQL 测试](../backend/src/test/java/com/zhubao/erp/business/infra/A4MysqlOrderCorrectionIntegrationTest.java) 1 项也通过：经现有收货入口产生母单，故意拒绝调整记录后原货品字段未改变，解除约束后字段与记录同次保存。该测试仅在显式设置本机 `a3_verify_` 独立库连接变量时运行；没有执行真实 MySQL 子单、并发或重复请求验证。

该增量不改变页面允许的字段，已入账事实仍可能被直接覆盖，不能将“A4 改单一致性”整体标为完成。

## 5. 请求回放和旧页面快照保护

管理员查找母／子单时，服务端对完整当前记录计算 `revision` 摘要；保存时页面提交 `expectedRevision` 和按内容复用的 `requestId`。`BusinessWorkUnit` 先核同账号、同目标、同内容请求；新请求锁定单据行并重新读取，版本不符则整单拒绝。JDBC 的重新读取使用锁定读，避免 MySQL 默认隔离级别下先查命令请求形成的旧快照继续覆盖新单。字段、调整记录及请求结果共用一次连接提交；失败后请求占位也回滚，可用原编号重试。没有新增迁移或覆盖 V62 历史脚本。

内存服务定向测试验证母单同请求回放、改内容拒绝，以及两个旧快照并发改子单只成功一个；隔离 MySQL 8.4 定向测试验证两个母单并发请求只成功一个、胜出请求回放不新增调整记录，以及调整记录失败后沿用原编号成功重试。前端组件验证同内容网络重试复用编号、改内容换编号；API 测试验证母／子单请求确实携带两个字段，TypeScript 检查通过。真实 MySQL 的子单并发、测试服务器业务账号操作与客户端旧版本兼容未实测；旧客户端缺少新字段会收到重新查找或请求编号提示。

母／子单请求保护已随 `cloud-a4-1e783e4-20261019` 发布测试服务器；无业务账号的发布核验见[项目核心](./00_项目核心.md)。后续按独立增量处理已入账差额／冲正、打印任务改正及整单回收恢复；不把母／子单请求保护扩写成这些链路已完成。

## 6. 已入账事实直接覆盖保护（本地，未发布）

收货母单和拆分子单写入时均保存库存流水编号。管理员维护现以该编号识别已入账单据：客户身份与名称、材质、货品、数量、重量不允许通过原字段覆盖；子单工序也不允许覆盖。校验在版本锁定读之后、调整记录写入之前执行，失败不会占用请求编号或留下审计行。页面按响应的 `postedFactsLocked` 禁用这些字段，仍允许改要求和期限。数值只改变小数表示而未改变实际值时不视为数量差异。

内存服务 7 项、JDBC 仓储原子性 2 项、前端组件与 API 3 项及 TypeScript 检查通过；隔离 MySQL 连接本轮未配置，相关 2 项跳过。当前只实现阻止不一致写入，尚无库存差额、财务冲正和工序版本生效流程；旧单库存流水编号缺失但实际已入账的识别，以及业务账号现场操作仍需核对。测试服仍运行上一批 `cloud-a4-1e783e4-20261019`。

## 7. 打印任务改单工作单元（本地，未发布）

旧打印任务与目标任务均按完整当前记录计算 `revision`。管理员保存需要请求编号和旧快照版本；工作单元先锁定任务，再检查版本、状态及目标，最后将任务字段、`biz_order_adjustment` 与请求结果同次提交。JDBC 共用连接，内存模式登记回滚动作；旧的独立连接覆盖方法已移除。旧任务的 `stationId` 是领取工位，不是目标工位；两类任务都只允许 `PENDING` 直接调整份数。工位与队列变更必须使用现有打印批次改派，保留原任务、快照和新批次关联。已领取、已入系统队列、失败、状态不明或已回收任务不可直接覆盖；是否出纸须先核对。

内存服务测试覆盖未领取任务成功、同请求回放、旧快照拒绝和已领取拒绝；H2 MySQL 模式故意使调整记录写入失败，证实任务份数、审计和请求占位一同回滚，同编号可重试。后端服务与仓储共 13 项、前端 API 与面板 5 项及 TypeScript 检查通过。真实 MySQL 并发、目标电脑队列和纸张未实测；打印批次初始份数保留原请求，后续改单的实际份数以目标任务和调整记录为准。测试服仍运行 `cloud-a4-1e783e4-20261019`。

## 8. 母／子单整批回收与恢复工作单元（本地，未发布）

母单或子单的回收与恢复现在需要请求编号。母／子单标记、同批旧打印任务和目标打印任务标记，以及请求结果写入同一工作单元；JDBC 仓储使用同一连接，内存仓储登记撤销动作。母单恢复仅解除原回收批次的子单与打印标记，原先单独回收的子单不会被误带回。失败请求不占编号，同编号同内容可重试或回放；换内容复用编号拒绝。页面在失败重试时沿用编号，成功后清除缓存。

内存失败注入覆盖回收中途失败和重试，H2 MySQL 模式在最后一个打印仓储强制约束失败，验证回收与恢复的单据、打印标记及请求记录一同回滚；后端相关 12 项、前端 6 项及 TypeScript 检查通过。库存流水、余额、财务和附件不随隐藏动作冲正；已送系统队列与实物纸张也不由数据库标记撤回。真实 MySQL 并发、业务账号和设备现场未实测。测试服仍运行 `cloud-a4-1e783e4-20261019`。

## 9. 单独打印任务回收恢复工作单元（本地，未发布）

两类单独打印任务的回收与恢复也使用请求编号、共享工作会话。标记更新与命令请求结果同次提交，数据库更新以未回收／已回收状态为条件；同编号回放不重复动作，请求结果写入失败则标记回滚。恢复前仍核对关联母／子单未被回收。内存与 H2 MySQL 模式共 15 项相关后端测试通过，其中一项故意在请求结果写入前失败并沿用编号重试。真实 MySQL 并发、业务账号和外部打印设备未实测；数据库恢复标记不表示已送系统队列的纸张可撤回。

## 10. 历史入账来源与冲正边界（本地，未发布）

母／子单缺少 `ledgerCode` 时，维护服务按母单范围补查实际库存流水。母单只要该母单号下有任意流水即视为已入账；子单匹配流水单据号、目标工单号或来源工单号。因此单据号是发货单、工单号仍是子单的流水不会被漏掉。JDBC 用存在性查询，不把整本母单流水载入内存。隔离 MySQL 8.4.11 的 `EXPLAIN` 走 `idx_stock_ledger_mother_time`，不必为这条判断新增索引。内存样本覆盖入库／拆分单据号，以及只有发货单号的流水；隔离库用例删除收货流水后只留发货流水，改数量和工序仍被拒绝。此查询不能证明历史数据完整无漏账。

现有进度页改单申请经财务确认后由 `OrderChangeService` 追加应收差额／红字和工费调整，不覆盖原账；该流程处理要求、期限、路线及金额，不调整库存数量、重量、材质或客户。库存转移目前仅支持正数量和必填目标维度，流水仅保存单组客户／材质维度，不能直接表达通用逆向冲销或跨客户／材质更正。后续库存事实增量应先分录入错误、真实退料、生产损耗与金额变化，明确原流水关联、下游拆分／交付／发货及来源分配的限制，并以追加流水及对应财务处理实现；在这些规则落地前保持原字段拒绝覆盖。测试服仍运行 `cloud-a4-1e783e4-20261019`。

已追加迁移 `V64__m3_stock_ledger_reversal.sql` 和 `ReceiptEntryReversal`：冲正流水用 `source_ledger_code` 指回原收货流水，去向为空，只扣减原余额。`reverseInbound` 必须处在工作单元中；余额不足不会留下半笔流水。隔离 MySQL 8.4.11 已执行到 V64 并验证失败回滚。尚未拆单、交付、发货或形成应收、工资、应付的母单，管理员改正数量或重量时会在同一工作单元里冲正唯一收货流水并追加更正后的收货流水，同时更新母单当前数量和至多一条收货明细。原流水保留。客户、材质、货品、已拆子单和其他库存事实仍拒绝。隔离 MySQL 8.4.11 验证了成功冲正和同请求回放。子单数量、真实退料、生产损耗和金额差额不走这条路径。测试服没有执行 V64，也未发布该改正。

## 11. 回收锁顺序与打印改单复核（本地，未发布）

母／子单标记、两类打印标记和请求结果的写入，在 `workUnit` 已装配时共用 `JdbcBusinessWorkUnit` 的同一条连接；请求结果写入失败会回滚本次标记。内存仓储用撤销动作达到同样效果。H2 失败注入已经覆盖这条回滚，不能代替下面的并发。

原先的缺口是：子单列表和回收标记用另一条自动提交连接读取，单独恢复打印先 `FOR UPDATE` 打印行，再在别的连接上检查单据是否可见。母单回收因此可能看见子单仍在回收站而跳过重标，提交后母单已回收、子单标记却被并发恢复清掉。子单自己的行未标回收时，按子单号恢复打印也看不到母单回收标记。

现在的顺序是：先锁定母单，再按子单号锁定子单，最后按打印任务编号锁定旧任务和目标任务，然后才改标记。可见性检查改为当前事务里的锁定读，能看到已提交的最新回收状态，不会沿用命令开始时的旧快照。子单未标回收但所属母单已回收时，单独恢复两类打印任务都会拒绝。无工作单元的旧调用仍各自提交，正式 JDBC 和内存命令路径都走工作单元。

待领取才是 `PENDING`。已领取对应 `LEASED`，已入系统队列、失败、不确定和已取消都不能原地改份数；SQL 再次限制 `status_code = 'PENDING'` 且未回收。工位或队列变化直接拒绝，须走现有改派，新任务保留原任务编号。这次没有改该边界。

本机临时 MySQL 8.4.11、仅 `127.0.0.1:33067`、库名 `a3_verify_a4lock` 从空库升到 V63 后，[并发测试](../backend/src/test/java/com/zhubao/erp/business/infra/A4MysqlRecycleConcurrencyTest.java) 2 项通过。内存服务、H2 回收和打印改正共 17 项通过。测试服未发布本增量，也没有用业务账号操作。
