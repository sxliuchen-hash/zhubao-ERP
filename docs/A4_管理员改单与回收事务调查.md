> 2026-10-19 起分步处理。首批母／子单改单原子性与请求保护已发布测试服务器；发布前运行库只执行只读聚合 SQL，发布过程没有写入业务单据。业务账号现场操作未实测。A4 全部动作范围和验收条件见[架构升级总方案](./架构升级总方案.md)。

## 1. 页面到写入的链路

| 动作 | 页面／API → 服务 → 仓储 | 当前边界 |
|---|---|---|
| 母单、子单改正 | [运维页改单面板](../frontend/src/features/m1/OrderMaintenancePanel.vue) → [前端 API](../frontend/src/services/orderMaintenanceApi.ts) → [控制器](../backend/src/main/java/com/zhubao/erp/business/web/OrderMaintenanceController.java) → [OrderMaintenanceService](../backend/src/main/java/com/zhubao/erp/business/app/OrderMaintenanceService.java) → 单据仓储 | 要求管理员和原因。原实现无请求编号及版本、字段与调整记录独立提交；本地增量现要求 `requestId`、`expectedRevision`，通过命令工作单元同次提交，旧页面快照不能覆盖新值。 |
| 回收母单／子单 | 同一页面、API、服务 → 单据仓储、旧打印仓储、目标打印仓储 | 本地增量已将母／子单与同批打印标记及请求结果放入共享工作单元。库存流水、余额、财务记录和附件没有同步冲正；单独打印任务回收仍走原仓储路径。 |
| 打印任务改正 | 同一页面、API、服务 → 旧打印仓储或目标打印仓储、单据调整仓储 | 本地增量只允许待领取任务改份数，任务、调整记录和请求结果同次提交。工位／队列变更须走打印批次改派；出纸与队列状态仍需现场确认。 |

V62 迁移仅追加回收标记与 `biz_order_adjustment`；不提供数据库列形式的业务版本。母／子单和打印任务改正使用完整记录快照摘要校验；母／子单整批回收恢复及上述改单使用 `BusinessWorkUnit`。现有[服务测试](../backend/src/test/java/com/zhubao/erp/business/app/OrderMaintenanceServiceTest.java)覆盖权限、回放与旧快照竞争；[改单 JDBC 测试](../backend/src/test/java/com/zhubao/erp/business/infra/JdbcOrderCorrectionTest.java)和[回收 JDBC 测试](../backend/src/test/java/com/zhubao/erp/business/infra/JdbcOrderRecycleTest.java)覆盖故障回滚。当前测试服务器只发布母／子单首批改单增量，后续本地结果不等于现场验收。

## 4. 本地首个修复增量

母单和子单改单现由单据仓储同次写入业务字段与 `biz_order_adjustment`。JDBC 连接关闭前统一提交；调整记录因约束失败则回滚字段覆盖。内存仓储也在一个同步方法中写入这两个对象；普通的单独替换与调整记录方法保留给既有调用。`JdbcOrderCorrectionTest` 2 项及 `OrderMaintenanceServiceTest` 4 项通过，覆盖母／子单成功路径、调整记录失败回滚和既有管理员行为。[隔离 MySQL 测试](../backend/src/test/java/com/zhubao/erp/business/infra/A4MysqlOrderCorrectionIntegrationTest.java) 1 项也通过：经现有收货入口产生母单，故意拒绝调整记录后原货品字段未改变，解除约束后字段与记录同次保存。该测试仅在显式设置本机 `a3_verify_` 独立库连接变量时运行；没有执行真实 MySQL 子单、并发或重复请求验证。

该增量不改变页面允许的字段，已入账事实仍可能被直接覆盖，不能将“A4 改单一致性”整体标为完成。

## 5. 请求回放和旧页面快照保护

管理员查找母／子单时，服务端对完整当前记录计算 `revision` 摘要；保存时页面提交 `expectedRevision` 和按内容复用的 `requestId`。`BusinessWorkUnit` 先核同账号、同目标、同内容请求；新请求锁定单据行并重新读取，版本不符则整单拒绝。JDBC 的重新读取使用锁定读，避免 MySQL 默认隔离级别下先查命令请求形成的旧快照继续覆盖新单。字段、调整记录及请求结果共用一次连接提交；失败后请求占位也回滚，可用原编号重试。没有新增迁移或覆盖 V62 历史脚本。

内存服务定向测试验证母单同请求回放、改内容拒绝，以及两个旧快照并发改子单只成功一个；隔离 MySQL 8.4 定向测试验证两个母单并发请求只成功一个、胜出请求回放不新增调整记录，以及调整记录失败后沿用原编号成功重试。前端组件验证同内容网络重试复用编号、改内容换编号；API 测试验证母／子单请求确实携带两个字段，TypeScript 检查通过。真实 MySQL 的子单并发、测试服务器业务账号操作与客户端旧版本兼容未实测；旧客户端缺少新字段会收到重新查找或请求编号提示。

母／子单请求保护已随 `cloud-a4-1e783e4-20261019` 发布测试服务器；无业务账号的发布核验见[项目核心](./00_项目核心.md)。后续按独立增量处理已入账差额／冲正、打印任务改正及整单回收恢复；不把母／子单请求保护扩写成这些链路已完成。

## 6. 已入账事实直接覆盖保护（本地，未发布）

收货母单和拆分子单写入时均保存库存流水编号。管理员维护现以该编号识别已入账单据：客户身份与名称、材质、货品、数量、重量不允许通过原字段覆盖；子单工序也不允许覆盖。校验在版本锁定读之后、调整记录写入之前执行，失败不会占用请求编号或留下审计行。页面按响应的 `postedFactsLocked` 禁用这些字段，仍允许改要求和期限。数值只改变小数表示而未改变实际值时不视为数量差异。

内存服务 7 项、JDBC 仓储原子性 2 项、前端组件与 API 3 项及 TypeScript 检查通过；隔离 MySQL 连接本轮未配置，相关 2 项跳过。当前只实现阻止不一致写入，尚无库存差额、财务冲正和工序版本生效流程；旧单库存流水编号缺失但实际已入账的识别，以及业务账号现场操作仍需核对。测试服仍运行上一批 `cloud-a4-1e783e4-20261019`。

## 7. 打印任务改单工作单元（本地，未发布）

旧打印任务与目标任务均按完整当前记录计算 `revision`。管理员保存需要请求编号和旧快照版本；工作单元先锁定任务，再检查版本、状态及目标，最后将任务字段、`biz_order_adjustment` 与请求结果同次提交。JDBC 共用连接，内存模式登记回滚动作；旧的独立连接覆盖方法已移除。旧任务的 `stationId` 是领取工位，不是目标工位；两类任务都只允许 `PENDING` 直接调整份数。工位与队列变更必须使用现有打印批次改派，保留原任务、快照和新批次关联。已领取、已入系统队列、失败、状态不明或已回收任务不可直接覆盖；是否出纸须先核对。

内存服务测试覆盖未领取任务成功、同请求回放、旧快照拒绝和已领取拒绝；H2 MySQL 模式故意使调整记录写入失败，证实任务份数、审计和请求占位一同回滚，同编号可重试。后端服务与仓储共 13 项、前端 API 与面板 5 项及 TypeScript 检查通过。真实 MySQL 并发、目标电脑队列和纸张未实测；打印批次初始份数保留原请求，后续改单的实际份数以目标任务和调整记录为准。测试服仍运行 `cloud-a4-1e783e4-20261019`。

## 8. 母／子单整批回收与恢复工作单元（本地，未发布）

母单或子单的回收与恢复现在需要请求编号。母／子单标记、同批旧打印任务和目标打印任务标记，以及请求结果写入同一工作单元；JDBC 仓储使用同一连接，内存仓储登记撤销动作。母单恢复仅解除原回收批次的子单与打印标记，原先单独回收的子单不会被误带回。失败请求不占编号，同编号同内容可重试或回放；换内容复用编号拒绝。页面在失败重试时沿用编号，成功后清除缓存。

内存失败注入覆盖回收中途失败和重试，H2 MySQL 模式在最后一个打印仓储强制约束失败，验证回收与恢复的单据、打印标记及请求记录一同回滚；后端相关 12 项、前端 6 项及 TypeScript 检查通过。单独回收或恢复打印任务仍是原仓储路径，不属于此增量。库存流水、余额、财务和附件不随隐藏动作冲正；已送系统队列与实物纸张也不由数据库标记撤回。真实 MySQL 并发、业务账号和设备现场未实测。测试服仍运行 `cloud-a4-1e783e4-20261019`。
