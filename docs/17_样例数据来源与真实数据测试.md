# 来料加工进销存与生产管理系统 样例数据来源与真实数据测试

**文档版本**：V1.0
**更新日期**：2026-07-07
**用途**：记录样例数据来源、外部参考、真实数据测试边界和后续数据治理要求

---

## 1. 目标

项目不能长期依赖临时编造样例。样例数据必须服务四件事：

- 产品评审：让业务人员按真实链路检查页面、字段和状态。
- 自动化测试：让后端、前端和浏览器验证都有稳定数据。
- 现场试点：让硬件、PWA、标签、视频、称重都能用同一批样例复测。
- 验收交接：让每条需求能落到单据、台账、附件和审计证据。

---

## 2. 本轮浏览器调研来源

本轮按“优先公开官方资料，不采集真实客户隐私数据”的原则校准样例结构。

| 来源 | 用途 | 对本项目样例的影响 |
|---|---|---|
| ERPNext Manufacturing / Work Order / Job Card / Stock Entry 官方文档 | 制造工单、工序作业、库存流转参考 | 样例围绕母单、子工单、工序报工、库存台账组织 |
| Odoo Manufacturing / Quality 官方文档 | 制造、质量检查、返工处理参考 | 质检样例必须包含缺陷、处理动作、复检和放行边界 |
| InvenTree Stock / Build Order 官方文档 | 开源库存、构建/生产单、库存状态参考 | 首页和库存页按业务对象、工位、库存状态、动作入口组织，而不是只做指标卡 |
| ERPNext Sales Return 官方文档 | 从原出库/销售单据创建退货并回增仓库库存的参考 | 客户退货样例必须保留原出库单、退回物流、原因、证据和反向库存台账 |
| GS1 SSCC / 标识键官方资料 | 标签、批次、物流追溯编码参考 | 样例编码保留母单、工单、质检单、附件编码和业务对象绑定 |
| MinIO / S3 对象生命周期与保留策略文档 | 附件、视频、对象存储、归档策略参考 | 文档附件样例包含 `storageLocation`、`storagePolicy`、`checksum`、兜底动作 |

当前样例仍是“业务相似数据”，不是客户真实生产数据。后续现场试点时必须用脱敏真实单据替换。

M3.25 前端作业台整改继续沿用上述资料，但用途限定为“信息架构和样例口径校准”：首页将参考提示细化为 ERPNext Work Order/Job Card、Odoo Shop Floor/Quality Checks、InvenTree Stock/Build Orders 三类样例依据，用于约束工单、工序、现场优先级、质检点、批次、库位和追溯结构，不表示当前已经完成这些开源系统的二开集成。

M3.26 将上述样例映射继续下沉到来料母单页和生产工单页：来料页必须同时展示客户所有权、拆包称重、视频兜底、标签追溯和确认入库动作；生产页必须同时展示工位负载、工单池、当前工单、称重交接、工序模板和提交报工动作。样例不能只用于首页看板。

M3.27 根据页面评审反馈继续校正 UI 呈现：样例数据不能被大标题和说明区遮住，首页、来料母单、生产工单必须优先让阻断队列、母单池、工单池、证据/称重动作在普通桌面首屏尽早出现，并避免页面级横向滚动。

M3.28 将样例映射继续下沉到质检返工页和库存追溯页：质检页必须同时展示质检阻断队列、今日质检池、质量检查项、返工动作和损耗审批；库存页必须同时展示客户所有权、批次库存、台账明细、追溯阻断队列、证据槽、确认出库和退货入库动作。

M3.29 将轻量审批样例单独沉淀为前端 `approvalTaskFallback`：审批页必须展示待审批任务、自动通过任务、审批证据、工资试算边界、快照锁定和通过/驳回动作。样例来源参考 ERPNext Workflow 的状态/动作思路和 Odoo Approvals 的请求处理模式，但一期只实现固定场景轻量审批，不引入完整流程引擎。

M3.30 将软硬件样例从静态说明页下沉到 `软硬件联动` 作业台：设备兼容池、联动阻断队列、POC 记录、任务健康度和部署拓扑必须来自 `/api/hardware/*` 或本地兜底样例，不能只写在页面说明文案里。硬件样例继续参考 FFmpeg、ONVIF 和 MinIO 的公开资料，但当前只用于 NVR 截取、设备发现、对象存储和人工兜底方案校准，不表示已经完成现场设备直连。

M3.31 将售后复核样例纳入退货链路：客户退货入库只负责从 `SHIPPED-CUSTOMER` 回到 `RETURN-CHECK`，售后复核再根据 `RELEASE`、`REWORK`、`SCRAP`、`FREEZE` 分流库存。这样退货入库、复核结论、证据附件和库存台账不会混成一个不可解释的动作。

M3.32 将 UI 样例验证从“能看到页面”提升到“首屏能支撑评审”：全局外壳、顶栏、侧栏、状态色、表格和移动端密度必须让 1280 桌面视口同时看到总控指标、阻断队列和今日单据池，390 移动视口不得出现页面级横向溢出。

### 2.1 M3.25 样例映射规则

## 4. 真实数据测试要求

后续每个核心功能至少保留三类测试：

| 测试类型 | 要求 | 当前覆盖 |
|---|---|---|
| 单元测试 | 领域服务和映射函数必须验证状态流转、数量、重量、证据字段 | 库存台账、业务操作、复检放行、成品出库、客户退货、售后复核分流、损耗审批/工资试算、轻量审批任务、审批 JDBC 仓储、真实业务链路、文档附件 summary/上传/预览已覆盖 |
| API smoke 测试 | 通过 HTTP 调用验证接口返回真实结构和关键样例编码 | `/api/business/operations/*`、`/api/documents/*`、附件 multipart 上传已覆盖；`/after-sales-reviews` 已验证 `RETURN-CHECK -> REWORK` 分流；`/loss-approvals` 已验证 `formalPayroll=false`、工资试算字段和 `/api/approvals/tasks` 轻量审批处理 |
| 样例一致性测试 | 前端样例必须可被 API 映射和页面使用，不能只是展示文案 | 损耗审批样例已验证标准/实际损耗率、投入/产出称重证据、审批动作和待补称重异常 |
| 浏览器功能测试 | 打开本地页面验证关键模块、按钮、表格、无页面级横向溢出 | 首页表格优先调度台、质检页损耗审批入口已做；文档附件页需持续纳入 |
| UI 结构回归测试 | 首页必须能直接展示业务指标、一期链路、阻断队列、今日单据池、焦点工单、证据链、硬件兜底、开源样例依据和 API 契约；核心业务页必须直接展示业务对象池、当前对象、证据/称重/规则和真实动作入口 | M3.25 前端测试已覆盖“来料加工现场总控”“今日单据池”“当前焦点工单”“轻量审批任务”“证据链健康度”“软硬件结合管理”“样例与开源依据”“模块完成度与真实 API 契约”；M3.26 前端测试已覆盖来料/生产两页的作业台结构和真实动作入口；M3.27 浏览器验证补充检查桌面首屏内容密度和页面级横向滚动；M3.28 前端测试补充质检/库存作业台结构断言；M3.29 前端测试补充审批工作台结构和审批 API 封装；M3.30 前端测试补充软硬件联动作业台结构和硬件 API 映射；M3.32 浏览器验证补充 1280 桌面首屏和 390 移动视口密度检查 |

真实数据测试不得只检查页面文字。至少要检查：

- 业务动作是否写入库存台账。
- 附件是否绑定业务对象、存储位置、校验和和审计事件。
- 样例是否能从前端、后端、文档三处对应同一业务链路。
- 同一客户、母单、工单和物料维度下的连续业务命令是否会保持客户所有权和库存维度不串线。
- 异常路径是否有兜底，例如视频截取失败、称重照片缺失、弱光扫码失败。
- 出库后的退货是否能追溯原出库单、退回物流、入库证据和反向库存台账。
- 退货入库后的售后复核是否能保留原出库、退货单、复核结论、证据和分流台账，且不会绕开返工/报废/冻结状态。
- 损耗审批是否能解释投入、产出、合理转移、允许损耗、超标损耗、扣款和试算工资，且不会被误认为正式工资发放。
- 首页是否能直接暴露车间业务调度表、客户/物料、节点、责任人、状态和下一动作，而不是只展示概念说明。
- 首页是否把外部开源参考落到具体样例映射，而不是只写“参考 ERP/MES”。
- 来料和生产核心页面是否同样承载样例链路，而不是只在首页展示完整度。
- 软硬件联动页是否用设备、任务、POC 记录和部署拓扑解释失败兜底，而不是只写“支持硬件集成”。

## 5. 当前真实化缺口

| 缺口 | 风险 | 下一步 |
|---|---|---|
| 样例仍以固定集合为主 | 页面和 API 可演示，但不代表真实生产聚合 | 将样例迁移到 MySQL seed，并建立真实业务聚合查询 |
| 真实链路测试仍为单份 JSON fixture | 已能验证维度和台账，但还不是现场多单据批量导入测试 | 后续增加 CSV/SQL 脱敏样例导入和批量验收脚本 |
| 附件只做元数据 | 不能真正上传、预览、下载、签名访问 | 接入 MinIO/S3 或 NAS，补上传 API 和预览 URL |
| 硬件联动仍为兼容样例 | 页面已能读取硬件 API，但不能证明真实 NVR、打印机、扫码设备和电子秤已在现场稳定运行 | 组织现场 POC，保存视频截取日志、标签补打记录、弱光扫码失败样本和称重照片 |
| 损耗审批已有试算快照和轻量审批任务 | 可以验证口径、待审批、审批通过/驳回、锁定和 JDBC 持久化，但不能替代复杂审批流、真实权限、工资锁账和工资发放 | 后续接入真实用户/角色、审批 UI、工资单和审计锁定 |
| 外部编码规则未冻结 | 标签和追溯码可能后期返工 | 结合现场标签打印和 GS1 编码原则冻结内部编码规则 |
| 权限审计未接入真实用户 | 无法证明谁上传、谁审批、谁修改 | 接入登录、角色、审批流和审计上下文 |
| 浏览器自动化覆盖不足 | UI 回归可能只靠人工发现 | 后续增加 Playwright/浏览器脚本检查关键工作台 |

## 6. 样例变更规则

1. 新增样例必须同步更新前端数据、后端 API、测试和文档。
2. 样例编码必须能看出业务对象类型，例如 `MD`、`ZD`、`QC`、`FG`、`DOC`、`ATT`、`POC`。
3. 任何“已完成”状态必须能找到对应证据：台账、附件、审计、测试或浏览器验证。
4. 真实客户数据进入测试前必须脱敏，不保留客户隐私、真实联系方式、真实价格或人员敏感信息。
5. 每轮提交必须在 `docs/14_开发进度跟踪.md` 记录验证结果和剩余缺口。
