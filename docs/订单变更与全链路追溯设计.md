# 订单变更、换标、计费与全链路追溯设计

**定位：改单、换标、计费与追溯的业务设计。2026-10-25 清理过时基线；完成范围、发布与现场阻断只查[项目核心](./00_项目核心.md)。** 草稿、财务确认、差额、生效版本及执行轮次已有主路径，后文规则不等于全部待实施或全部验收通过。接口字段见[API 契约](./16_字段字典与API契约.md)。

## 1. 要解决的业务问题

客户在加工途中修改要求、工序、交期或数量时，现场要能迅速找到原料与当前执行单，记录旧要求和新要求，核对已做工序及剩余工序，经财务确认费用后继续加工并换贴新标签。原母单、原子单、质检返工、库存台账、账单和照片视频不能因改动而断链或被覆盖。管理人员需要从一张母单查看有权限范围内的全部经手和修改历史。

这里的“改单”是生产中客户需求变更，不等同于质检失败后的返工，也不等同于丢失标签后的同版补打。三种动作须分别记录原因和业务关联。

## 2. 实现定位与适用边界

从 `frontend/src/features/orders/OrderChangePanel.vue`、`business/app/OrderChangeService.java` 追到财务、标签、扫码和证据消费者。早期“无结构化改单、无版本标签、无差额流程”已失效；实际能力与剩余验收统一见项目核心。

改单不直接覆盖历史交付；管理员录入错误更正、实物退料、生产损耗、质检返工与业务金额差额分别处理。在途分批交工会阻止改变路线的改单生效。现场换贴、完整追溯和真实岗位流程仍须按本设计核验。

## 3. 不可破坏的业务约束

1. 母单号是追溯根。子单、后续执行单、质检返工、标签、账务调整和附件均应能追到母单；不得把客户改单创建成不相关的新母单。
2. 已发生的工序交付、称重、质检、库存和已入账金额只追加更正或反向记录，不原地抹除。历史事实显示其发生时的要求、工序、单价和操作者。
3. 客户收费、工人工费、公司成本分开。改期限、路线、重做或费用时，仍须财务手动确认收费和工费影响，包括确认“金额不变”。只修改子单加工要求文字时直接保存当前要求并留下调整记录，不送财务审批，也不改费用。客户月度协议是默认报价来源，改单的订单级确认不能靠改协议冒充。
4. 新版标签只依据已生效的服务端订单版本生成；同版补打与换新版分开。打印任务送入 Windows 队列不等于实物已出纸或已换贴。
5. 客户范围、工序权限和财务金额权限由服务端分别校验，列表、计数、扫码直查、附件链接和导出使用同一可见性口径。

## 4. 业务身份和记录

| 记录 | 最低内容 |
|---|---|
| 改单申请 | 改单号、母单、受影响工单、客户原始要求和证据、申请人及时间、原因、前后要求／规格／数量／重量／期限／路线、状态、`requestId`、预期版本 |
| 订单版本 | 母单和工单的稳定身份、版本号、生效时间、适用范围、前版与改单号；已完成事实继续指向原版本 |
| 工序执行轮次 | 原工单、新工单或轮次、母单、工序实例、前序交付、改单号、接手／交出人和时间、状态；质检返工保留其独立来源 |
| 财务确认 | 改单号、客户、各受影响工序的计价单位／单价／数量和金额前后值、工人工费影响、已发生与未发生作业的处理结论、确认人及时间、原账单行及调整行 |
| 标签实例与换贴 | 单据、版本、标签实例号、旧标签、打印任务、补打或换版原因、打印状态、实物换贴人及时间 |
| 追溯事件与证据 | 事件类型、原业务编号、母单和工单、操作者与时间、变更前后摘要、证据链接；查询时由各源业务事实汇总 |

若只调整尚未开工的部分，保留原工单号并新增版本；若重新拆分或重做已完成工序，产生带 `supersedes` 关系的新执行单／轮次，仍属同一母单。新轮次不能覆盖原交付；计费和工资按财务确认结论分别决定是否产生新行。现有“单号＋工序”唯一约束要求在实现重复工序时引入工序实例或轮次身份，不能简单放开重复提交校验。

## 5. 改单状态与生效流程

`DRAFT → PENDING_FINANCE → FINANCE_CONFIRMED → APPLIED`；另有 `REJECTED`、`CANCELED`，每次状态变化保存操作者、时间和理由。已生效内容不能退回草稿，错误走下一次更正改单。

1. 业务人员从母单或子单发起申请，录入客户要求、照片／视频或文件，列出受影响的实物、已做工序与待做工序。申请阶段不改变当前生产要求。
2. 组长核对现场在制位置，拟定后续路线和需要重做的工序；若影响数量或重量，列出库存与交接调整，不能直接改余额。
3. 财务逐次确认客户收费、工人工费、已入账处理和预计差额；可填写“无金额变化”或拒绝。确认后的价格快照和结论保留，后续报价变化不得反改该次决定。
4. 有权限人员生效时重新检查工单版本、权限、在制状态与库存余额；订单版本、路线、必要反向／新增台账及改单状态在同一工作单元提交。并发旧版本拒绝，网络重试用原 `requestId` 回放结果。
5. 生效后产生新版标签任务和待换贴事项。打印失败、出纸不明、已出纸未换贴分别显示；人员核对纸张与实物后确认换贴。未换贴完成前，旧版扫码要警示并限制关键提交，例外放行需权限和原因。

拆单当前逐行写库存和子单的事务风险是该方案前置整改；改单不能叠加在未收口的非原子拆单链路上。若客户变更涉及已发货或售后实物，先进入现有退货／售后核对链路，再确定是否可申请生产改单，不直接改已发货工单。

## 6. 计价、工费和账务处理

桌面和安卓财务页面应能一次维护客户的多道工序报价，分别显示雕刻、镶嵌、抛光的单位、单价、生效期间；工人工价另列，不能把客户价当工资价。改单确认记录保留所选报价来源与订单级前后快照。已做部分、待做部分和重做部分分别列数量与计费决定，财务可明确选择原价、改价、减免或单独收费，避免系统自作推断。

已入账账单行保留原金额。需要减额时，复用红字冲销能力并关联原账单行和改单号；需要增加或补差时，新增有独立来源键的正数调整行。现有 `PROCESS|单号|工序` 来源键不能作为重做或多次差额的唯一身份，应以改单／执行轮次／调整序号防重。再次运行月度账单不能悄悄重复计费。对已经核销或收款的金额，财务需按现有核销限制处理，不以改单直接回写已收款。

工资未确认试算会重建，故改单前后工人工费决定应另存独立历史；已确认工资不得覆盖，使用可追溯的调整记录。公司经营报表分别呈现客户应收调整、工资调整和成本影响。具体损耗、重做是否收费／计工资不预设统一答案，由每次财务确认记录决定。

## 7. 标签版本与扫描兼容

新版二维码包含类型、稳定业务单据、业务版本和标签实例身份；确切编码格式实施时写入 API 契约并验证打印尺寸和扫描兼容。新版明文显示母单、工单、版本、客户、当前要求与截止时间，并可显示改单号。服务端只从正式业务记录生成内容，不能接受客户端自填任意单号与要求。

扫描新版旧版本能准确提示过期、关联改单与当前版本；现行 `JG|类型|单号` 不含版本，只能定位原单并标记“版本未知”，不能凭码断言是哪次要求。上线时须明确存量标签换贴范围。母单拆分后扫母单仍让操作者选具体子单。同版补打保留原版本但生成新的标签实例和任务；换版必须关联已生效改单，且不复用同版补打动作。旧标签作废、纸张回收或保留作为证据的结果需记录。

## 8. 母单总时间线和权限

系统桌面订单详情与安卓详情共用服务端聚合查询。沿“母单 → 子单／执行轮次 → 原业务事实”汇总收货及备料来源、拆单、工序接手／交付、百分比、称重和库存、质检返工、改单、财务确认与调整、标签任务和换贴、发货、照片视频。每项保留原单据链接和发生时间；不得复制一套可被手工改写的平行流水。

当前证据按精确目标单号和操作查询，新增聚合需先取得有权业务对象，再逐项查询绑定证据和历史附件。照片／视频上传或预览失败显示待补状态，不伪称已留证。今后的交接明确保存接收人和交出人；旧记录缺失的一方显示“历史未记录”。生产过程查看权限不自动展示客户价格、工资和经营金额，附件预览仍走签名链接及独立授权。

## 9. 实施与验证边界

实现按现有领域拆分：`business` 管改单与执行版本，`finance` 管逐次确认及调整，`label` 管标签实例与打印任务，`document` 管证据关联，`scan`／查询层汇聚时间线；前端桌面和安卓共用服务端接口。持久化沿用内存默认与 JDBC 可切换，新增迁移只追加，历史账单、交付和标签数据不改写。现有 API 契约在接口落地时更新。

后续只处理项目核心列出的未关闭事项，按真实调用链补足事务、权限、追溯与现场验收；不按早期顺序重做已有版本、财务确认和标签能力。定向验收至少覆盖：部分工序已完成后改单、同工序重做、财务拒绝与无金额变化、已入账差额、工资确认后调整、旧版／存量二维码、并发改单、失败回滚、越权附件、真实打印和备份恢复。
