# 来料加工进销存与生产管理系统 开发原则与版本管理规范

**文档版本**：V1.0  
**适用阶段**：M1 起长期适用  
**目标**：约束开发方式、测试门槛、Git 管理、文档更新和交付验收

---

## 1. 开发原则

### 1.1 业务优先

- 所有功能必须能映射到流程、数据、页面、权限、硬件或验收用例。
- 不做脱离车间现场的办公化想象。
- 页面不能直接修改库存余额，只能触发业务单据或业务命令。
- 返工必须走工单模型，不单独发明第二套返工状态机。

### 1.2 工程边界

- 后端采用模块化单体，按业务域分包。
- 前端按业务域拆分页面，公共 UI、数据模型、服务调用独立复用。
- 核心业务规则优先进入后端领域服务，不散落在页面中。
- 接口和页面可以先使用样例数据原型，但必须保留替换为真实 API 的边界。

### 1.3 开源复用

- 权限、菜单、字典、日志优先复用 RuoYi-Vue 体系。
- 图表、Excel、条码、视频处理、文件存储优先复用成熟组件。
- 不重复自研通用 ERP 能力，除非现有开源项目与本项目的客户来料追溯模型冲突。

### 1.4 UI 原则

- 后台界面以工作台、表格、状态、筛选、详情、抽屉为主。
- 车间/PWA 界面以扫码、少录入、强校验、明确下一步为主。
- 不做营销式首页，不用空洞卡片堆砌。
- 每个业务页面必须显示状态、责任人、下一步动作、异常提示和证据入口。

## 2. 测试原则

### 2.1 必跑检查

每次提交前至少运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\check-m1.ps1
```

该脚本覆盖：

- 后端 Maven test。
- 前端 Vitest。
- 前端 TypeScript 检查和生产构建。

### 2.2 测试分层

| 层级 | 要求 |
|---|---|
| 后端领域服务 | 库存、扫码、视频、后续工单/质检/损耗必须有单元测试 |
| 前端数据规则 | 样例数据和状态计算必须有函数测试 |
| 前端页面 | 关键页面必须验证核心业务信息可渲染 |
| 集成验收 | M3 起按真实业务链路跑主验收用例 |

## 3. Git 版本管理

### 3.1 分支建议

| 分支 | 用途 |
|---|---|
| `main` | 可演示、可验证的基线 |
| `feature/*` | 单个功能或页面开发 |
| `fix/*` | 缺陷修复 |
| `docs/*` | 文档专项调整 |

当前小团队阶段可以直接在 `main` 上提交，但每个提交必须保持可运行。

### 3.2 提交要求

- 一个提交只表达一个清晰目标。
- 提交前必须确认 `git status --short` 中没有无关文件。
- 依赖缓存、构建产物、日志不得提交。
- 文档、脚本、测试和代码应随功能一起提交。

提交信息建议：

```text
feat: build m1 business prototype
test: cover m1 dashboard data
docs: update m1 progress report
fix: correct inventory status rendering
```

### 3.3 基线提交

| 基线 | 提交号 | 内容 |
|---|---|---|
| M0 | `170ebea` | 工程基础、M0 测试、文档包、Git 初始化 |

## 4. 文档管理

### 4.1 必维护文档

| 文档 | 更新时机 |
|---|---|
| `01_PRD_产品需求文档.md` | 一期范围、角色、业务目标变化 |
| `02_业务流程与规则设计.md` | 流程、异常路径、状态机变化 |
| `03_领域模型与数据库设计.md` | 表结构、字段、状态枚举变化 |
| `04_页面原型与交互说明.md` | 页面、字段、按钮、校验变化 |
| `07_接口与集成设计.md` | API、扫码、标签、视频任务变化 |
| `08_实施计划与验收用例.md` | 里程碑和验收用例变化 |
| `14_开发进度跟踪.md` | 每次阶段性开发后更新 |

### 4.2 文档变更原则

- 文档不得只写结论，必须写边界和未完成项。
- 验证报告必须包含命令、结果、失败提示和是否阻塞。
- 原型页面与文档不一致时，必须同步修正文档或记录差异。

---

## 5. 交付门槛

每个阶段完成前必须满足：

- 代码可构建。
- 测试通过。
- 文档更新。
- Git 工作区干净。
- 有明确下一阶段风险清单。
