# 架构升级总方案

**编写日期：2026-10-16。状态：规划与代码评估，尚未实施本方案中的改造。**

本文是后续逐项升级的工作清单。实际已交付能力、进度与阻断以[项目核心](./00_项目核心.md)为准；当前代码瘦身的取证与归档规则以[系统瘦身操作手册](./系统瘦身操作手册.md)为准。实施某项时，先重新核对当时的代码、运行库和现场使用情况，再把完成事实写回项目核心。本文不替代[API 契约](./16_字段字典与API契约.md)或[部署手册](./19_Docker一键部署与离线交付.md)。

## 1. 目标与边界

目标是让收货、拆单、标签、工序、质检、发货、库存、财务和附件证据形成可追溯、可恢复、易维护的一条业务链。衡量升级效果时，优先看数据一致性、岗位完成任务的步骤、故障恢复能力和现场响应时间，不以减少表数、文件数或增加架构层数作为目标。

- 保留现有模块化单体、领域内 `domain / app / infra / web` 四层、内存默认与 JDBC 可切换、桌面与手机共用业务服务。
- 保留 `frontend/src/App.vue` 当前 16 个页面及实际调用链。仍可达的财务、审批、登记导入、设备和运维能力需要具体去留证据。
- 已发布迁移原文保持不变；新结构使用实施时下一个连续的 `V{n}__m3_xxx.sql`。历史数据、表和附件原件不随代码归档删除。
- 每批只收口一条业务动作或一个边界清楚的问题，使用受影响链路的最小充分验证。真实 MySQL、手机、打印机或恢复演练只在该批结论确实依赖它们时执行。
- 编写本文时，工作树存在尚未提交的订单维护、会话和部署相关改动。任何实施批次先固定代码版本、迁移目录、部署版本与数据备份，避免把其他在途工作误计入升级结果。

## 3. 目标结构

正式业务事实由对应领域服务处理：

`页面／安卓壳 → API 与权限检查 → 应用服务 → 领域规则 → BusinessWorkUnit／仓储 → 单据、库存和财务事实`

查询可以从这些事实生成岗位视图。写入入口的权限、状态转换、请求编号和事务归属保持明确；同一个业务动作不长期保留两套规则。演示快照继续与正式 `LIVE` 数据隔离。

附件链路按“**原件、元数据、业务引用、派生预览**”区分职责：

1. 原图、原视频作为不可覆盖的证据原件，记录大小、内容类型和 SHA-256。
2. `doc_evidence_attachment` 保存原件身份及位置，`doc_business_evidence_link` 记录它关联的单据、阶段与操作。一个原件可以有多条合法引用。
3. 缩略图、轻量预览和视频封面是可重新生成的派生内容，不能替代原件或成为新的业务证据。需要多种尺寸时，为派生内容建立独立记录，避免复制整条附件元数据。
4. 业务列表按母单／子单、阶段、操作、时间、类型与关联状态检索；物理目录和文件名不承担业务分类。
5. 管理员下线先改变访问状态并保留恢复期；原件清理需要保留规则、备份核验和审计记录共同约束。

## 4. 工作项与实施顺序

优先级含义：P0 影响数据安全、越权或主线正确性；P1 影响日常效率及后续规模；P2 是有证据后再做的整理。排序不等于要求一次性发布。

### A0　固定基线与资产清单（先行）

本轮只读盘点结果见[A0 固定基线与资产清单](./A0_固定基线与资产清单.md)：含测试库 103 表逐表行数／容量、附件对账、消费者矩阵、候选分类及未实测门槛。盘点不等于完成本节要求的当前成套快照与隔离恢复验收。

**范围：**固定 Git 状态、运行镜像、迁移版本、MySQL 结构和附件卷；只读统计表行数与容量、附件数量与总量、缺文件与无元数据文件、最大文件、各页面请求量及响应时间。查明外部报表、打印程序、备份脚本对候选表和接口的使用。

**交付：**可审阅的“入口 → 服务 → 仓储 → 表／文件”矩阵；每项标记保留、待收口、待业务决定，记录数据量、外部消费者和恢复点。明确正式数据与演示数据边界。

**完成标准：**候选表与附件不凭名称判断去留；数据库、附件备份均能在隔离环境恢复，并抽查同一批单据及文件校验和。

### A1　附件原件安全与恢复（P0）

**问题：**手机采集和电脑通用上传的失败清理行为不同；本地流式写入直接落最终路径；管理员下线先删原件再改元数据；数据库备份本身不含文件。

**实施：**统一两条上传入口的文件类型、大小、内容核验和失败语义。流式写临时对象，计算 SHA-256，完成后原子发布；元数据采用明确的待处理／可用状态，并建立中断后的对账与补偿。审计记录失败不得把已保存附件误报成“可重新上传且不存在”。下线先停止访问，保留可恢复原件；物理清理另设受控流程。数据库快照与附件快照记录共同的批次、清单、校验和、数量和恢复结果；定期检查活跃元数据与原件是否匹配。

**完成标准：**覆盖上传中断、元数据失败、重试、服务重启和下线中断；活跃附件无缺失原件，异常对象可报告和处理；隔离恢复后抽样附件与数据库关联及 SHA-256 一致。异地备份目标启用前要完成一次真实上传与恢复。

### A2　附件整理、低清预览与原件访问（P1，依赖 A1）

当前调用链、安全边界与未实测项见[A2 附件访问与预览调查](./A2_附件访问与预览调查.md)。A1 安全增量及 A2 用途签名、流式原件、视频单段 Range、服务端分页筛选、图片派生图和视频封面已在 2026-10-18 发布到测试服务器；跨客户业务账号与手机弱网现场验收仍待完成，进度以[项目核心](./00_项目核心.md)为准。

**实施：**附件页与收货、生产、质检、发货共用按单据分组的服务端分页查询；增加阶段、操作、时间、媒体类型、上传人、待关联／已关联筛选。清单懒加载小缩略图；点开使用轻量图片预览，提供“查看原图”“下载原件”。先为新图片生成派生图，再按访问需要补生成历史图片；方向修正只作用于派生图。视频先生成封面，并让原视频支持分段读取及拖动；视频转码以现场播放数据决定。

**访问边界：**每次申请缩略、预览或原件地址仍校验单据和客户范围；短期签名绑定附件、清晰度和用途。只允许确认安全的内容类型内联显示，其他文件按附件下载，并禁止浏览器嗅探类型。派生图丢失时可以从原件重建，原件丢失必须告警。

**完成标准：**手机弱网先看到缩略图，可显式打开完整原图并按原文件名下载；旧附件仍可回看；无权限账号不能通过列表或地址跨客户取文件；同一单据能找到关联与待关联证据。用约定的现场网络和样例文件记录传输大小、首图时间、原图打开与视频拖动结果。

### A3　数据库事实与重复明细收口（P1，依赖 A0）

2026-10-19 的测试库只读对账、当前消费者和隔离 MySQL 收货／拆单／发货事务补验见[A3 明细事实与对账调查](./A3_明细事实与对账调查.md)；旧明细暂保持写入，测试服务器仍缺 V60 逐行收货与发货样本，仓库外消费者待确认。

**实施：**以收货、拆单和发货各选一条真实链，核对 `biz_mother_order_item`、`biz_receipt_line`、`biz_child_line_allocation`、`biz_outbound_order_item` 与主单、台账的行数及业务含义。为新单据明确唯一明细来源和兼容读法；停止没有消费者且已证明无用的重复写入。`cfg_*`、`biz_workspace_*`、样例和迁移标记分组审计，保留有历史、演示或结构探针用途的表。日期字符串、外键和索引仅对有实际数据风险或查询证据的链路逐项调整。

**完成标准：**新旧单据、拆分余额、发货数量和库存流水可对账；失败回滚与重复请求不产生孤立行；旧库可升级、旧单可读。表数在兼容期允许保持不变。

### A4　主线事务、幂等与改单一致性（P0／P1，按动作推进）

管理员改单与回收的首轮源码边界、测试库只读样本，以及已完成的母／子单改单、打印任务份数改单和四种类型回收恢复事务增量见[A4 管理员改单与回收事务调查](./A4_管理员改单与回收事务调查.md)。已入账事实可用现有进度页改单申请办理要求、期限及财务差额；库存来源更正目前阻止原字段覆盖，库存差额／冲正仍待按业务原因分别收口。本地后续增量尚未发布测试服。

**实施：**逐项核对收货、拆单、岗位交付、质检、发货、备料领退、改单、回收／恢复的页面、API、领域规则、`BusinessWorkUnit` 和 JDBC 写入。每项明确请求编号、内容冲突、重复提交、并发锁、失败补偿及回收对库存和财务的影响。已入账事实需要调整时走可追溯的差额或冲正，不能只改页面上显示的单据字段。

**完成标准：**每个动作有正常、失败、重试及必要并发／越权验证；同一请求只产生一次业务结果；原单、台账、财务与证据关联能解释调整前后。真实 MySQL 验证仅覆盖此次改变的事务链。

### A8　查询性能与运维可见性（P1／P2，依赖 A0 数据量）

2026-10-20 的只读查询计划已合并到本地分支，见[A8 调查](./A8_查询计划调查.md)。当前行数下没有补索引或读模型。

**完成标准：**每个实际交付包的镜像、迁移、配置、备份批次和回滚路径可对应；目标设备与真实 MySQL 的结论单独记录，不把自动化测试当作现场验收。

### A10　桌面、手机与接口契约收口（P1，随业务批次触发）

2026-10-20 的只读对照已合并到本地分支，见[桌面手机对照](./A10_桌面手机对照.md)。现场作业按岗位收起入口，发货主按钮只给出库单。没有改页面，也没有真机验收。

**实施：**同一收货、生产、质检和发货动作继续复用共享面板及服务端规则。逐项核对桌面和手机的必填字段、扫码多候选选择、请求编号重试、会话失效、错误提示与操作后刷新；接口字段、权限和错误码有变化时同步更新现行 API 契约。仅对已经出现重复规则或交互阻断的页面拆分组件，不因文件较大引入新框架。

**完成标准：**同角色在桌面与目标手机得到相同业务结果和权限边界；弱网重试不会重复入账；扫码和附件返回目标不会串单；受影响的接口、组件和安卓壳检查通过。

| 0 | A0 基线、真实附件与表资产清单、候选矩阵 | 只读盘点及隔离恢复；不改业务数据 |
| 1 | A1 上传／下线安全与成套备份 | 附件存储和元数据故障用例、恢复样例；涉及部署装配时验证实际包 |
| 2 | A2 缩略预览、原图、服务端分类检索 | 附件权限和前端定向测试，浏览器及安卓现场文件样例 |
| 3 | A3 收货与发货明细收口 | 单据、库存、旧单兼容、失败回滚；新迁移在隔离 MySQL 演练 |
| 4 起 | A4—A8 按一条业务动作或一个实测性能瓶颈逐项推进 | 每项只扩大受影响的验证范围；A9、A10 随相关批次触发 |

批次 1 和 2 的功能开发可以并行准备，但上线顺序先保护原件。A4 中影响库存、金额、权限或幂等的发现可提前作为单独 P0 增量处理。每批独立语义化提交；功能、架构、进度、阻断与实际验证摘要更新项目核心，接口或部署实际变化再更新对应专题。

## 6. 每项任务的记录模板

后续从本方案取出一个工作项时，至少写清：

1. **当前证据：**入口、调用链、表／文件、现场数据量、外部消费者及已复现问题。
2. **目标与范围：**保留的事实来源、需要调整的页面／API／仓储／迁移、旧数据兼容和明确不处理的相邻问题。
3. **实施顺序：**先扩展和兼容，后切换，最后停用重复路径；文件和数据库无法同事务提交时写明状态与补偿。
4. **验证：**正常、失败、重试、必要并发与越权；按实际影响选择内存、JDBC、真实 MySQL、浏览器、安卓、打印机或恢复演练。
5. **交付记录：**提交号、迁移版本、包与环境、备份批次、前后指标、剩余限制及回滚路径。

**下一项建议：**先执行 A0 的只读盘点，并把 A1 的“下线先删除原件”和“数据库、附件分离备份”作为第一批安全改造。A0 结果可能调整后续优先级；未经盘点不对旧表、旧文件或历史证据执行清理。
