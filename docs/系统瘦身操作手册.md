# 系统瘦身操作手册

**状态：2026-10-14 执行方案，尚未开始代码清理。** 用户决定先彻底盘点并清理已放弃的系统实现，再推进新业务功能。本文定义 Grok 或其他执行者的实际操作步骤；[项目核心](./00_项目核心.md)仍是当前功能、风险和进度的唯一总览。本次没有预先指定“已放弃页面”名单，必须先取证，不能凭命名或主观印象删除。

## 1. 目标和完成定义

从现有可运行系统出发，找出并移出无运行消费者的旧原型、重复实现、专属夹具、失效入口与冗余依赖；对仍可达但业务价值存疑的功能提交去留清单。瘦身完成应使现行行为、权限、数据、部署和恢复能力保持可用，并能用文件清单、调用链和验证结果解释每一次归档。

本轮先做**可证明安全的归档与必要的重复路径收口**。当前 16 个菜单页面仍视为运行范围，除非用户明确确认某项业务退出；“设备”“登记导入”“运维”“财务”等名称不能自行视为废弃。将来要移除可达页面时，单独处理菜单、服务端接口、权限、测试、部署和存量数据，不把页面隐藏当作功能删除。

## 2. 事实基线与保留边界

- 前端入口是 `frontend/src/App.vue` 的 16 个页面、`frontend/src/main.ts` 及其实际调用链；异步加载、`provide/inject`、服务层、共享收货／生产／质检／发货面板也算消费者。
- 后端从仍被页面、移动入口、导入、设备、脚本和外部兼容请求使用的 Controller 向内追踪到应用服务、领域、仓储与安全规则。Spring 自动扫描、`@ConditionalOnProperty`、profile、反射和测试装配不能仅用普通导入搜索判死。
- 必须保留登录、菜单与客户／工序权限、`BusinessWorkUnit`、`StockLedgerService`、内存与 JDBC 双实现、附件文件及元数据、PWA、升级、备份与恢复等现行依赖，除非其替代链路已经实际验证。
- `docs/archive/` 和 `archive/code/` 已是历史，不作为新需求或默认扫描范围；追查某个候选的历史来源时才显式读取。`archive/README.md` 中 2026-10-13 的归档是路径与说明格式参考，不代表本次应恢复旧功能。
- V1—V48 等已发布迁移、迁移索引和校验和保持原文；**归档 Java/Vue 代码不等于删表或清除客户数据**。本轮不执行生产库删除、批量清理或历史迁移改写。
- 用户已提出的安卓、集中打印、客户备料、工序进度和订单改单仍是待实施需求，不把当前未实现的方案误判成“废弃”。

## 3. 候选分类和判定证据

| 类别 | 判定 | 处理 |
|---|---|---|
| 保留 | 现行页面、接口、脚本、条件装配或部署有真实消费者，或属于上述关键依赖 | 记录调用链；不以行数、旧名称或界面不常用为由删除 |
| 可归档 | 查清运行时、类型、测试、脚本、配置和装配后，确认只有专属历史测试或自身互相引用；不再进入运行包 | 按原路径移到 `archive/code/<日期>/`，删除当前装配引用，保留恢复说明，完成定向验证 |
| 待业务决定 | 仍可从现行菜单/API 到达，但怀疑已经放弃，或存在外部消费者／数据语义不明 | 列出用户动作、受影响数据、权限与去留建议；继续处理其他已证实候选，不擅自下线 |
| 待修复再收口 | 与现行链路重复，但新旧路径在事务、权限、幂等或结果上尚不等价 | 先统一业务行为并验证，再归档旧路径；不得仅为减少文件数而拆断调用 |

每个候选至少记录：原路径与功能、当前入口／调用链、`rg` 命中、动态装配与配置、测试和脚本消费者、持久化表／字段和数据影响、替代实现、分类、归档位置、验证结果、提交号。`rg` 无命中只是线索，不能单独证明没有消费者。

## 4. 执行步骤

### 第 0 步：固定工作状态

1. 记录 `git status --short`、`git rev-parse HEAD` 和目标分支；已有未提交改动须先辨认归属，不覆盖他人工作。在独立分支或工作树执行，不在部署中的目录直接清理。
2. 记录现行 16 个页面及页面到 API 的映射、当前 profile 和实际部署模式；`docs/00_项目核心.md` 与 `frontend/src/App.vue` 有分歧时以运行调用链核实后更正。
3. 记录可用的前后端测试、TypeScript／构建状态和已知失败；广泛清理建议先取得同一环境基线，不能把历史测试记录当作本次通过。

### 第 1 步：建立消费者图和候选矩阵

按页面、共享面板、前端服务、后端 Controller、领域服务、仓储、配置、脚本、测试、数据库迁移逐层追踪。先检查代码导入与调用，再检查字符串路由、反射、Spring 扫描、条件装配、定时任务、导入和设备入口、运维与备份脚本。可用 `rg --files` 和 `rg -n` 定向查找；默认不扫描归档目录，确需追历史时用 `rg --no-ignore` 指向具体归档路径。

形成一张可审阅矩阵：**保留／可归档／待业务决定／待修复再收口**。先选高置信度且边界明确的候选。可达页面若被怀疑已放弃，附上实际页面、账号权限、API、数据和移除后影响，供用户决定；此类未决定时不阻塞已证实无用代码的处理。

### 第 2 步：逐批归档与收口

按一条业务动作或一个明确的原型族成批处理，先处理孤立前端夹具或旧组件，再处理后端无消费者原型，最后处理活跃路径的重复实现。每批先列文件与消费者证据，再改当前引用、移动专属代码和专属测试。归档路径为 `archive/code/YYYY-MM-DD/<原相对路径>`，保留原目录层级；在 `archive/README.md` 记录内容、原路径、退出原因、替代链和恢复条件。不要整目录递归搬走仍有消费者的文件，也不要删除可复用测试。

如果涉及可达的旧 API，确认页面、导入、设备、外部调用及权限消费者后才移除；必要时先做兼容转发，再在明确的版本边界退出。若数据库仍有历史数据，保留表和读历史的必要能力。若归档后配置或依赖不再使用，再单独清理配置键、前端依赖、Maven 依赖和脚本入口，并核对运行包。

### 第 3 步：按影响验证和提交

每批执行项目 [AGENTS](../AGENTS.md) 的最小充分验证：文档只查差异与链接；局部前端查相关组件／类型；后端查受影响服务及接口；库存、金额、权限、事务和幂等变化需覆盖正常、失败与必要并发／越权。定向检查通过就提交该批，不为每批重复全量和打包。

整个瘦身若跨越前后端公共路径，最终以当前代码状态运行后端测试、前端测试和生产构建；真实修改打包、部署或升级装配时才跑对应包结构门禁。失败要定位并修复，不能删测试、改断言或标成“既有失败”来获得绿灯。运行包检查不等于现场安装、数据库升级或客户验收。

每批独立语义化提交，提交正文用中文说明归档依据、受影响入口和实际验证。避免 `git reset --hard`、`git clean -fd` 和盲目递归删除；恢复优先使用归档原路径或可审阅的 `git revert`，不得借瘦身清理客户数据。

### 第 4 步：交付盘点结果

最终提交一份候选矩阵与变更清单，列出：已归档文件及原路径、已统一的重复链路、保留理由、待业务决定的仍可达功能、前后端净变化、实际验证及未验证项、各批提交号。把当前功能、架构、阻断与结果摘要更新至 `docs/00_项目核心.md`；规则／接口／部署实际变化才更新对应专题，入口变化更新 README。不要把旧归档文档重新当执行计划。

## 5. 验收标准

- 没有用户明确放弃的菜单仍按原角色可见、可打开；登录、客户／工序权限、扫码、收货、拆单、交付、质检、发货、库存与证据链没有因归档断开。
- 本地内存模式及 MySQL/JDBC 条件装配仍可启动或通过针对性装配检查；历史迁移校验和未变化，原数据未删。
- 新旧业务入口的归档依据可复核；保留或未决的功能有具体调用和数据证据，而不是“看起来没用”。
- 构建、相关测试和实际触发的包门禁结果真实记录；不把未运行项目写作已通过。
- 归档内容能按原路径找回；用户可以根据“待业务决定”清单继续指定下一轮真正要下线的功能。
