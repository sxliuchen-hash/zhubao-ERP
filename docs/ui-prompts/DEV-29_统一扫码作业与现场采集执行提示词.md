# 统一扫码作业与现场采集：小模型总提示词

**日期**：2026-10-11

**用途**：将下方提示词交给执行模型。默认一次推进一个开发增量；用户指定某项时，先核实前置条件。

```text
你在 F:\APPkaifa\zhubao-ERP 开发珠宝 ERP。请实施 docs/29_统一扫码作业与现场采集开发方案.md，目标是统一扫码查单、展示要求与状态、按岗位记录进度和办理收货/报工/质检/发货，并在各步骤复用拍照录像留证能力。

先读取 AGENTS.md 和开发方案。按需读取 docs/02_业务流程与规则设计.md、docs/05_系统架构设计.md、docs/16_字段字典与API契约.md、docs/14_开发进度跟踪.md、docs/23_客户交付版本记录.md。UI 和部署分别按 26/27 与 19，历史归档不作为当前规则。

默认执行第 9 节第一个未完成且前置条件满足的增量，首次先做 S0。一次只推进一个增量，按其中子任务完成契约、实现和验证；不要一次重写全部工作台。不要只给建议，完成本增量可完成的实际工作。S0 只复核和更新执行记录，不修改业务代码。遇到缺少真实业务决定的扩展，按方案首期口径完成不依赖它的工作并报告，不擅自新增规则。

开工要求：
1. 先运行 git status --short 和相关 git diff，区分已有改动与本次责任范围。保护现有 HTTPS/Nginx/手机摄像头和其他文档改动，不覆盖、不回退、不混入提交；不能 git add .。
2. 简单查找用 rg。修改重度测试服务前按 AGENTS 使用调研型子智能体检查调用链和影响面。子任务独立才并行，同一文件编辑、Git 操作以及有依赖的构建测试必须串行。
3. 所有新增代码注释、界面文案和文档使用中文；保持 domain/app/infra/web、内存默认和 JDBC 可切换。新可选依赖遵守兼容构造器规则。SQL 只追加，先查 db/mysql 最新迁移号，不修改旧迁移。

必须遵守的设计：
1. 共用 ScanInput/useScanner、useScanContext、OrderContextCard 和 EvidenceCapture；收货、生产、质检、发货各有业务面板。手机和桌面复用同一表单或业务 composable，不复制一套流程。不把所有状态和分支继续塞入 MobileOpsWorkspace.vue。
2. 复用 cameraBarcode.ts、scanCode.ts、真实单据查询、process-stations、quality-checks、文档上传预览、数量重量表单及原领域命令。原 scan/resolve 只解析格式，固定 allowed=true 不是权限。新增统一上下文查询，服务端登录、数据范围和可操作性判断先于详情返回。
3. 目标扫码只查单，不自动报工或发货。扫到哪个对象就精确定位哪个对象；不得把列表过滤、第一行、默认余额作为提交目标。已拆母单选择真实子单，多余额选择完整物料/仓库/货权/状态维度。A 后扫 B，A 的迟到响应不得覆盖 B；目标输入变化、切页、切单使旧提交上下文失效，附件不转挂新单。运单字段扫码只解析并填写当前物流字段，保留订单、余额和草稿，不触发目标切换查询。
4. 过程记录不产生库存、工资、工序完成或质检结论。正式报工保留岗位及前序规则；质检保留逐条判定、原因及冻结规则。当前原不合格记录会阻断返工后的放行，S5c 必须补最小复检轮次和真实复检判定，保留原历史，不能仅复用现有 release 宣称闭环。确认发货才执行既有库存转移。首期发货准备记录不伪装成已创建出库单或已发货，不新增签收状态机和任意进度百分比。
5. 文件存储和业务证据引用分别管理。同文件去重不得丢跨场景/操作引用；引用唯一键包含目标类型/编码、stage、scene、操作类型/编号、process、clauseNo、附件编号，可空项规范化。stage 是业务阶段，scene 是证据内容，使用方案固定代码。S3 补持久化附件来源类型或可靠来源映射，不能只比较 businessCode。多附件用结构化引用，不拼逗号字符串。操作编号来自真实服务端记录。绑定时验证单据、附件、操作和当前权限，保留历史附件及下线审计。
6. 新来料和未创建出货单的文件先留当前表单，取得正式单号后上传绑定。业务成功后上传/绑定/刷新失败，只补相应步骤，禁止重新建单、交工序或扣库存。先上传但业务未成功的文件显示待关联，不冒充业务成功。
7. S5p 完成有限的幂等/工作单元公共基础；S5a 来料建单/入库、S5b 工序、S5c 初检/开返工/返工报工/复检/放行、S5d 发货分别接入并验证。同一次确认使用稳定 requestId，同键同载荷回放，同键异载荷拒绝。前端禁用按钮、已有重复报错、JVM 锁以及外层加 @Transactional 均不足以证明数据库安全。核实 JDBC 连接和提交边界，确保库存、正式业务事实与成功结果一致，并做失败注入和并发测试。
8. QR 保留稳定身份和旧协议，要求/状态查询服务器。操作人来自会话。客户端不能通过动作码、场景或姓名扩大权限。
9. 不新增工作流引擎、动态表单引擎、第二套库存账或完整离线队列。替换一个入口就清理对应无消费者重复逻辑，避免仅包壳或大面积无关重构。
10. S1 固化扩展字段，S4 前过程记录集合为空且不开放保存动作；S3 只关联已存在的正式操作或保留历史单据证据，S4 再接入过程记录及其证据校验。不得为通过当前增量虚构后续操作记录或提前实现半套后续模型。

验证和交接：
1. 按 AGENTS 只做本次最小充分验证：文档/S0 只查差异、链接和格式；前端局部改动只验相关组件/页面，后端局部改动只验相关服务/接口和调用链；库存、权限和事务改动补对应失败、并发或越权用例。不默认运行前后端全量或生产构建。
2. 全量仅在用户要求、正式发布验收或公共改动广泛且定向验证不足时执行对应一侧；打包和包门禁仅在实际制作交付包、修改装配/部署逻辑或用户要求时执行。普通增量不生成运行包。同一代码状态的相关测试通过后可用 -SkipTests 避免打包重跑，注明复用结果即可。
3. 按实际变化更新文档：功能进度更新 14，入口/使用变化更新 README，交付范围变化更新 23，落地规则/接口更新 02/16。更新开发方案第 11 节，记录真实结果。S0 属调研记录，不冒充业务功能完成。
4. 本次选定的必要验证通过后即可独立语义化提交，不把未触发全量、构建或打包视为阻塞，不另行请求许可。仅提交本增量负责的改动，不混入已有改动；有相关失败或无法隔离时保留并报告。提交标题可英文，正文用中文。
5. 最后用中文简要交接：本次结果、关键文件/契约、实际验证、影响结论的重要缺项、提交和下一项。没有实际打包时不要求包路径，不反复罗列未触发检查。验证已通过且没有新问题时停止，避免为了形式完整重复执行。
```

指定单项时，在上述提示词末尾追加：

```text
本次只执行增量：S1（替换为实际编号）。先核实第 9 节前置项，不跨增量扩大范围；完成后更新执行记录并交接。
```

恢复中断工作时追加：

```text
继续上次未完成的增量。先读开发方案第 11 节及当前 git diff，核实已经完成的部分和真实测试结果，接着补齐，不重写已完成模块，不重复执行已成功的业务写操作。
```
