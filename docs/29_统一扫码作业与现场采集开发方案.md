**执行方式**：按第 9 节逐个增量实施，适合小模型接力；总提示词见 [执行提示词](./ui-prompts/DEV-29_统一扫码作业与现场采集执行提示词.md)。

## 1. 目标、范围与完成口径

目标链路：**统一扫码 → 查询真实单据 → 展示订单要求和状态 → 按岗位选择操作 → 拍摄留证 → 提交业务 → 刷新详情和进度**。

用户已经明确：收货建单、生产进度与报工、质检进度与判定、发货等步骤都应能按需调用摄像头；标签扫码后应能看到订单要求并办理适用业务；基础能力应复用，避免重复代码和巨型组件。

### 1.1 本轮必须覆盖

- 母单、子工单、返工单、出货单和快递运单的统一识别与真实查询。
- 客户、货品、加工要求、岗位要求、期限、数量重量、工序进度、质检和发货情况的权限内展示。
- 手机与电脑共用扫码输入、单据上下文、详情卡片、证据采集和业务面板。
- 收货发起母单、生产过程记录与正式报工、质检过程记录与正式判定、发货准备记录与正式确认发货。
- 照片和短视频关联到具体单据、场景及本次操作，上传失败可单独重试。
- 单据精确定位、防串单、岗位和客户范围控制、业务重试及库存一致性。

### 1.2 首期明确采用的业务边界

| 项目 | 首期执行口径 |
|---|---|
| 拍摄要求 | 默认选拍；不新增未经确认的必拍门禁 |
| 生产进度 | 可重复保存说明及证据；正式工序完成继续调用已有交付命令 |
| 部分数量报工 | 不在过程记录接口过账；分批计量、累计完成量和工资计算须另定规则后扩展 |
| 质检进度 | 保存检查过程，不提前产生合格、不合格、冻结或放行事实；正式判定沿用现有服务 |
| 发货进度 | 支持打包、称重等准备记录；正式确认发货沿用已有成品转已发货命令 |
| 多段物流状态 | 承运、运输、签收、退回等独立状态机与自动物流对接另行确认，不以自由文本修改库存状态 |
| 离线 | 当前页面保留文件和输入并允许重试；刷新后恢复大文件、离线自动过账不在首期承诺内 |
| 标签协议 | 保留 JG 类型编码和历史兼容标签；动态要求及状态查询服务器 |

打包准备记录属于作业动态，不伪装成已经创建正式出库单、已经冻结库存或已经发货。正式状态与准备动态应在界面分别标识。需要扩大上述口径时，先在本文记录业务决定，不让执行模型自行补造规则。

#### 与第 2 节一致、后续仍须处理的事实

- `POST /api/scan/resolve` 只做格式解析。`ScanCodeParser` 对系统码和运单都返回 `allowed=true`，不查单据、加工要求或权限。仓库中不存在 `POST /api/scan/context`。
- 前端不存在 `ScanInput`、`useScanner`、`useScanContext`、`OrderContextCard`、`EvidenceCapture`，也不存在收货、生产、质检、发货四个业务面板。页面不读取 `nextAction`，也不调用 `/api/scan/resolve`。
- 手机收货扫到母单时在本地拼空详情；拍面单只识别条码，不上传留证。质检页没有相机，也没有条款证据。顶栏追溯和进度跳转写入的是文本，各工作台用子串过滤，选中仍可能落到默认行。
- 岗位重复交付、出库号已存在、质检已提交、返工已开过，都是再次拒绝，不回放原成功结果。
- `src/main/java` 中没有 `@Transactional`。`JdbcStockLedgerRepository.save` 自己建连接并提交；母单、出库单、工序交付和质检头在另一条连接保存。库存已变化而单据保存失败的窗口仍然存在。
- 质检不合格后 `frozen` 保持为真。放行要求未冻结，且结果为合格或让步。返工报工在 `BusinessOperationService.reportRework`，只把返工库存转回半成品。没有复检轮次。质检表按订单唯一，不能靠改掉“已提交”校验冒充复检。
- 确认发货先转移成品库存，再保存出库单。来料确认先写待加工入库流水，再保存母单。母单运单字段只有普通索引，不是唯一约束。
- 采集去重键是业务单号加 checksum，不含场景。附件实体没有持久化的对象类型；请求里的 `objectType` 不落库，`businessType` 被写成场景中文。
- 迁移目录最新文件是 `V41__m3_finance_receipt_idempotency.sql`。MySQL 8.4 空库仍会停在 V36 未加引号的 `year_month`。本方案不修改 V36。
- 收付款幂等挂在财务单据的 `idempotencyKey` 上，并在单条连接里提交。可以借鉴同键回放，不能复制后当成库存工作单元。

#### 方案原文未写准、后续增量必须按源码执行

1. `/api/scan/resolve` 不在 `PermissionGuardInterceptor` 的权限表中，未登录也可以调用。S1“未登录拒绝”针对新的上下文查询。旧解析接口若继续兼容，须在 `docs/16` 写明它仍只解析格式，不能写成已经完成授权。
2. 旧请求字段名是 `scene`，不是方案里的 `intent`。S1 新接口使用 `intent`；旧 `/resolve` 继续接收 `scene`。
3. 现场工序交付是 `ProcessStationService.reportProduction` 和 `POST /api/business/operations/process-stations`。该类注入了 `BusinessOperationService`，但没有调用。`BusinessOperationService.reportProduction` 始终把在制转为半成品，供登记过账，和中间工序留在在制不是同一命令。S5b 接入岗位交付命令。
4. 没有独立返工单仓储。返工号写在质检记录的 `reworkOrderCode`，开返工时为 `FG-` 加原单号。岗位和质检查询扫到 `JG|rework|` 会要求改扫子单。S1 通过质检记录和原单关系解析返工，不能假设存在返工表。
5. 结构化单据读取只有母单和出货单。子单详情在岗位查询和质检查询。`GET /api/business/documents/mother-orders/{code}` 与出货单读取不经过 `BusinessDataAccess`。S1 新上下文必须先按会话和客户范围过滤，再返回详情。收口这两个旧读取接口不在 S1 默认范围内，也不能借用它们返回未授权详情。
6. 出货单不能按运单反查。发货意图下扫运单只填写当前物流字段。收货意图下运单只查母单的来料快递号。没有母单是可以新建来料的结果，不是查询失败。
7. 前端 `scanCode.ts` 对非 `JG|` 且像运单的手输会判成快递单，长度规则可能把 `MD-`、`ZD-` 一类编码判成运单。质检页对非 `JG|` 把原文交给后端。S2 按第 4.1 节要求明确对象类型，或由服务端在授权数据中消歧，不能靠编码长度猜测。
8. 工作台 `OperationContext` 只在唯一余额时填充，多仓库或多状态时为空。这只服务列表投影，不是扫码后的精确目标。
9. 过程记录、证据引用和业务 `requestId` 都不存在。S1 只固化响应中的空过程记录集合，不开放保存动作。

#### S1 可复用的现有查询，不必重写

`BusinessDataAccess` 的读取与客户校验，`ProcessStationService.lookup`，`QualityRequirementService.lookup`，`MobileIntakeService.lookup`，`BusinessDocumentRepository` 的母单、子单、出货、质检和工序交付查询，以及工作台里“子单要求不回退成母单原文”的读取方式。统一查询放在 `scan/app`，写命令仍留在原业务服务。

#### S0 未决项

- 部分数量报工、多段物流状态、离线自动过账和必拍门禁仍按第 1.2 节不做，本复核不新增规则。
- 既有单据 GET 缺少范围校验是历史缺口。本方案保证新上下文查询不泄露；是否收口旧 GET 需另作决定，不并入 S1。
- 真机相机、真实 MySQL 升级和 Docker 镜像不在 S0 验证范围内。

## 3. 整体职责和复用边界

### 3.1 前端

以下为建议命名；已有合适模块可沿用，避免为改名制造大面积差异。

| 模块 | 输入、输出和职责 | 禁止承担 |
|---|---|---|
| ScanInput.vue 与 useScanner.ts | 接收识别模式；相机、照片、扫码枪、手输统一输出原始内容 | 查询订单、决定权限、提交业务 |
| useScanContext.ts 与 scanContextApi.ts | 查询真实上下文；管理 loading、error、识别代次及目标身份 | 写库存、全局共享可变单据草稿 |
| OrderContextCard.vue | 只读展示真实单据、要求、状态和关联对象 | 自动选默认单、提交业务 |
| EvidenceCapture.vue 与证据列表 | 文件选择、拍摄、预览、上传、失败重试、绑定状态 | 完成工序、判定质检、扣库存 |
| IntakePanel、ProductionPanel、QualityPanel、ShippingPanel | 各业务的表单、提交、结果和业务特有校验 | 再实现相机或另一套扫码解析 |
| 手机作业容器及桌面入口 | 组织上述组件和面板，传递精确目标 | 堆入所有场景的状态和条件分支 |

可按 features/scan、features/evidence、features/operations 组织。业务面板必须同时被手机和桌面消费，或者提供同一 composable 和表单片段；不得新建一套手机生产、质检状态账。

继续复用 OperationInputs.vue、operationAmounts.ts、operationDraft.ts 中适用逻辑；不要把已有巨型表单原样再包一层称为完成抽取。面板按一次明确业务操作组织。

useScanner 和 useScanContext 每次调用拥有独立状态；避免跨页面的全局扫描单例和可变草稿。顶层仅可持有可序列化的目标引用，业务提交目标来自当前成功查询的上下文。

### 3.2 后端

- scan/app 新增统一上下文查询，使用各领域应用层查询能力聚合，不在 Controller 拼仓储查询。
- 抽取已有生产、质检服务共用的单据事实和可操作性判断；写命令继续调用所属 business/app 服务。
- 进度记录属于 business 的领域事实；文件与引用生命周期属于 document。保持 domain / app / infra / web 分层。
- 提交权限和状态校验与查询提示复用同一规则来源，提交时重新读取事实；查询结果不构成授权凭据。
- 只增加当前需要的适配器和固定类型动作映射，不引入通用工作流引擎、动态表单引擎或任意接口执行器。

## 4. 统一扫码与上下文契约

### 4.1 输入与识别

- 继续支持 JG|mother|编码、JG|work_order|编码、JG|outbound|编码、JG|rework|编码及既有旧类型。
- 保留快递纯运单和既有运单 URL 提取。任意 URL 不自动跳转或执行；仅提取支持的身份信息。
- 手输业务编码必须带明确对象类型，或由服务端在授权数据中精确解析；出现歧义让用户选择，不靠编码长度猜业务。
- 扫码枪输入、照片识别与手输都进入同一查询链路。输入框使用表单提交或明确结束符，不能每输入一个字符就发请求。
- 扫码默认只查询。场景参数表示当前操作意图，不能替代服务端权限和状态判断。
- 区分“选择业务目标”与“填写某字段”。发货表单的运单字段扫码只解析并填写当前草稿的物流单号，保留已查明的单据、余额和附件；不调用目标切换查询，也不使订单上下文失效。正式发货提交由服务端校验物流及业务目标。相机及解析能力仍共用。

### 4.2 建议新增查询

建议 POST /api/scan/context；原 POST /api/scan/resolve 保持兼容。新路径和 DTO 在 S1 固化并更新 16，后续增量不得各自再定义同义接口。

请求字段：content、可选 objectType、intent（LOOKUP / INTAKE / PRODUCTION / QUALITY / SHIPPING）。

响应分组：

| 分组 | 最少内容与约束 |
|---|---|
| target | 规范对象类型、精确单号、母单号及可选子单/返工/出货单号；稳定目标引用 |
| order | 客户、货品、数量及单位、重量及单位、要求、期限；未知值用空值，不补假数据 |
| requirements | 母单要求、子单实际要求、岗位要求分别保留；明确来源，不用母单覆盖子单快照 |
| progress | 已有工序交付、质检、库存、发货事实及新增过程记录；正式事实与准备动态分别返回 |
| relatedTargets | 授权内的子单、返工及出货对象；需要选择时明确 requiresSelection |
| actions | 固定动作码、是否可执行、中文阻断原因；权限不足和状态不满足分别处理 |
| operationContext | 当前业务允许的正式操作维度、可选余额候选及版本校验信息；不返回客户端可任意执行的接口 URL |

响应遵循现有 ApiResponse 和错误处理。未登录拒绝，未授权不泄露客户、要求或关联单据；不存在与无权读取的提示按项目既有口径处理。新快递没有母单是可建立来料的合法结果，不伪装成已存在订单。

阶段兼容：S1 固化过程记录的扩展字段，但 S4 前该集合为空且不开放保存过程记录动作；不得用样例补齐。S3 仅关联已存在的正式操作或保留历史单据证据；S4 再接入真实过程记录的存在性验证和引用。复检轮次未实施前返回真实受限状态，不宣称已有完整复检。

查询组合复用 process-stations、quality-checks、正式母单/子单/出货查询及 BusinessDataAccess；返工通过真实质检和原单关系解析。避免在统一查询里复制一遍业务规则。

### 4.3 目标定位及防串单

1. 选择业务目标时，扫到 A 后立即使此前上下文失效；改成 B 时清空可提交状态。A 的迟到响应不得覆盖 B。填写运单字段的扫码按 4.1 处理，不切换业务目标。
2. 当前动作提交使用成功查询返回的规范身份，不使用可继续编辑的原始输入、列表第一行或默认余额。
3. 扫母单且已有拆分时展示授权子单，用户明确选择后再生成岗位上下文；不能自动操作第一张子单。
4. 同单多个物料、仓库或余额状态时必须选择完整维度。只传母单号或批次号不能确定扣减目标。
5. 切单时文件和草稿仍属于原目标；需明确保留到原草稿或放弃，不自动转挂新单。
6. 提交进行中固定目标；不允许异步扫码结果改写正在提交的请求或结果归属。
7. 刷新或深链接恢复后重新查询授权和状态，未完成查询前禁用业务提交。

界面即使从进度页或顶部追溯进入，也应传结构化 target 并精确选中。保留列表过滤作为查找功能，不能用它承担正式目标定位。

## 5. 各对象与业务动作

| 扫码对象 | 默认展示 | 可办理动作与限制 |
|---|---|---|
| 母单 | 来料、加工要求、期限、拆分情况、总体进度 | 收货及补证据；已拆则选择子单；明确不拆的母单沿用已有岗位和库存规则 |
| 子单 | 子单要求、工序、数量重量、质检及发货事实 | 本人岗位进度和报工、适用质检、成品发货；前序未交不能跳交 |
| 返工单 | 原单要求、真实缺陷、返工要求、复检情况 | 适用返工记录、报工与复检；不能当普通子单直接跳过返工规则 |
| 出货单 | 本批次货品、来源单、运单、证据、已发货事实 | 查看和授权补证据；已发货不再执行一次扣库存 |
| 快递运单 | 收货关联母单或发货物流输入 | INTAKE 下查是否已有母单；SHIPPING 下填写/核对当前发货物流，不触发来料建单 |

同一标签可供多个岗位使用。客户端动作码只映射预定义面板，服务端按会话、岗位、客户范围、单据状态复核。操作人取服务端会话，客户端姓名不作身份依据。

## 6. 进度记录与正式命令

### 6.1 新增最小过程记录

建议新增 OperationProgressRecord，字段至少包括：code、targetType、targetCode、motherOrderCode、stage、process、可选 clauseNo、note、operatorId/操作人快照、recordedAt、requestId。stage 首期限定生产过程、质检过程、发货准备；场景中文名在展示层映射。

- 每次保存追加一条，不覆盖历史；照片可稍后补关联。
- 不写工序交付、质检结论、工资或库存台账，不接受任意目标库存状态。
- 当前动作权限和业务对象范围都满足时才能记录；已完成业务不伪造新的进行中状态，补充说明应标识为补充记录。
- 首期不增加任意完成百分比或重复累计产量字段；确需分批报工时另设计数量、重量和结算语义。
- 内存默认、JDBC 可切换，MySQL 配置按项目约定接入；过程记录和证据关联都不能只保存在浏览器。

### 6.2 正式业务复用与必要加固

- 生产：继续校验账号绑定工序、实际子单/不拆母单、前序已交和重复交付；中间工序保持在制，末道交付按现有规则转半成品。
- 质检：逐条要求完整判定，不合格和让步有原因；末道未交或库存不符不得提交。首次判定和适用的返工命令继续复用；现有放行仍读取原质检，不具备完整的“不合格→返工→复检合格→放行”闭环，必须按下节补齐。
- 发货：确认本次数量和重量、精确来源余额、真实物流信息；以正式发货命令产生出货单及已发货事实。
- 动作成功后保留服务器返回的单号、台账号、操作编号；详情刷新失败只重试查询，不能重发业务命令。

### 6.3 最小复检事实与闭环

S5c 补齐独立的质检轮次及复检提交，不能仅去掉“已提交”校验或改写原不合格结果。轮次至少含稳定轮次编号、原质检案件、轮次序号、初检/复检类型、关联返工单与真实返工报工事实、逐条判定、结果、操作人及时间。

- 原不合格条款、原因、冻结和返工历史保留；旧初检作为历史首轮兼容读取，不随意回填虚构复检。
- 只有真实返工已报工、库存回到适用半成品且具备复检权限时，才允许发起下一轮复检。一次有效轮次不能被重复提交覆盖。
- 复检不合格继续产生真实冻结事实；复检合格或让步产生可供放行校验的真实结论。
- 放行以最新有效的适用轮次、真实库存状态、未处理的冻结事实及原单关联共同校验。不能直接把原质检 frozen 改为 false 宣称解决闭环。
- 过程拍摄可绑定轮次和条款；没有轮次的早期过程记录保留原编号，不冒充正式结论。
- 首次质检及复检的结果接口区分案件编号和轮次编号，保持旧调用兼容；范围和字段落地时更新 02、16。

### 6.4 幂等与一致性不能靠 UI 补丁

本轮接入的正式写操作应逐项核查，并在对应增量补齐：

- 同一次用户确认生成稳定 requestId；超时、断网和点击重试复用该 ID。改变目标或载荷必须开启新请求。
- 服务端记录请求身份、动作、目标、规范化载荷摘要及成功结果。同键同载荷回放原结果；同键异载荷拒绝，键不可跨无权用户重放。
- 已有“工序已交/出库号已存在”的错误只防重复，不能代替结果回放。
- 不能用 JVM synchronized、前端按钮禁用或执行前查重宣称多实例安全。
- JDBC 现有仓储可能自己创建连接和提交；先核实事务边界，再建立有限的业务工作单元。仅给外层服务加 @Transactional 不证明库存、业务单据和请求记录同事务。
- 必须在同一提交边界协调库存流水、正式业务事实及成功结果；质检自动冻结也包含在核查范围。内存实现提供对应原子语义，JDBC 用数据库约束和事务保证。
- 注入单据保存失败、请求结果保存失败与并发重复请求，验证不出现“库存已扣但无出货单”或重试再次扣减。

适用的已有幂等模式可借鉴，但不能复制收付款代码后新建另一套库存。若当前架构无法在本增量内保证，明确列为未完成，不把超时提示改成“再点一次”规避。

S5p 先完成有限的请求回放与业务工作单元契约及内存/JDBC实现，不建立通用工作流引擎。S5a–S5d 各自将实际命令接入并验证，不能把公共基础的测试当成具体命令已经安全。

| 责任增量 | 必须核查并纳入同一次提交的实际事实 |
|---|---|
| S5a | 母单及来料事实、适用入库流水和请求成功结果；运单唯一识别与重复建单竞态 |
| S5b | 不拆母单首次转在制、工序库存流水、交付事实及请求成功结果 |
| S5c | 初检/复检条款与轮次、适用冻结流水；开返工关联及库存；返工报工；放行流水；各命令的成功结果分别与自身业务事实原子提交 |
| S5d | 发货库存流水、正式出货单和请求成功结果；同出货号或同请求的重试及并发 |

## 7. 统一拍摄与证据关联

### 7.1 采集与文件生命周期

- 扫码与留证共享相机基础能力，但业务用途分开。照片识别结果不默认等于已留证；需要留存时必须明确上传绑定。
- 用户主动点拍照或录像再启动设备；扫码成功、取消、切页及组件卸载停止媒体流。扫描与拍摄同时请求相机时由组件协调，避免设备被占用。
- 保留系统拍摄和选择文件回退，区分拒绝授权、设备不可用、HTTP、识别失败、格式不支持及上传失败。
- 沿用实际服务端限制：JPEG/PNG 图片 8MB，MP4/WebM 视频 50MB；30 秒是提示，不宣称已有服务端时长检测。iPhone、Android 实际输出格式必须真机核验；不支持时给出可操作提示，不能只改扩展名。
- 文件状态至少区分本地待上传、上传中、失败、已上传待关联、已关联。成功与失败按文件反馈，重试只处理失败部分。
- URL.createObjectURL 预览及时释放；取消选文件不清掉原草稿；同文件重选可响应；退出后不承诺内存文件恢复。

### 7.2 业务证据引用

建议增加 BusinessEvidenceLink，复用现有附件实体、存储、checksum、预览签名与审计。引用至少含：linkCode、attachmentCode、targetType、targetCode、stage、scene、operationType、operationCode、可选 process/clauseNo、操作人及时间。

stage 表示业务阶段，首期固定为 INTAKE、PRODUCTION、QUALITY、SHIPPING、REWORK；scene 表示证据内容，两者不得混用。保留 UNPACK、WEIGH、DEFECT、FINISH，并按实际入口新增 PROCESS（加工过程）、CHECK（检查过程）、PACK（打包）、WAYBILL（面单）。S3 固化场景枚举和兼容映射，接口与引用保存稳定代码，中文在展示层映射；同一文件不同引用可以有不同 scene，不能沿用首次附件场景覆盖所有引用。

操作编号使用真实服务端事实：过程记录 code；生产结果的真实台账/交付身份；质检案件及适用复检台账；出货单号及台账。不要依赖可能为空的客户端 handoffCode，更不能由前端任意生成一个编号当正式记录。

- 文件去重与引用去重分开。重传相同文件不重复落盘，但同文件用于不同场景或操作时保留新引用。
- 引用唯一键包含 targetType、targetCode、stage、scene、operationType、operationCode、process、clauseNo、attachmentCode；同场景同工序同条款的重复绑定只保留一份，跨场景/工序保留新引用。可空字段须规范化，不能依赖 MySQL 对 NULL 的唯一性行为。
- SQL 字段长度按真实编码限制，物理唯一索引须符合 MySQL 索引长度限制；选择规范化业务键摘要时仍需核对原始维度，避免以任意超长字符串拼接代替模型。
- 绑定时同时校验目标和附件的真实归属、当前用户权限、附件有效状态及对应操作存在。只知道 attachmentCode 不能跨客户或跨单盗绑。
- 首期只允许同一真实单据的证据绑定；需要跨母子单复用时另建服务端明确映射和授权，不依靠客户端宣称同客户。
- S3 必须为附件来源补充持久化的 objectType 或可靠的服务端来源映射。现有附件只有 businessCode，不能仅比较编码字符串就认定同一单据。无法确定旧附件来源时保留历史只读展示，拒绝不确定的新绑定。
- 新增查询按具体操作和阶段展示，也能按订单查看全链路；旧附件无引用时保留为“历史单据证据”，不伪造某次工序关联。
- 沿用老上传接口和单 evidenceCode 字段的兼容性，新增多附件引用采用明确 DTO/接口；不要用逗号拼接编号。
- 下线附件不再预览或新增绑定；历史业务引用保留审计，不能静默消失。

### 7.3 保存顺序与部分成功

| 场景 | 首期处理 |
|---|---|
| 新来料尚无母单 | 文件先留当前表单；建单成功取得母单号后上传和绑定；超时先按运单核对已有母单，不盲目再建 |
| 已有订单的过程记录 | 保存过程记录后上传并绑定；失败保留记录编号和待补文件 |
| 正式报工/质检 | 单据存在时可先上传；正式提交成功取得操作编号后绑定；业务失败的上传件仍标记待关联，不冒充报工成功 |
| 发货尚无正式出货单 | 文件暂存于当前发货草稿；确认发货成功后按真实出货单上传绑定；超时通过幂等结果恢复，禁止再次扣库 |
| 业务成功、上传或绑定失败 | 明确显示“业务已保存，证据待补”；仅重试上传/绑定 |
| 业务成功、详情刷新失败 | 留下原结果并提供刷新；不重新执行业务 |

文件落盘和数据库不是同一事务；处理落盘后元数据失败的清理或可恢复状态，不以数据库事务宣称文件已回滚。必拍前置、服务端大文件暂存及后台离线队列属于后续扩展。
