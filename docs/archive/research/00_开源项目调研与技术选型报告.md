# 来料加工进销存与生产管理系统 开源项目调研与技术选型报告

> 归档说明：本文保留当时的设计、验证或客户沟通记录，不再作为当前开发入口；现行依据见[文档索引](../../README.md)。

**文档版本**：V1.0  
**适用阶段**：立项评审、技术路线评审、M0 POC  
**最终策略**：生产主路线选择 Java/Vue 定制业务系统，后台基座选择 RuoYi-Vue 体系；ERPNext/Frappe、Odoo 作为业务模型参考，不作为一期生产主基座。继续复用成熟开源能力，避免重复建设通用权限、报表、条码、视频处理能力。

---

## 1. 调研目标

本项目不是普通进销存，也不是完整财务 ERP。核心业务是客户来料加工场景下的：

- 客户所有物料的批次追溯。
- 母单、子工单、工序、质检、返工、损耗、出库的全链路闭环。
- 贵重物料按数量和重量双维度管理。
- 工序交接称重、损耗归因和视频证据留存。
- 计件工资试算，不在一期做正式薪资发放。

调研目标不是简单选择“最强 ERP”，而是判断哪些能力应复用，哪些行业核心能力必须定制。

---

## 2. 评估维度

| 维度 | 评估问题 |
|---|---|
| 库存与批次 | 是否支持批次、序列号、库存流水、库存状态、冻结库存、调拨和追溯 |
| 生产与工序 | 是否支持工单、工艺路线、工序、报工、在制品流转 |
| 质检与返工 | 是否支持质检记录、不合格处理、返工、报废、复检 |
| 客户来料所有权 | 是否能明确区分客户所有物料与企业自有物料 |
| 贵重物料损耗 | 是否能按工序投入重量计算损耗并保留责任证据 |
| 条码与移动作业 | 是否支持二维码、扫码作业、PWA 或移动端 |
| 视频证据 | 是否能挂接拆包、打包、异常处理视频 |
| 权限与审计 | 是否支持角色权限、数据范围、操作日志 |
| 报表与导出 | 是否支持台账、产量、损耗、工资试算导出 |
| 二开成本 | 数据模型、UI、工作流、部署维护是否可控 |
| 国内交付生态 | 是否容易找到开发、运维、培训和二开资源 |
| 许可证风险 | 是否允许商用部署，是否存在企业版功能边界 |

## 3. 候选项目调研

### 3.1 ERPNext / Frappe

参考：

- [ERPNext Manufacturing](https://docs.frappe.io/erpnext/user/manual/en/manufacturing)
- [ERPNext Work Order](https://docs.frappe.io/erpnext/user/manual/en/work-order)
- [Frappe Framework](https://frappeframework.com/)

ERPNext 覆盖制造、库存、采购销售、质量、报表和权限，Frappe 的 DocType 模型适合快速扩展业务单据。它适合拿来验证：

- Work Order 是否能表达子工单和工序流转。
- Batch / Serial No 是否能表达母单批次和成品追溯。
- Stock Entry / Stock Ledger 是否能表达待加工、在制、成品、冻结、发货等库存变化。
- Quality Inspection 是否能承载质检、返工、报废的入口。
- Custom DocType 是否能增加称重交接、视频证据、损耗审批和工资试算。

优势：

- 制造和库存基础完整，较接近本项目底层模型。
- DocType、权限、表单、列表、报表能力成熟。
- 可减少后台、权限、报表和通用单据建设成本。

风险：

- 客户来料所有权不是标准 ERP 常规模型，需要定制字段和规则。
- 贵重物料按工序称重、损耗归因、视频证据不是原生核心能力。
- 如果核心库存逻辑需要绕开 ERPNext 原生 Stock Ledger，则复用价值下降。

结论：

ERPNext / Frappe 应作为 M0 POC 第一优先级。若能自然跑通 60% 以上核心业务闭环，可作为首选基座。

### 3.2 Odoo Community

参考：

- [Odoo Manufacturing](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/manufacturing.html)
- [Odoo Inventory](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/inventory.html)
- [Odoo GitHub](https://github.com/odoo/odoo)

Odoo 的制造、库存、销售、采购和应用生态成熟，适合做制造和库存管理对照验证。

优势：

- ERP 生态成熟，模块覆盖面广。
- 制造订单、库存、批次、条码、质量等方向都有成熟方案或生态模块。
- UI 和业务对象成熟度高。

风险：

- 社区版、企业版、第三方模块之间的功能边界需要逐项核实。
- 深度二开需要熟悉 Odoo ORM、模块机制和版本升级策略。
- 如果条码、质检、报表或自动化能力依赖企业版，交付成本和授权成本会变化。

结论：

Odoo 不作为第一验证对象，但可作为 ERPNext POC 失败后的第二轮候选。

### 3.3 Tryton

参考：

- [Tryton](https://tryton.org/)
- [Tryton Stock Modules](https://docs.tryton.org/latest/modules-stock/index.html)

Tryton 是模块化 ERP 框架，库存、批次、生产等模块设计较清晰。

优势：

- 领域模型干净，适合作为库存和批次设计参考。
- 模块化程度高，适合严谨业务建模。

风险：

- 国内交付生态弱。
- UI、移动作业、硬件集成和二开资源不如 Java/Vue 或 Odoo/ERPNext 常见。

结论：

作为模型参考，不建议作为一期主基座。

### 3.4 InvenTree

参考：

- [InvenTree Documentation](https://docs.inventree.org/en/latest/)

InvenTree 偏库存、BOM、Build Order、条码和零件管理，适合参考库存追溯和扫码体验。

优势：

- Stock Item、Build Order、Barcode 等能力对库存追溯有借鉴价值。
- 系统较轻，适合研究扫码和库存 UI。

风险：

- 不是完整 ERP/MES，客户来料、工序损耗、工资试算、视频证据需要大量扩展。

结论：

不作为主系统，作为库存与条码设计参考。

### 3.5 Dolibarr

参考：

- [Dolibarr GitHub](https://github.com/Dolibarr/dolibarr)
- [Dolibarr](https://www.dolibarr.org/)

Dolibarr 是轻量 ERP/CRM，部署简单，模块较多。

优势：

- 适合小企业的客户、产品、订单、库存等基础管理。
- 部署和学习成本相对低。

风险：

- 制造、工序、质检、损耗责任和车间追溯深度不足。

结论：

不建议作为本项目主基座。

### 3.6 Apache OFBiz

参考：

- [Apache OFBiz](https://ofbiz.apache.org/)

Apache OFBiz 是企业业务自动化框架，覆盖 ERP、CRM、电商、订单等能力。

优势：

- Apache 生态，许可证友好。
- 企业业务组件较多。

风险：

- 技术栈和 UI 体验偏老。
- 二开成本和团队适配成本高。

结论：

不建议作为一期主基座，仅作为企业业务组件拆分参考。

### 3.7 RuoYi-Vue

参考：

- [RuoYi-Vue GitHub](https://github.com/yangzongzhuan/RuoYi-Vue)

RuoYi-Vue 是 Java/Spring Boot + Vue 后台管理框架，常用于权限、菜单、字典、代码生成、日志和后台管理系统。

优势：

- 国内开发者熟悉，招聘和维护成本低。
- 权限、菜单、字典、日志、代码生成等通用后台能力可复用。
- 适合按本项目业务模型定制库存、工单、质检、追溯。

风险：

- ERP/MES 业务模块需要自研。
- 如果团队业务建模能力不足，容易写成“表单堆砌系统”。

结论：

作为自研路线第一候选框架。

### 3.8 JeecgBoot

参考：

- [JeecgBoot GitHub](https://github.com/jeecgboot/JeecgBoot)

JeecgBoot 是 Java 低代码开发平台，包含代码生成、表单、权限、报表等能力。

优势：

- 低代码和在线表单能力强。
- 适合快速生成基础档案、单据列表、权限和报表。

风险：

- 平台复杂度高于 RuoYi。
- 核心业务仍需定制，不能把复杂业务完全交给低代码表单。

结论：

作为自研路线第二候选。若团队熟悉 JeecgBoot，可进入 POC。

## 4. 组件级复用清单

| 能力 | 推荐复用 | 一期建议 |
|---|---|---|
| 二维码生成 | node-qrcode、后端二维码库 | 复用，不自研 |
| 二维码识别 | ZXing、浏览器 BarcodeDetector 兜底 | PWA 优先使用浏览器能力，失败用 ZXing |
| 视频截取 | FFmpeg、NVR SDK、ONVIF 能力 | 一期半自动截取，失败人工上传 |
| 对象存储 | MinIO / S3 兼容存储 | 视频、图片、附件统一对象存储 |
| 报表图表 | ECharts | 管理端统计图 |
| Excel 导入导出 | SheetJS / EasyExcel | 数据导入导出复用 |
| 审批流 | 简单审批表；Flowable 二期预留 | 一期不引入完整流程引擎 |
| 打印 | 浏览器打印、LODOP、打印机 SDK | 一期先标签模板 + 浏览器/驱动打印 |
| 权限 | ERPNext/Frappe 权限或 RuoYi/JeecgBoot 权限 | 不自研权限体系 |
| 日志审计 | 框架内置日志 + 业务操作日志 | 敏感操作必须留痕 |

## 5. 技术路线建议

### 5.1 已选主路线

主路线已确定为 Java/Vue + RuoYi-Vue 定制业务系统。M0 阶段不再用来决定是否采用 ERP 基座，而是验证最终路线下的关键风险：

1. RuoYi-Vue 基座能否满足权限、菜单、字典、日志、代码生成。
2. 转移式库存台账和库存余额能否跑通。
3. PWA 手机扫码能否满足现场报工和质检。
4. NVR/FFmpeg 能否按时间段截取视频。
5. 标签打印能否满足母单、子工单和出库标签。
6. 备份和恢复演练能否满足试点要求。

样例链路：

1. 创建客户订单。
2. 收到一批客户来料，生成母单和客户所有库存。
3. 拆成 2 个子工单。
4. 每个子工单走 2 道工序。
5. 第一道工序完成报工并记录称重交接。
6. 第二道工序发生质检不合格，生成返工。
7. 返工完成后复检通过。
8. 记录一次超标损耗。
9. 部分成品入库并创建出库单。
10. 打包发货并关联视频证据。
11. 通过母单、子工单、快递单号查询完整追溯。
12. 导出员工产量、损耗、库存台账和工资试算。

### 5.2 ERP 参考标准

ERPNext/Frappe 和 Odoo 不再作为主路线候选，但可按以下维度提取参考经验：

| 判断项 | 参考内容 |
|---|---|
| 库存台账 | Stock Ledger / Stock Entry 的台账组织方式 |
| 工单工序 | Work Order / Job Card / Operation 的页面和流程组织 |
| 质检返工 | Quality Inspection 和不合格处理思路 |
| 批次追溯 | Batch / Serial No 的追溯设计 |
| 权限审计 | ERP 单据权限、状态和日志管理经验 |

### 5.3 推荐默认路径

按 Java/Vue + RuoYi-Vue 进入 M0 风险验证；验证通过后进入数据库 DDL、API 字段字典和一期开发。ERPNext/Frappe、Odoo 只作为参考资料和流程对照，不进入生产主基座实施。

## 6. 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 直接自研范围过大 | 周期失控 | 先 POC，复用权限、报表、条码、对象存储 |
| ERP 模型不贴合客户来料 | 二开变形 | 用真实样例验证库存和工单，不只看页面演示 |
| 一期硬件集成卡住 | 业务无法上线 | 视频半自动 + 人工上传兜底，电子秤二期强集成 |
| 低代码变成表单堆砌 | 业务规则散乱 | 核心库存、工单、损耗必须领域建模 |
| 开源许可证和版本边界不清 | 商用和升级风险 | POC 阶段输出许可证清单和企业版功能边界 |

---

## 7. 最终选型结论

本项目可以复用开源，但不适合直接套用普通进销存或完整 ERP。最终路线是：

1. 生产主基座选择 Java/Vue 定制路线，优先使用 RuoYi-Vue 体系复用权限、菜单、字典、日志和代码生成。
2. JeecgBoot 作为备选，仅在团队已有成熟 JeecgBoot 经验时进入替代评估。
3. ERPNext/Frappe、Odoo 保留为制造、库存、工单、质检模型参考，不进入一期生产主基座。
4. 条码、视频处理、报表、Excel、权限等通用能力尽量复用。
5. 文件和视频存储一期优先使用 NAS；需要对象存储时选择 S3 兼容商业/云服务或经许可证评估后的方案。
6. 客户来料所有权、称重交接、工序损耗、返工、视频证据、工资试算是核心行业能力，必须按本项目领域模型定制实现。
