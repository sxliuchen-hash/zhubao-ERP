# UI-04：财务读取授权与客户范围

> 已完成任务的历史施工说明，不再作为待执行入口。当前规范见 [固定基调](../../ui-prompts/00_固定基调.md)，完成状态与提交见 [任务入口](../../27_UI开发执行提示词.md)。

前置：UI-03 已完成。共同基调的财务边界必须遵守。本段先做后端，不制作仪表盘。

## 起点与范围

先读：

- `backend/src/main/java/com/zhubao/erp/finance/web/FinanceController.java`
- `backend/src/main/java/com/zhubao/erp/security/web/PermissionGuardInterceptor.java`
- `backend/src/main/java/com/zhubao/erp/security/domain/OperatorContext.java`
- `PermissionGuard`、`PermissionCode`、`OperatorContextResolver`、`CustomerAuthorizationService` 及现有权限／范围测试
- `BusinessWorkspaceService` 中已经实现的客户范围规则

当前财务 GET 的 customerId 仅是过滤参数，不能当作授权。开始先列出财务 GET 清单、现有角色与数据范围语义，再按 AGENTS.md 调研影响面。

## 实施

1. 为财务读取建立显式服务端权限，沿用项目命名与角色映射方式。订单可见不能自动获得收入、工资和公司成本权限。
2. 统一解析可信操作人上下文，拒绝未登录和无权限请求；不扩大请求头身份兜底的生产边界。
3. 明确公司全量、授权客户集合、单个授权客户三种查询范围；复用现有账号客户范围语义，不把空范围默认为公司全量，也不把合法 ALL 语义改错。
4. 限定客户的账号不能通过空 customerId、换参数、排行、应付列表或其他财务 GET 绕过范围。工资明细、公司固定资产及无法按客户归集的费用需要额外可解释的读取边界。
5. 后续聚合和下钻共用同一范围解析逻辑。保留既有服务调用测试兼容；新增依赖按项目构造器范式处理。
6. 不顺便重写全部财务写命令或身份系统；与读侧缺陷直接相关的调整须说明影响。

## 完成条件

必须有未登录、操作工、正常财务用户、单客户、授权客户集合、越权 customerId、空参数尝试、公司成本／工资访问的测试。错误状态和包络沿用现有 API 规范。现有合法财务操作与其他模块权限不回退。

在 `docs/16_字段字典与API契约.md` 记录实际读权限和范围规则。没有解决读取授权不能启动 UI-05。下一段 UI-05。
