## 2. 对首轮结论的勘误

1. **账号强制审批开关的解释过宽。** `validatePreApprovalApplication()` 第 1173—1175 行在申请号为空时直接返回 null；只有传入申请时，才在 `enforcePreApprovalForAccountActions` 为真时核对绑定审批任务。因此不能将 MySQL 配置 true 描述成现行所有账号操作必须先审批。用户选择与当前管理员直接保存链一致，后续裁剪专属兼容分支。
2. **v1 代理端点已经停用。** `PrintJobController` 的旧创建／重试／领取／回报都直接返回中文停用异常，不调用对应算法。可退出的残留重点是 `PrintJobService.claim/report/assertStation`、共享旧令牌、旧仓储领取能力和测试装配；v2、快照及历史任务不是同一删除边界。
3. **结单组件名称以实际文件为准。** 现行组件为 `features/finance/SettlementPanel.vue`，由 `OrderActionHost` 异步装配，首轮表格写成 `OrderSettlementPanel` 不准确，已更正。
4. **没有另一个现成的新发货行表。** 收货新行是 `biz_receipt_line`；发货每次记录的当前实体是 `OutboundOrderRecord`／`biz_outbound_order`，内含材质、单位、数量、重量、物流和 `ledger_code`。退役旧 item 双写不要求为瘦身再建一套发货模型。

## 3. 收发货与财务接续依据

- `BusinessOperationService.postInbound` 在正式会话、主数据已装配且非多行标记时，保存单材质 `ReceiptLine`；多材质收货由 `MobileIntakeService` 逐行保存并更新汇总，备料建单由 `MaterialStockService` 保存来源行。迁移旧无请求写入后，这些正式链都必须实际落新行，不能依赖母单汇总合成明细来冒充原始数据。
- `JdbcBusinessDocumentRepository.writeMotherOrder` 调用 `insertMotherOrderItem`，`writeOutbound` 调用 `insertOutboundOrderItem`。停止这两处写入不会移除母单／发货主记录；但 `motherHasDownstream` 仍把旧发货 item 表加入 `FOR UPDATE` 检查清单，须改为新结构且保留锁后当前读。
- `OrderDeliveryCompletionQuery` 读取母单范围内发货记录与台账，检查有效状态、来源、单位、数量及台账关联。其职责不写库存和财务，应该保留，不能改成“看到出货单即可结单”。
- `OrderSettlementService` 在工作单元内确认应收、逐单工资和员工应付；`FinanceReportService`、`FinanceDashboardService` 区分 `PayrollLine.POST_DELIVERY` 与历史月确认。取消旧工资生成器不等于删除这些历史读取和报表过滤。
- `FinanceBillingService.unpriced()` 的空壳仍被外部只读端点和经营缺项判断调用；“已交齐但未结单”要从现行交货评估及结单状态得到，来源不明仍待核。不能恢复按旧协议计价，也不能继续把空结果当作业务完整。
- 仓内 `a3-readonly-audit.sql`、`a6-readonly-audit.sql` 有旧表读取；测试里也有旧表建表和记录数断言。应保留新行／库存／交货／原请求场景，只移除双写实现专属断言。
