# UI-06：当前余额、客户排行与明细下钻

**归档说明（2026-10-13）**：本文保留历史执行提示，不作为当前开发指令或验收证明；现行唯一入口见 [项目核心](../../../00_项目核心.md)。
前置：UI-05 已完成。只做后端数据补齐及契约，不编写仪表盘页面。

## 数据边界

- `currentBalances` 固定为当前状态：返回实际 `asOf`、`outstandingAmount`、`unpaidAmount` 及支持状态。选择月份不把余额改成该月账单的小计。
- 未收款基于全部相关账单、冲销和核销的当前余额；应付基于当前全部适用未付。不能分别对分页结果求和。
- `receivableRanking` 为同范围当前客户未收款排行；后端排序，明确返回总数、返回条数和是否截断。所有客户均无余额时空数组可用，但未提供或无权访问时用不可用状态。
- 不实现历史 asOf 参数回放。月末回放、账龄和到期日均不在本段范围。

## 实施

1. 基于现有账单核销和应付付款规则计算，不另造一套余额公式。红字、部分核销、跨月核销、未分配收款、重复来源及部分付款必须正确。
2. 复用 UI-04 范围解析；公司范围的共用应付不能泄露给仅有某客户权限的用户。无法归集的公司工资、采购或外协不强塞给客户，返回明确限制。
3. 新增只读 `GET /api/finance/dashboard/details`，明细种类为收入、成本、未收、应付；参数与分页方式写入 docs/16。收入／成本继承月份与范围，余额明细使用当前时点与范围。
4. 每类指标可追到实际来源单、账单、费用或应付。无需在本段重做完整账务编辑 UI，不能给一个无数据的跳转地址当下钻完成。
5. 当前数据发生变化后，明细返回实际时点，前端后续可同步刷新指标；不谎称新的明细仍代表旧查询时点。
6. 所有汇总、排行和明细都只读；不允许前端逐客户请求凑总额。保持 UI-05 一级契约兼容，能力标记准确。

## 完成条件

手工可核对的样例覆盖两客户、红字、跨月部分核销、预收未分配、部分应付付款。验证筛选范围、排行排序、分页全量总额、读取无副作用与越权明细访问；同一稳定样例下指标与明细对得上。内存／JDBC 一致。
