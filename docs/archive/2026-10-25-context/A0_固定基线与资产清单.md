## 2. MySQL 结构、版本和容量

- 工作树 V1—V63 共 63 个连续迁移文件，CREATE TABLE 定义 **102 张不同的表**；[JdbcMigrationStore](../../../backend/src/main/java/com/zhubao/erp/ops/infra/JdbcMigrationStore.java)另建 schema_migration。对照测试库 information_schema，实有 **103 张 BASE TABLE**，名称与这 102+1 完全一致，无额外表和缺表。
- schema_migration 精确计数 **63 行**，V1—V63 全为 SUCCESS，无 APPLYING／FAILED。逐版本比较表内 script_name、原文 SHA-256 与本地工作树文件，**63 项一致**。这证明当前文件字节与测试库登记一致，不证明本地未提交代码就是运行镜像源码。
- 对每张表运行 SELECT COUNT(*) 得到下表精确行数；合计 527 行（含 schema_migration 63 行）。information_schema 的 DATA_LENGTH+INDEX_LENGTH 合计 **4,718,592 字节（4.50 MiB）**，是 InnoDB 页分配量，不能视为 SQL 导出大小或实际业务负载。逐表容量也用此口径。
- 测试库两张历史明细：biz_mother_order_item **3 行**，biz_outbound_order_item **0 行**；新 biz_receipt_line、biz_child_line_allocation 均 **0 行**。因此测试库尚不能证明新旧明细和拆单库存对账正确。13 张 cfg_* 均 **0 行**；12 张 biz_workspace_* 共 **59 行**，是迁移演示快照。零行只说明这一个测试库，没有删除依据。

复核可在有权访问测试库的服务器执行以下**只读**命令；不在命令行展开数据库密码。逐表精确计数采用先生成 SELECT 再逐条执行的方式，下表为本轮结果。

    sudo docker exec -i zhubao-erp-mysql sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" mysql -u"$MYSQL_USER" -D "$MYSQL_DATABASE" -N' <<'SQL'
    SELECT COUNT(*) FROM information_schema.tables WHERE table_schema=DATABASE() AND table_type='BASE TABLE';
    SELECT version,status,checksum FROM schema_migration ORDER BY version;
    SELECT table_name,data_length+index_length FROM information_schema.tables WHERE table_schema=DATABASE() AND table_type='BASE TABLE' ORDER BY table_name;
    SQL

逐表精确计数可用下面的双层只读查询复现，第二个 mysql 进程只执行第一步生成的 SELECT；不要把它替换成 information_schema.table_rows 的估计值。

    sudo docker exec -i zhubao-erp-mysql sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" mysql -u"$MYSQL_USER" -D "$MYSQL_DATABASE" -N' <<'GEN' |
    sudo docker exec -i zhubao-erp-mysql sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" mysql -u"$MYSQL_USER" -D "$MYSQL_DATABASE" -N'
    SELECT CONCAT('SELECT ',QUOTE(table_name),',COUNT(*) FROM ',table_name,';')
      FROM information_schema.tables
     WHERE table_schema=DATABASE() AND table_type='BASE TABLE'
     ORDER BY table_name;
    GEN

现行[数据库备份脚本](../../../deploy/backup-mysql.ps1)只执行 mysqldump 并导出 SQL 与 .sha256；它**不包含 evidence-data**。附件包来自测试环境发布流程的单独操作，运行包尚无统一的数据库＋附件同批次清单。同名前缀的这对历史备份在**文件路径与内容校验和**层面已核对一致，不等于 SQL 可成功导入、业务引用可恢复。COS 只在显式 UploadCos/--upload-cos 下上传 SQL 与校验文件；没有证据表明附件包被自动异地上传。[部署手册第 7 节](../../19_Docker一键部署与离线交付.md)也将附件备份列为单独责任。数据库和附件在本轮均可读取，但**当前 103 表＋6 文件的成套恢复点、异地覆盖和隔离恢复未实测**。

对测试主机补充只读核验：ubuntu 用户无 crontab；root crontab 未见项目备份／打印命令；/etc/cron* 与 /etc/systemd/system 未检出项目名、backup-mysql、evidence-data 或 coscmd；运行中的 systemd 定时器仅有与此关键词命中的系统 dpkg-db-backup，现行进程未见打印代理。后端运行环境的 ZHUBAO_COS_BACKUP_ENABLED=false，主机无 coscmd 命令。故**这台测试主机当前未见自动项目备份或打印代理**；这不能证明厂内电脑没有定时任务或打印程序，也不能证明 COS Bucket 内无人工上传的历史对象。

[LocalAttachmentObjectStorage](../../../backend/src/main/java/com/zhubao/erp/document/infra/LocalAttachmentObjectStorage.java)的 putStream 直接写最终路径，完成后返回 SHA-256；[DocumentCaptureService](../../../backend/src/main/java/com/zhubao/erp/document/app/DocumentCaptureService.java)先落文件再保存元数据，元数据异常时尝试删文件；审计失败会在附件已保存时返回错误。[DocumentManagementService](../../../backend/src/main/java/com/zhubao/erp/document/app/DocumentManagementService.java)的通用上传把 byte[] 写文件，再分别保存元数据与审计；下线顺序是**删除文件 → 元数据改为已下线 → 审计**。这是代码可证实的中断风险，不表示测试库现有 6 个文件已有损坏。

**已证实**的是当前代码路径、测试库 103 表／行数／容量、迁移登记、6 个文件与元数据校验、SQL 与附件包文件存在及其 SHA-256。**推测／未实测**的是客户生产库行数、外部消费者是否存在、页面请求量及响应时间、并发上传窗口、当前 103 表的同批次隔离恢复、COS 覆盖和现场打印机。A0 只读约束下没有执行需写临时库或生成备份的“完成标准”；正式 A1 前必须补成套快照和隔离恢复验收。

页面性能基线建议以同一角色、同一数据集逐页记录浏览器网络面板的请求数、P50／P95、最大响应体与后端查询耗时；Nginx 当前配置没有 request_time 字段，现有日志不能可靠还原页面响应时间。本轮没有使用真实账号打开 16 页，故这些指标**未实测**，不能据此判定分页或索引必要性。
