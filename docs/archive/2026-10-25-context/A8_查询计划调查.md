## 3. 计划结果

`type=ALL` 表示全表扫描。`type=index` 表示按索引顺序读完该索引的全部条目；无 `WHERE` 的列表按主键排序时就是这样读完这张表。`EXPLAIN ANALYZE` 的实际时间是这条 `SELECT` 在测试库上的执行时间，单位为毫秒。

### 3.1 工作台与进度

首页三次请求和进度在制列表共用下面几条整表或可见行读取。生产视图再加拆分和流水，质检视图再加审批。

| 语句 | 访问 | 实际耗时 | 检查行数 |
|---|---|---:|---:|
| 可见母单：`recycled_at is null`，按 `created_at desc` | 全表扫描，文件排序。`recycled_at`、`created_at` 都没有索引 | 0.52 | 3 |
| 可见子单：`recycled_at is null`，并排除已回收母单，按 `code` | 子单全表扫描；每行用 `uk_mother_order_code` 反连接母单 | 1.03 | 2 |
| 按母单查可见子单 | `idx_work_order_mother` 等值查找，再过滤回收标记 | 0.009 | 索引定位 |
| 按单号查母单、按单号查子单 | `uk_mother_order_code`、`uk_work_order_code` 常量查找 | 0.67 以内 | 1 |
| 全部拆分；按母单查拆分 | 主键扫描 3 行；单行主键常量查找 | 0.011 / 0.0002 | 3 / 1 |
| 全部交工；按单号查交工 | 主键扫描 0 行；`uk_process_station_order_process` 等值查找 | 0.006 | 0 |
| 全部质检核对，按 `order_code` 排序 | 全表扫描加文件排序。`order_code` 已有唯一索引，这条语句没有过滤条件，优化器在空表上没有用它来避免读表 | 0.009 | 0 |
| 在制百分比全表；按单号和工序点查 | 主键 `(order_code, process_name)` 扫描或常量查找 | 0.006 以内 | 0 |
| 进度历史：`order_code` 与 `process_name` 过滤，按 `id` | 主键扫描后过滤。事件表只有主键 `id`，过滤列没有索引 | 0.006 | 0 |
| 审批全表，按 `id` | 主键扫描 | 0.016 | 2 |

进度百分比列表在读完母单和子单后，对每张母单再查一次子单和拆分状态，对每张可见单据再点查交工和百分比。以当前 3 张母单、2 张子单、0 条交工和 0 条百分比计算，这些点查与单据数同量级，单次都在 1 毫秒内。客户范围不是全公司时，权限判断还会按单号做母单或子单主键查找；查到单据后即返回，不会为了普通子单号再扫质检表或整本流水。

### 3.2 库存追溯

| 语句 | 访问 | 实际耗时 | 检查行数 |
|---|---|---:|---:|
| 全部余额，按维度列排序 | 全表扫描加文件排序。唯一键列顺序与这条 `ORDER BY` 不一致，5 行用不上该索引 | 0.031 | 5 |
| 全公司流水：无 `WHERE`，按 `biz_time, id` | 全表扫描加文件排序。现有 `idx_stock_ledger_mother_time` 以母单号开头，不能服务这条无母单条件的排序 | 0.032 | 5 |
| 客户范围流水：`customer_id in (?) or mother_order_code in (?)`，同样按时间排序 | 优化器看到母单索引，但没有选用。`customer_id` 没有索引，`OR` 使语句退回全表扫描。5 行里返回 1 行 | 0.022 | 5 |

`4447d79` 的流水查询在选择列中包含 `source_ledger_code`。测试库没有这一列，对它执行 `EXPLAIN` 得到 `ERROR 1054 Unknown column 'source_ledger_code'`。上表的流水计划去掉了这个不存在的列，`FROM`、`WHERE` 和 `ORDER BY` 与源码一致。该列不改变“无过滤则全表扫描”的访问路径。V64 尚未在测试库执行；本轮不补迁移。当前在线镜像的流水查询还不读这一列。

### 3.3 财务

总览使用的列表都没有 `WHERE`，按主键 `code` 或 `year_month` 扫描。应收、收款、工资行、消耗品、消耗流水、资产、折旧和应付各 0 行，单次实际耗时 0.004–0.007 毫秒。按月份查工资运行表走主键，当前没有 2026-10 的行，优化器直接得到空结果。按收款号查分配走主键 `receipt_code`，0.004 毫秒。

这些表上已有客户、月份或来源索引，例如 `idx_fin_receivable_customer (customer_id, year_month)`。总览的 SQL 先整表读出，月份和客户过滤发生在内存里，所以上述索引没有参与计划。服务对 6 个月各算一次经营结果，每次都会重复这些空表扫描；客户未收还会再读应收和收款。0 行时重复扫描的数据库时间仍是数毫秒量级。

## 4. 结构缺口与当前耗时

下面只记“过滤列没有可用索引，计划因此扫描”。无 `WHERE` 的整表列表本来就要读完该表，不记成缺索引。

| 缺口 | 本次计划 | 当前数据 | 结论 |
|---|---|---|---|
| `doc_evidence_attachment.business_code` 不是任何索引的首列 | 主键范围检查全部 6 行 | 6 行附件，0.013 毫秒 | 结构缺口仍在。当前没有慢查询 |
| `biz_process_progress_event` 只有主键 `id`，历史查询按 `order_code, process_name` 过滤 | 主键扫描后过滤 | 0 行，0.006 毫秒 | 结构缺口。当前没有可扫描的历史，也没有慢查询 |
| `biz_mother_order.recycled_at`、`biz_work_order.recycled_at` 无索引；母单排序列 `created_at` 也无索引 | 可见母单、可见子单全表扫描 | 3 行和 2 行，回收行都是 0；最慢 1.03 毫秒 | 活跃行就是全部行，单列回收索引即使存在也几乎不能缩小读取。当前没有慢查询 |
| `inv_stock_ledger.customer_id` 无索引；客户范围语句用 `OR` 连接母单号 | 母单索引出现在候选里但未使用，5 行全表扫描 | 5 行，0.022 毫秒 | 结构缺口。全公司流水本来就无过滤，5 行全表扫描是语句形状。当前没有慢查询 |
| 文档包关键字为前置通配 | 3 行主键范围后过滤 | 0.020 毫秒 | 普通等值索引不能服务这种 `LIKE`。当前没有慢查询 |

本轮测得的单条语句实际耗时最大约 1.0 毫秒。服务器自本次启动以来没有语句达到 10 秒阈值。这些缺索引在当前行数下还不是性能故障，本轮不追加索引。

工作台三次请求会重复读取同一批小表，财务总览会把同一批空表读多遍，附件汇总仍在分页之外再全量取数。这是查询形状。以现有行数把重复次数乘上单次毫秒数，数据库时间仍然远小于可感知的停顿，也没有达到慢查询阈值。页面响应时间、权限范围下的 HTTP 往返和目标数据量都还没有测量。

## 5. 本轮边界

保持现有事实表查询、分页和内存筛选。不建可重建读模型，不改游标或页大小，不新增迁移，不修改已发布 SQL。

以后只有在约定数据量和同一数据集的响应基线上，确认某条过滤语句的扫描已经超过目标时，才为对应列追加索引并重测计划。优先候选是附件 `business_code`、进度历史 `(order_code, process_name)`，以及客户范围流水在 `OR` 改写后能否用上已有母单索引。回收标记要先看活跃行比例，再决定是否建索引。财务现有客户和月份索引已经存在，下一步应先让 SQL 使用这些条件，而不是先加新索引。

`4447d79` 的库存读取依赖 `source_ledger_code`。测试库仍是 V63，这条语句现在无法执行。该差异属于发布顺序，不属于本轮查询性能结论。
