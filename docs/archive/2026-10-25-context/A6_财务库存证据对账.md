## 1. 只列两类差异

| 类型 | 含义 |
|---|---|
| 缺失 | 业务动作已经留下应同时存在的台账、账单或证据，但对应记录不在 |
| 孤立 | 台账、账单或证据在，却找不到它声明的业务来源 |

差额、退货、返工、回收和冲正按追加事实处理。原收货流水、原应收和原工资行继续保留；回收只隐藏单据，不要求反向台账或红字。因此本脚本不把母单当前数量与首笔流水相减，也不把退货流水当成发货流水被覆盖。

下列情况不列入差异：

- 应收、工资、应付和消耗品要等财务入账或确认后才生成。没有入账动作时，母单或交付下面没有账单，表示还没到生成时点。
- 证据可以后补。附件没有业务引用时，只要它没有声明一个不存在的单据，就保持待关联。
- 账号前置审批写在 `approval_task.evidence_code` 里的是申请单号。它要对 `auth_account_pre_approval_application`，不对附件表。
- 退货、售后复核、客户备料和公司料目前以库存流水本身作为业务事实，没有单独单据表。流水能对上母单或批次语义时，不算孤立。
- 测试服没有 V64。`inbound_reversal` 若出现会单独计数；本次为 0。脚本不读取 `source_ledger_code`。

本次查询在 3 张母单、5 条流水的库上完成，没有慢查询样本，所以不新增索引或约束。

## 2. 生成时点

| 业务动作 | 台账 | 账单 | 证据 |
|---|---|---|---|
| 收货建母单 | 同一工作单元写 `inbound_confirm`。逐行收货时每行各有流水，母单引用的是首行 | 财务事后按客户协议入账。按克或按件写 `INBOUND\|母单`；按工序的协议不写来料应收 | 收货可留下证据编号。正式关联在 `doc_business_evidence_link`，操作号应等于母单流水号 |
| 拆单 | 写 `work_order_split`。不拆母单的首道交付也可能先把待加工转入在制，单据号仍是母单 | 不直接写账单 | 不强制 |
| 岗位交付 | 中间工序写 `process_station_report`，末道写 `production_report`，交付行保存流水号 | 按工序协议时，财务入账写 `PROCESS\|工单\|工序`。工资要到该月确认才由交付生成 `PAY\|工单\|工序`；`FG-` 开头的返工交付不进这批工资 | 绑定到交付流水号 |
| 质检冻结、返工、放行 | 不合格冻结写 `quality_freeze`；开返工和返工报工追加 `rework_dispatch`、`rework_report`；放行写 `quality_release`。原交付流水保留 | 不在这些动作里写应收或覆盖工资 | 可后补。返工证据指向返工单 |
| 发货 | 与出库单一起写 `outbound_shipment` | 发货事务本身不写应收 | 出库单可记证据编号，关联指向出库单 |
| 退货、售后复核 | 追加 `customer_return`、`after_sales_review`，原发货流水保留 | 不自动写红字 | 没有单独退货单据表 |
| 备料、公司料 | 追加 `prep_receipt`、`prep_issue`、`prep_return`、`company_receipt`、`company_issue`、`company_return`。领用和退回要能找到母单 | 不进入客户金料台账。财务消耗品另行记账 | 不强制 |
| 改单生效 | 不改库存数量 | 客户增额追加 `CHANGE\|改单\|…`，减额追加 `CHANGE-RED\|改单` 并保留原应收；工费追加 `PAY-ADJ\|改单`。金额不变或差额为零时不写 | 引用绑在母单，操作号是改单号 |
| 回收、恢复 | 不冲正流水和余额 | 不冲正应收、工资、应付 | 不解除已有引用 |
| 收货冲正 | 本地 V64 才追加 `inbound_reversal` 并保留原流水。测试服没有这一列 | 这条路径不写账单 | 不强制 |
| 损耗审批 | 不写库存 | 已批准的扣款在工资确认时计入工费行，不另建账单 | 损耗单的非空证据编号应对附件 |
| 收款、消耗品、外协、折旧 | 不写客户金料台账 | 收款分配必须指向已有收款和应收；未分配收款是预收。采购消耗品同时有应付，领用没有应付。外协应付本身就是业务动作。折旧必须指向资产 | 不强制 |

## 6. 证据编号缺口

2026-10-20，分支 `codex/a6-evidence-gap`，基线 `64acd7c`。测试服镜像仍是 `cloud-a4-1e783e4-20261019`，运行库 V63，`source_ledger_code` 不存在。本次查询使用 `START TRANSACTION READ ONLY`，没有写入业务库。

### 6.1 判断

这不是另一套附件编号对不上，而是收货建单把运单号写进了母单证据编号。旧代码把来源类型写成“手机收货”、备注写成“手机收货生成母单”，并把同一个运单号传给证据编号。测试服这三行都符合这个形状：证据编号与 `inbound_express_no`、`courier_identity` 相同，长度为 13 或 15 位字母数字，对不上任何附件编号。收货流水备注里也有“证据：”接上同一号码。

当前源码在改这一处之前仍会这样做。备注已改成“收货生成母单”，来源类型改成收货来源代码，但证据编号参数仍是运单号。所以这三行是历史写入，而新的手机收货仍会留下无法关联的编号。测试服正在运行的镜像还是旧代码，发布前新建母单仍会按旧方式写入；本增量没有发布。

现场文件的正式关联仍是 `doc_business_evidence_link`。两张母单已经有对上收货流水的引用和附件，只是母单上的证据编号不是这些附件。另一张没有引用，也没有挂在该母单上的附件。

直接确认入库和登记导入仍保存调用方提交的证据编号。本增量不改那些入口，也不在保存时按附件表拒绝编号。

### 6.2 历史清单

下列三行保持原样。不改母单证据编号，不改流水备注，不补文件，不删编号，不改附件字节。来料列表仍把非空证据编号显示为“已关联”，所以这三张在列表上仍会显示已关联；文件是否在，以业务证据引用和附件为准。

| 母单 | 写入时间 | 证据编号长度 | 与运单号相同 | 业务证据引用 | 其中对上收货流水 | 挂在该母单的附件 | 证据编号命中附件 |
|---|---|---:|---|---:|---:|---:|---:|
| MD-20261013-001 | 2026-10-13T20:13:42.832295605 | 15 | 是 | 2 | 2 | 3 | 0 |
| MD-20261014-0002 | 2026-10-14T22:32:46.53530933 | 13 | 是 | 2 | 2 | 2 | 0 |
| MD-20261014-001 | 2026-10-14T17:44:09.275002752 | 15 | 是 | 0 | 0 | 0 | 0 |

三行的来源类型都是“手机收货”，备注都是“手机收货生成母单”。运单号本身不写入本文。

复查时仍用只读事务，只看编号是否相同和引用是否存在，不选出运单号、客户或附件名：

```sql
START TRANSACTION READ ONLY;
SELECT m.code,
       CHAR_LENGTH(m.evidence_code) AS evidence_len,
       (m.evidence_code = m.inbound_express_no) AS same_as_express,
       (m.evidence_code = m.courier_identity) AS same_as_identity,
       (SELECT COUNT(*) FROM doc_business_evidence_link l
         WHERE l.target_type = 'MOTHER_ORDER' AND l.target_code = m.code) AS link_count,
       (SELECT COUNT(*) FROM doc_business_evidence_link l
         WHERE l.target_type = 'MOTHER_ORDER' AND l.target_code = m.code
           AND l.operation_code = m.ledger_code) AS link_matches_ledger,
       (SELECT COUNT(*) FROM doc_evidence_attachment a WHERE a.code = m.evidence_code) AS attachment_hit,
       (SELECT COUNT(*) FROM doc_evidence_attachment a WHERE a.business_code = m.code) AS files_on_mother
  FROM biz_mother_order m
 WHERE TRIM(m.evidence_code) <> ''
   AND NOT EXISTS (SELECT 1 FROM doc_evidence_attachment a WHERE a.code = m.evidence_code);
COMMIT;
```
