## 1. 当前写入与读取链

| 动作 | 当前代码路径 | 事实表及兼容语义 |
|---|---|---|
| 收货建母单 | [MobileIntakeService](../../../backend/src/main/java/com/zhubao/erp/business/app/MobileIntakeService.java) → [BusinessOperationService](../../../backend/src/main/java/com/zhubao/erp/business/app/BusinessOperationService.java) → [JdbcBusinessDocumentRepository](../../../backend/src/main/java/com/zhubao/erp/business/infra/JdbcBusinessDocumentRepository.java)、库存服务 | 母单、`biz_mother_order_item` 与首条库存流水同次写入。显式逐行收货才标记 `INTAKE_LINES:` 并写 `biz_receipt_line`，随后更新母单汇总；因此新单的旧明细和母单流水保留首行值，母单数量重量变为多行合计。旧单读取明细时从母单合成一条只读行。 |
| 拆单 | [MotherOrderSplitService](../../../backend/src/main/java/com/zhubao/erp/business/app/MotherOrderSplitService.java) → 单据仓储、库存服务 | 旧路径写子单和库存流水，不写来源分配；`INTAKE_LINES:` 路径核对每条来源余额，为子单写 `biz_child_line_allocation` 和逐来源库存流水。 |
| 发货 | BusinessOperationService → JdbcBusinessDocumentRepository、库存服务 | 出库主单、`biz_outbound_order_item` 与库存流水同次写入；当前 Java 读取出库主单及台账，未发现读取旧出库明细的 SQL。 |

两张旧明细表来自[V14 迁移](../../../backend/src/main/resources/db/mysql/V14__m3_business_document_contract.sql)，当前 Java 只执行插入；逐行收货与来源分配来自[V60 迁移](../../../backend/src/main/resources/db/mysql/V60__m3_receipt_line_allocation.sql)，已有读写消费者。仓库外报表、导出和打印程序是否直接查询旧明细仍未核实，不能把当前 Java 的“只写”解释为整个系统不再需要这些表。

## 2. 测试库只读结果

使用[可复跑 SQL](../../../scripts/a3-readonly-audit.sql)在测试服务器 MySQL 执行 `START TRANSACTION READ ONLY`；脚本只输出聚合数量和异常计数，不输出客户或单据明细。

| 对象 | 行数 | 已核对关系 |
|---|---:|---|
| `biz_mother_order`／`biz_mother_order_item` | 3／3 | 每张母单恰有一条旧明细；材质、数量、单位、重量和流水号与母单一致；母单流水的数量、重量和来源维度一致。相关异常计数均为 0。 |
| `biz_receipt_line` | 0 | 没有 V60 逐行收货样本，不能验证新旧明细共存与母单汇总。 |
| `biz_work_order`／`biz_child_line_allocation` | 2／0 | 两张子单均属非 `INTAKE_LINES:` 的旧路径；子单及流水的数量、重量和来源维度一致，子单合计未超过母单。逐行拆单无样本。 |
| `biz_outbound_order`／`biz_outbound_order_item` | 0／0 | 没有发货样本，主单、旧明细与流水的异常计数为 0 不具备证明力；零行不是停写依据。 |
| `inv_stock_ledger`／`inv_stock_balance` | 5／5 | 流水为 `inbound_confirm` 3 条、`work_order_split` 2 条；母单和子单引用的流水均存在。余额表仅核行数，本轮没有把余额与全部维度重算。 |

拆单决定另有 `KEEP` 2 条、`SPLIT` 1 条；未发现逐行来源子单缺分配、子单无母单、出库无旧明细或主单缺引用流水，但后两类检查因没有出库数据而**不具备证明力**。上述结论只覆盖这一个 3 张母单的测试库，不代表客户库或新流程已通过对账。

在测试机 Linux shell 中复核时，可将 SQL 文件复制到测试机，再于运行目录执行：

```sh
sudo docker compose exec -T mysql sh -c 'mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" --batch "$MYSQL_DATABASE"' < /path/to/a3-readonly-audit.sql
```

## 3. 收口判定与下一增量

| 候选 | 当前判定 | 进入实现的条件 |
|---|---|---|
| V14 两张旧明细停止写入 | 待收口，暂保持写入；旧路径中母单明细与母单重复，新逐行路径中它仅代表首行，语义并不等同于母单汇总；隔离库已验证出库写入但测试服务器仍无发货样本 | 取得真实发货样本并核对主从表、台账和旧单兼容读取；确认仓库外消费者，再决定兼容期及停写位置。 |
| V60 逐行收货和来源分配 | 保留；隔离 MySQL 已验证两行收货、多来源部分拆分、失败回滚及同请求重试 | 真实客户库出现样本后执行只读对账，并核查目标数据量、锁与并发边界。 |
| V14／V60 历史表和迁移 | 保留 | 迁移 append-only；本轮没有删表或改已发布脚本的依据。 |

2026-10-19 已补充 H2 MySQL 模式的 JDBC 定向用例：两条来源收货后，第二条来源分配的数据库约束故意失败，子单、来源分配、拆单决定和库存流水均回滚；解除约束后沿用同一请求编号成功拆单，再回放不重复写入。`IntakeReceivingTest` 4 项通过。它验证 JDBC 工作单元，不代表真实 MySQL 的迁移和锁行为已验收。

隔离 MySQL 的发货主从表、库存流水和失败回滚已补验。在有真实数据和仓库外消费者结论前，不停止旧明细写入；后续优先补充客户库只读样本及消费者确认。

## 4. 本机隔离 MySQL 的 V60 样本

本机临时 MySQL 8.4 独立库经项目升级入口从空库执行 V1—V63，登记 63 条迁移、形成 103 张表；只监听本机地址。定向[集成测试](../../../backend/src/test/java/com/zhubao/erp/business/app/A3MysqlIntakeSplitIntegrationTest.java)实际运行 2 项：两来源收货与第二来源分配失败的完整回滚、同请求编号重试及回放；旧路径收货拆单后转入成品，出库旧明细插入失败时主单、流水和库存余额回滚，解除约束后沿用原请求成功并回放不重复写入。该测试只有显式设置 `A3_MYSQL_JDBC_URL`、`A3_MYSQL_DB_USER`、`A3_MYSQL_DB_PASSWORD` 才运行，并拒绝连接本机 `a3_verify_` 前缀之外的库。

首轮成功样本为 1 张母单、1 条 V14 旧明细、2 条 V60 收货行、2 张子单、2 条来源分配和 4 条库存流水。母单汇总数量／重量为 8／12；旧明细与母单的 `ledger_code` 均指向首行 3／4，第二来源为 5／8。由此确认原只读脚本把旧明细或首行流水直接与新母单汇总比较会误报。现已按 `INTAKE_LINES:` 分支分别核对旧单的母单快照、新单的首行投影、逐行合计与逐行流水、子单分配与拆单流水。

第二项测试留下 1 张出库主单、1 条旧出库明细和 1 条出库流水，数量／重量、母单／子单及材质相符。两项测试多次复跑后的隔离库合计 3 张母单、3 条旧母单明细、4 条逐行收货、6 张子单、4 条来源分配、1 张出库主单、1 条旧出库明细、13 条库存流水；[只读脚本](../../../scripts/a3-readonly-audit.sql)在此样本和测试服务器旧样本上均执行成功，除隔离库 2 张、测试库 2 张旧路径子单无来源分配按兼容语义单独计数外，异常计数均为 0。脚本现同时检查出库旧明细数量、主从字段、流水存在及数量重量。

隔离样本不包含实际客户数据；它证明所测事务与 SQL 在 MySQL 8.4 上可运行，不证明测试服务器已有 V60 新单、发货单或仓库外消费者已验收。
