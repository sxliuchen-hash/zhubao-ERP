# ERP 整体 UI 与多端设计规划

**文档版本**：V0.2

**更新日期**：2026-10-10

**文档定位**：整体设计依据；任务完成状态统一见 [UI 开发执行入口](./27_UI开发执行提示词.md)

**适用范围**：电脑 Web、手机 Web／PWA，以及后续 APP、微信小程序。

**关联**：[业务流程与规则](./02_业务流程与规则设计.md)、[字段与接口契约](./16_字段字典与API契约.md)、[部署与手机访问](./19_Docker一键部署与离线交付.md)、[固定基调](./ui-prompts/00_固定基调.md)。

## 1. 产品方向

统一为「专业、清晰、克制的珠宝加工 ERP」。电脑承担管理、核算、批量处理；手机承担扫码、收货、报工、质检、审批和随时看经营。品牌、业务名称、状态、数据口径一致，页面结构根据设备和岗位调整。

视觉上采用深蓝灰导航、浅灰工作区、白色内容区、蓝色主要操作。珠宝行业感通过品牌标识与少量暖金点缀表达；财务数字、表格和状态仍以可读性为先。日常作业页避免满屏大卡片、渐变背景和大面积金色。

设计参考图中的金额、客户、任务均为样例，仅指导信息层级。正式界面必须连接真实查询，不能将参考图或任务准备视为功能完成。

## 2. 改造重点

- 保留既有业务能力和权限，使用六组导航与统一单据模板降低入口和布局复杂度。
- 财务以经营总览组织阅读，登记表单作为二级入口；先解决读取授权和权威汇总，再展示看板。
- 手机围绕岗位任务、独立详情和分步提交组织，不依赖横滑桌面表格完成核心动作。
- 复用现有基础组件，按模块迁移并清理对应旧样式；固定示范参数改为可核对的真实业务表单。

## 3. 信息架构与角色首页

电脑端采用左侧业务导航、顶部追溯与用户区、页面标题与操作区、主内容区。一级分组控制在六组，二级页面逐步承接现有入口：

| 业务分组 | 页面与功能归属 |
|---|---|
| 工作台 | 我的待办、经营概览（有财务权限才显示）、最近处理 |
| 来料与订单 | 收货母单、拆分子单、加工要求、标签打印 |
| 生产与质量 | 派工报工、在制进度、质检、返工 |
| 库存与交付 | 库存台账、出库、退货、全链路追溯 |
| 财务经营 | 经营总览、客户账单与计价协议、收款、工资、消耗品、固定资产、外协与应付 |
| 协同与系统 | 审批、附件、登记导入、账号与客户范围、设备、运维 |

展示分组不自动新增权限。保留现有菜单与操作编码；老板身份不能自动获得财务数据权限。没有权限的入口不显示，接口同时校验操作权限和客户范围。

| 使用者 | 默认首页重点 | 常用动作 |
|---|---|---|
| 管理者（已获经营查看权限） | 加工收入、经营结余、未收款、应付、交付异常 | 看趋势、查客户、处理例外 |
| 财务／统计 | 资金与账单待办、核销、工资确认、成本缺项 | 登记收款、核对账单、确认工资、查应付 |
| 收货人员 | 待收货与待补资料 | 扫面单、建母单、录拆包视频、打印贴纸 |
| 工序人员 | 本岗位任务与加工要求 | 扫贴纸、核对工序、提交报工 |
| 质检人员 | 待检、返工复检 | 逐项核对、判定、上传证据 |
| 仓库／办公室 | 待交付、在制进度、库存异常 | 查批次、出库、追溯 |

工资、经营结余等敏感数字不能因某人能看订单而一并开放。隐藏金额是旁人防窥功能，不能替代授权。

## 4. 统一视觉规范

全站视觉参数以 [固定基调](./ui-prompts/00_固定基调.md) 为唯一执行依据，统一颜色、字号、间距、金额、状态、响应式和打印边界。设计先在代表页验证，再推广，不同时维护两套皮肤。

普通文字对比度至少 4.5:1；图表不能只靠红绿区分，操作有可见键盘焦点。参照 [W3C 对比度说明](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum)。现场触控目标至少 44px，是项目设计目标。

### 4.1 全站六类页面模板

1. **经营总览**：统一筛选 → 核心指标 → 趋势和结构 → 异常与明细入口。
2. **单据列表**：标题与主操作 → 常用筛选 → 表格／手机卡片 → 分页与汇总。高级筛选收起，不把新增表单固定堆在列表下方。
3. **单据详情**：单号、状态、客户与期限 → 工序／流转进度 → 明细 → 证据与操作记录 → 当前允许的动作。
4. **新建与编辑**：按业务分区组织字段；手机长表单分步；错误贴近字段显示，失败保留已填信息。
5. **扫码现场作业**：任务身份 → 加工要求 → 本岗位可提交项 → 确认结果；拍摄与扫码失败时有手工输入或照片识别入口。2026-10-12 的统一扫码 S2 只把收货、岗位报工、质检贴纸和现场贴纸收成同一输入和只读上下文卡片，提交前必须重新查到规范身份。S3 在来料工作台增加共用现场证据：选择文件、拍照、预览、上传、失败重试和关联状态。S4 在岗位、质检和发货准备入口追加过程说明，手机和桌面调用同一保存接口。阶段显示为生产过程、质检过程或发货准备；补充记录单独标出。扫码成功不等于已经留证或已经报工。上传失败时保留记录编号，显示「过程已保存，证据待补」。S5a 把手机收货和桌面新建来料收成同一面板：建单前可以选文件，同一次确认复用请求编号，超时先按运单打开原单。证据上传失败只显示业务已保存并重试文件。这不是 UI-08 的手机作业流程，UI-08 与 UI-09 仍未开始。
6. **审批与异常**：风险及原因 → 原始单据与证据 → 同意／退回及意见；红色只用于异常和危险动作。

桌面宽屏可采用列表＋详情双栏。普通宽度用独立详情或侧边抽屉；手机详情进入单独页面，避免窄屏同时放列表和长表单。打印继续使用独立黑白版式及毫米纸张尺寸。

### 4.2 基础组件边界

优先沉淀 `ErpPageHeader`、`ErpFilterBar`、`ErpDataTable`、`ErpMobileList`、`ErpStatusTag`、`ErpAmount`、`ErpMetricCard`、`ErpChartPanel`、`ErpFormSection`、`ErpEmptyState` 和 `ErpActionBar`。名称为建议，实施时避免与现有组件重复。

组件统一加载、空数据、无权限、校验错误、接口失败、保存中、成功反馈。组件只负责表现与交互；业务状态、计价和权限仍来自领域及接口，不写入颜色判断或组件内部。

## 5. 财务经营仪表盘

### 5.1 首屏应回答的四个问题

本期做了多少加工收入？已记录成本后剩余多少？还有多少未收款？有哪些应付和缺项需要处理？

电脑首屏布局：

```text
财务经营 / 经营总览           月份 · 授权客户范围 · 更新时间
加工收入          经营结余          未收款余额          应付未付余额
加工收入与结余趋势（近 6／12 月）     成本构成（工资／耗材／折旧／外协）
客户未收款排行                      待核对：未定价／未确认工资／成本缺项
点击指标或客户 → 保留月份、范围与状态 → 对应账单和明细
```

补充层显示本期收款和本期付款，并分别注明「发生额」。不把收入和收款画成同一指标，不把经营结余称为净利润，不以收款减付款代表完整现金流。

图表优先折线、柱状和横向条形；成本结构带金额标签。仪表盘指经营数据看板，不强制做速度表形状；仅在存在明确目标及可靠实际值时使用目标进度。避免 3D 饼图、装饰性刻度和缺少明细入口的数字。

### 5.2 指标口径与数据准备

下表区分已有字段与拟建能力；完整口径需在聚合接口实施时用样例账逐项对齐。

| 指标 | 已有基础 | 上线前必须解决的口径与边界 |
|---|---|---|
| 加工收入 | `OperatingStatement.revenue`、应收账单行 | 依据账单所属月份；冲销按既有账务规则抵扣；不是银行到账金额 |
| 经营结余 | `OperatingStatement.result` 及四项成本 | 明示「加工收入减已记录工资、耗材、折旧、外协」；成本未齐标为暂估，保留 `gaps`；不得标作净利润 |
| 本期收款 | 客户收款的 `amount`、`receivedOn` | 按收款发生日期统计，包含未核销款；不能直接拿账单已核销额代替 |
| 未收款余额 | `CustomerStatement.outstandingAmount` | 需要明确截至日、期初余额、累计核销与冲销；不能简单把选定月份的账单合计称为全部欠款 |
| 预收／未分配款 | `CustomerStatement.prepaymentAmount` | 独立展示未核销款，不能作为新增加工收入，也不能重复抵扣未收款 |
| 应付未付余额 | `PayableView.unpaidAmount` | 区分本月新增应付与截至日全部未付；工资、耗材采购、外协等来源需可追溯 |
| 本期付款 | 已有应付付款命令 | 需要可查询的付款发生明细与聚合，不用应付金额代替付款金额 |
| 成本构成 | 工资、耗材领用、折旧、外协字段 | 耗材采购不是领用成本；固定资产原值不是当月成本；工资计提与支付分开 |
| 环比与历史趋势 | 单月经营查询 | 新增同口径、同范围多期聚合；上期为零或缺失显示「不可比」，不算无限增长 |
| 客户未收款排行 | 单客户账单查询 | 新增授权范围内批量聚合，后端排序、分页；不能前端逐客户请求并拼成全公司数据 |
| 账龄／逾期 | 当前字段不足以可靠判断 | 先补协议账期、到期日和截至日核销关系；未补齐前显示「尚未提供」，不以账单月份冒充逾期 |
| 客户来料数量／克重 | 库存与账单关联字段 | 作为受托保管和交付信息单列；不合并进自有资产估值或利润指标 |

现有查询有以下明确边界，改版时必须保留或通过新接口纠正，不能仅改标签：

- 选月客户账单的 `receivedAmount` 是该月账单被跨月收款累计核销的金额；不是本月实际收到的钱。
- `outstandingAmount` 是所选账单截至当前的未核销余额；`prepaymentAmount` 是所选月收款中当前未分配部分；当前 API 不回放历史月末余额。
- 客户账单的数量和克重是当前结存；应付查询的已付与未付是所选应付单的累计付款结果。不能与当月发生额混成一组现金流。
- 工资未确认、折旧未生成时成本可能按 0 计，未计价单据不进入收入，需醒目展示 `gaps`。
- 客户经营查询不包含公司折旧，也不包含未分配到该客户的公司耗材和外协；各客户结余相加未必等于公司结余。客户分析必须注明「已归集成本口径」。
- 已登记收付不能推导完整银行账户余额；当前缺少账户、期初余额与全部收支科目。

### 5.3 数据交互与可信度

- 每张卡片显示单位、期间或截至日、客户范围和更新时间。期间型收入与时点型余额分区或明确标注。
- 后端计算权威汇总，金额采用现有精度规范；前端负责格式化，不对分页表格求和冒充全量汇总。
- 点击卡片进入同口径明细，筛选条件必须继承。回到总览保留月份、客户与列表位置。
- 只读打开仪表盘不得自动触发生成账单、生成工资、折旧等写入命令。
- 无数据显示空态；接口失败显示重试；数据不全显示缺项；无权限显示不可访问。不能统一填成 0。
- 部分图表失败时保留成功部分并标记失败部分；旧数据展示其实际更新时间，不伪装为最新结果。
- 客户过滤、总额、排行、导出、明细必须使用同一授权范围；异常数据、人员工资也按权限拆分。
- 记账成功后刷新相关汇总与明细；重复点击禁用，重复请求和并发记账由后端防重规则保证。

### 5.4 接口边界与实现分层

只读 `GET /api/finance/dashboard` 以月份和可选客户为输入；经营、趋势、当前余额、排行、缺项和能力状态分开表达。余额返回实际 `asOf`，一个日期字段不能同时代表账期和发生日期。实际字段、读取权限和范围规则以 [API 契约](./16_字段字典与API契约.md) 为准，后续明细与汇总沿用同一范围解析。

经营查看、资金登记和工资管理分别授权。`customerId` 是查询条件，不能替代服务端授权；汇总、排行和明细也不能泄露未授权客户或公司成本。实现与验收状态仅记录在任务入口，不在设计文档重复维护。
实现保持财务模块 `domain / app / infra / web`：领域负责金额与口径，应用层负责授权范围和查询用例，基础设施负责可切换的内存／JDBC 查询，Web 层负责契约。需要新增表时按现有 append-only 迁移规则递增，不能修改已发布迁移。

## 6. 手机 Web／PWA 设计

手机不是缩小版电脑。先按管理者与现场岗位提供不同首页，再使用相同业务词汇和组件规范。

| 场景 | 手机结构 |
|---|---|
| 管理者看经营 | 月份与金额显隐 → 收入／结余 → 未收／应付 → 一张主要趋势 → 客户未收款与异常 |
| 财务日常处理 | 我的待办 → 客户账单卡片 → 收款核对 → 确认结果；复杂批量核算留在电脑 |
| 收货 | 扫面单／输入单号 → 客户和要求 → 建母单 → 拆包视频与上传状态 → 标签后续入口 |
| 报工 | 扫贴纸 → 当前单与本岗位要求 → 必填项 → 确认提交 → 成功凭据 |
| 质检 | 扫单 → 逐条加工要求 → 判定与问题 → 证据 → 确认结果 |
| 审批 | 待办卡片 → 金额／风险／证据 → 意见 → 审批结果 |

底部常用导航建议为「工作台、任务、扫码、消息、我的」，按岗位与已有能力裁剪；没有消息中心时不放空入口。扫码入口突出但不遮挡键盘与确认按钮，财务经营由有权限的工作台进入。

手机单据卡片首行显示单号和状态，随后显示客户、期限、工序或金额，保留一个主要动作。完整财务明细可提供专门表格查看，但日常列表不要求左右滑动才能读核心字段。

页面底部确认区适配安全区和软键盘；返回时提示未保存变更；上传显示进度、失败重试和成功凭据。网络中断时保留可恢复草稿，必须区分「本地草稿」「待提交」「服务端已确认」；离线账务自动补传不纳入一期。

手机默认显式确认收款、付款和质检等业务提交，避免误触。摄像头授权失败仍能继续手工输入；上传和提交状态分别反馈，避免把视频上传成功当作业务单据已保存。

## 7. APP 与小程序的延续方案

### 7.1 复用什么

共用色彩、字体层级、间距、图标含义、状态名称、字段字典、校验规则、权限和接口契约。桌面表格、浏览器 DOM、摄像头和打印代码不假设能直接复制到 APP／小程序。

建议将可共享内容逐步拆为设计令牌、纯业务类型与校验、平台无关 API 契约。扫码、拍摄、文件上传、登录、消息通知和打印按平台适配。现有 Web 先改善，后续移动应用独立验证，不为未来平台提前重写桌面 ERP。

### 7.2 各端职责

| 平台 | 优先功能 | 需要单独设计与验证 |
|---|---|---|
| 电脑 Web | 全量经营、账单、批量编辑、对账、导出、系统维护 | 多列信息密度、快捷键、打印与批量操作 |
| 手机 Web／PWA | 现场扫码、视频证据、报工、质检、轻审批、经营速览 | HTTPS、浏览器权限、网络失败、安装与兼容性 |
| APP | 高频现场作业、设备接入与移动协同 | 原生权限、安全区、扫码性能、断网草稿、上传恢复、推送与版本更新 |
| 微信小程序 | 轻量现场作业、查询、审批 | 微信登录与 ERP 账号绑定、相机与文件能力、包体、后台生命周期、通知入口 |

客户自助查单若后续需要，单列客户身份、数据范围和入口设计，不把内部财务界面直接对外开放。

### 7.3 技术路线验证门槛

APP／小程序阶段可把 uni-app 作为候选，通过扫码、短视频上传、任务详情和权限登录四个真实流程做小样验证，再决定是否采用。官方说明提供跨端编译和条件编译，但仍需要处理平台差异，不能承诺现有 Vue 页面无改动运行。参照 [uni-app 跨端原理](https://uniapp.dcloud.net.cn/tutorial/) 与 [多端差异处理](https://zh.uniapp.dcloud.io/tutorial/platform.html)。

验收必须覆盖真机的拒绝授权、低光扫码、上传中切后台、弱网重试、账号过期、重复提交和安全区。采用何种框架不改变后端权限及领域规则。

## 8. 响应式与布局基线

| 宽度 | 导航 | 主要内容 |
|---|---|---|
| ≥1440px | 完整侧栏 | 多列指标、图表双栏、列表＋详情 |
| 1024–1439px | 可收起侧栏 | 指标 2–4 列，较长详情使用独立页或抽屉 |
| 768–1023px | 精简侧栏或抽屉 | 双列卡片，表单按可读宽度重排，复杂详情单列 |
| 320–767px | 顶部上下文＋岗位底部导航 | 指标两列或单列、单据卡片、全屏详情、分步表单 |

断点是初始基线，依据内容调整，不按设备名称硬编码。验证宽度至少覆盖 320、375、390、768、1024、1440px；同时验证文字放大、横屏、长单号、负金额和大金额。页面外层不得横向溢出。

## 9. 实施阶段

| 阶段 | 设计目标 | 通过条件 |
|---|---|---|
| 统一基础 | 主题、外壳、导航和来料代表页 | 登录、追溯、打印和既有业务不回退 |
| 财务总览 | 读取授权、期间经营与趋势、当前余额、下钻和仪表盘 | 指标可核对、范围一致、缺项真实、读取不写账 |
| 全站及手机 | 其余模块统一模板，手机完成收货、报工和质检 | 核心手机流程无需横滑表格，真机可采集和提交 |
| 移动应用验证 | APP／小程序小样与平台差异验证 | 真机验证后决定正式开发范围 |

具体任务、前置条件、完成提交和下一步统一维护在 [UI 开发执行入口](./27_UI开发执行提示词.md)。每个模块迁移后清理无人调用的旧样式，避免长期保留两套实现。

## 10. 验收清单

- 视觉：页面标题、按钮、表格、状态、金额、筛选和间距符合统一规范；标签仍黑白打印。
- 业务：登录、菜单授权、客户范围、追溯、现有收货报工质检出库和财务命令均保持正确。
- 财务：收入与收款、成本与付款、月份发生额与截至日余额分清；预收、冲销、跨月核销、成本缺项均有用例；结余可核对，缺项不能被隐藏。
- 权限：无财务权限、仅一个客户范围、跨客户查询、导出、排行和汇总均有服务端验证；操作工不能通过手机入口收款。
- 交互：加载、空态、失败重试、失去登录、重复提交、保存中返回均有明确结果；没有只改颜色却保留失效按钮的页面。
- 移动：至少在实际 Android／iPhone 浏览器检查扫码、拍摄、键盘、安全区、切后台和弱网；APP／小程序另做平台真机验收。
- 工程验证和文档同步遵守 [AGENTS.md](../AGENTS.md)；UI 专项验收见 [整体验收任务](./ui-prompts/UI-10_整体验收.md)，设计示意、内部验证和正式交付分别记录。
