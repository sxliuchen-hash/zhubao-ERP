# 交货后工费结单与收付款改造方案

**日期：2026-10-27。状态：已完成源码调查，待定业务项见第 16 节；尚未实现、迁移或发布。**

本方案以 `App.vue` 的现行调用链和当前工作区为依据。调查期间工作区有其他界面调整，本方案不覆盖这些改动。当前事实与待办统一由[项目核心](./00_项目核心.md)承接；本文件保存本项需求的设计、改造边界和验收条件，不替代现行 API 契约。

## 1. 已确定的业务规则与范围

用户已明确：**客户加工费和员工计件工费，全部在本单完成交货以后填写，前期不再填写。**

据此确定以下规则：

1. 收货、拆单、生产、交工、质检及交货前改单不填写本单客户价、员工工费、收费差额或工资差额，也不据此形成应收、工资或员工应付。
2. 交货完成后进入“待工费结单”；此时才允许建立金额草稿。客户加工费、员工工费均完整确认后，业务才完成。
3. 保存草稿不入账；最终确认结单时，同次保存客户应收、员工工资明细及员工应付，任一步失败整体回滚。
4. 客户实际付款后，通过收款分摊核销多张订单；先前已登记的预收款允许后续关联订单，不再登记一次到账。
5. 业务完成、客户收款结清、员工付款结清分别表达。客户付款不能使员工应付自动变成已付，员工工资也不等待客户付清才形成。
6. 新流程不依赖预先维护客户协议或员工工价，不自动套价、预填金额，也不把空白当作零。历史协议和工价只用于查旧账。
7. 库存、交工、质检、附件、标签、PWA、备份等沿用现有事实和基础设施，不另建生产或资金总账。

“交货”在本方案中暂按**现有成品确认发货，且本单应交范围已全部交完**解释；当前系统没有独立的客户签收事实。若业务要求客户签收后才能填费，需增加签收事实，不能把物流单号或附件上传当作签收。此项是方案假设，尚未得到业务确认。

不在本次默认范围：银行对账和支付通道、完整会计凭证、员工代发、员工跨订单一笔批量付款、自动退款、自动扣罚、任意分批工费结算和跨订单合并工费结单。客户一笔收款核销多订单属于本次范围。

## 2. 源码调查结论

以下是当前实现事实，不代表已具备目标功能。链接均指向实际代码；实施时应以当时最新代码复核。

| 链路 | 现有实现与证据 | 对本次改造的含义 |

## 3. 目标流程与结单粒度

### 3.1 正常流程

收货 → 母单／拆单 → 生产与分批交工 → 质检／返工／放行 → 分批发货 → **本单交货完成 → 填客户加工费和员工工费 → 确认结单 → 业务完成**。

之后分别办理客户收款核销和员工应付付款。允许客户预收；交货前只登记实际到账，不分摊到尚未形成的本单应收，不产生收入或工资。

### 3.2 粒度建议，尚待业务选择

建议按实际生产目标结单：不拆单用母单，拆单后各子单分别结单，母单汇总。母单存在子单时，不再对同一批货额外生成一份母单基础工费。

同一目标的多张出货单归入一份最终结单；首版不做“发一批就填一批工费”。未交齐时不开放金额草稿，避免通过提前存草稿绕过用户的新规则。

执行轮次和质检返工不是天然的新收费订单。以原生产目标为结单归属，附上各次作业事实；是否另计客户费、是否支付返工工费，均在交货后明确填写，不能按轮次数自动复制整单费用。

如果业务选择“母单全部交货后统一结单”，同一套结单、应收和工资模型不变，结单范围改为母单及全部子单，明细仍保留子单来源；实施前固定一种粒度，不让同一母单在两种口径间自由切换。

## 4. 如何认定交货完成

新增只读的 `OrderDeliveryCompletionQuery`，归属 `business/app`，作为结单、订单列表、工作台及扫码动作的共同判定来源。该服务不写库存、进度或财务。

| 条件 | 判定与拒绝原因 |
|---|---|
| 身份明确 | 解析稳定客户、母单、实际生产单；运单号只用于定位。母子客户冲突、未知轮次、回收中的对象拒绝新结单 |
| 生产结束 | 读取当前有效要求／路线和正式交工，不以 100% 进度代替交齐；未结束批次、有效返工或执行轮次未处理时拒绝 |
| 质量结束 | 使用现有质量结论、轮次和库存放行事实，未解决的不合格、冻结或售后待核不得被当作正常交完 |
| 数量交齐 | 逐个目标及材质／原数量单位核对有效应交数量与净已发数量，结合出货单、退货及库存台账；不能只查“有一张出货单”或“成品余额为零” |
| 母单覆盖完整 | 母单汇总同时核对未拆分来源余量、全部子单及有效轮次。回收子单不能自动当作已交或从应交范围扣除 |
| 来源一致 | 出货单和实际台账对应，来源缺失、重复映射、单位不一致、负数或无法解释的差异进入“交货待核”，不自动认定完成 |

新流程默认只接受正常完整交货。当前子单数量更正、真实退料和生产损耗的事实更正仍有未关闭边界，不能在结单页面靠勾选“少交完结”抹平差异。确需少交／报废完结时，先完成有证据、有权限、可追溯的实物处置，再参与完成判定；本次不顺带建设整套异常库存业务。

数值使用服务端 `BigDecimal`；数量、重量分别核对，不混用件、克、颗等单位，也不要求发货重量等于收货重量。实物重量不从计费重量反写。

完成判定返回 `eligible`、结构化阻断原因、来源单号、实际数量与单位、`deliveryRevision`。该版本由服务端对当前事实生成；确认结单时必须重新校验。前端计算、旧列表标签和客户端传来的版本都不能作为交货证明。

已结单后发生退货或新增重做，原结单事实保留，当前业务显示“售后处理中／需复核”；不能删除原应收或工资，也不能因再发一次货自动重复计费。

## 5. 交货后结单表单与金额规则

### 5.1 客户加工费

自动带出客户、母子单、货品、交货事实和实际数量；**所有金额和单价初始为空**。支持整单固定金额、按件、按克及按实际工序分项填写，计费方式仅在交货后选择。

每行保存项目名称、来源生产目标／轮次、计费方式、计费数量与单位、单价、金额、备注；按件／按克由后端计算行金额，固定金额直接填金额。不得同时允许修改计算结果却不记录调整依据。折让以独立调整项目及原因表示，最终客户净应收不得为负。

允许明确免收：必须选择免收并填写原因。缺行、空金额、输入无效、没有协议均不等于免收。

### 5.2 员工计件工费

从真实工序、分批交工、返工及执行轮次列出**待核对作业清单**，只预填作业事实，不预填钱，也不自动认定收款员工。

每条员工工费明细至少保存：工序／作业实例、来源批次或轮次、实际计酬员工稳定身份、员工名称快照、计费数量与单位、交货后填写的单价或固定金额、工费毛额、确认扣减、工费净额及依据。

- 同工序多个人完成，允许拆成多条人员分配行。最后提交整工序交齐的人不能独占全部工费。
- 代报工、顶岗和零数量补重量都不自动增加计酬数量；同一批次多人分配时，按该来源内的份额核对，不重复使用整批数量。
- 按克计酬时如没有个人实测重量，不按人数、件数或整单重量自动推算；可交货后人工确认计费重量，保存依据，或选择固定金额。
- 员工工费总额不要求小于客户加工费；亏损订单可以存在，但应显示差额，不由系统悄悄截断。
- 返工工费、免计工费、无内部计酬作业均须逐项明确，不能因为没有有效工价就跳过。不存在内部作业时明确选择“无内部计件工费”并注明原因。
- 扣减属于交货后确认金额。保留关联损耗／责任事实和确认人，不从审批摘要解析字符串自动扣款；相同损耗依据不能在多个分配行重复扣减。
- 普通明细毛额和扣减均为非负，扣减不得超过该行毛额；净额为零可记录，负差额只走已确认账单的调整流程。

人员身份先复用现有登录账号的稳定 `username`，保存当时名称；操作人、制单人、计酬人三者分开。历史交工仅有显示姓名，重名、代报及未映射人员必须人工核对，不能自动匹配。若实际计酬人员没有账号，需要确定独立人员档案或受控的历史人员映射；设备记录里的可空 `operatorEmployeeId` 不等于已有可复用的完整员工档案。

### 5.3 草稿与确认

| 动作 | 结果 |
|---|---|
| 交货完成前打开 | 只读查看事实和阻断原因，不出现费用录入，不接受金额保存 |
| 保存草稿 | 仅保存结单草稿与版本，不写应收、工资、应付，不标业务完成 |
| 确认结单 | 再验交货、版本、所有客户／员工明细及历史账务，一次提交结单与账务 |
| 响应丢失重试 | 同账号、同请求、同内容回放原结果，不重复入账 |
| 入账成功后刷新失败 | 保留成功单号，只重读状态；不重新发货、不重新结单 |

第一版最终确认要求同时具有客户加工费入账与工资核算权限，并具公司 `ALL` 数据范围，沿现有财务职责完成。若要由业务人员填客户费、主管填员工费，可以按各自权限保存两个分区草稿，再由有两项权限的人整体确认；不能让其中一部分已写账、另一部分失败却显示业务完成。

## 6. 状态与财务口径

保留原生产、质量、库存、发货状态。新增查询投影，不覆盖母单 `status` 或库存状态。

| 维度 | 建议状态 | 依据 |
|---|---|---|
| 交货 | 未交齐／已交齐／交货待核／售后处理中 | 当前真实交付和质量事实 |
| 结单 | 不可结单／待填写／草稿／已确认／待调整 | 交货资格和结单记录 |
| 业务 | 处理中／待工费结单／业务完成／售后处理中 | 交货完整且客户费、员工费均已确认 |
| 客户收款 | 待出账／未收／部分收款／已结清／无需收款／待核对 | 有效应收、红字及有效核销 |
| 员工付款 | 待结单／未付／部分付款／已付清／无需付款／待核对 | 本单员工应付、调整及付款流水 |

界面使用“客户款已结清”和“员工工费已付清”，避免一个“财务已完成”掩盖另一方向的未结余额。若展示本单整体财务结束，必须同时满足两者，且无未处理差额；此状态不代表企业其他外协、耗材应付都已支付。

客户余额：原正数应收＋关联红字－有效收款核销。员工余额：原员工应付＋关联调整－有效付款。预收未分配金额独立显示，不自动抵减某张订单的欠款。余额异常为负或来源不完整时显示待核对，不用 `max(0)` 隐藏异常。

结单确认时记录收入月份和工费成本月份，默认均为确认日所在月份；交货日、作业日、收款日、员工付款日分别保留。不得按交工日回填到已锁历史月份。若以后支持人工指定记账期，另加期间授权与锁定规则，不在首版放开。

## 7. 数据结构：补业务凭据，复用现有账

### 7.1 继续使用的账务实体

| 实体／表 | 本次用法 |
|---|---|
| `ReceivableLine / fin_receivable_line` | 客户加工费及后续补差、红字，沿原客户账和收入汇总 |
| `CustomerReceipt / fin_customer_receipt` | 每一笔真实客户到账；原始到账与原始分摊不可变 |
| `ReceiptAllocation / fin_receipt_allocation` | 收款建立时的原始分摊，不原地增删改 |
| `PayrollLine / fin_payroll_line` | 结单后追加已确认员工工费及差额，不从交工或工价重算 |
| `Payable / fin_payable` | 每单、每员工的工资应付，保留母单／客户归属 |
| `PayablePayment / fin_payable_payment` | 沿用应付付款、禁止超付和幂等 |
| `PayrollRun / fin_payroll_run` | 保留历史月度确认事实；不再是新工资的计费与入账前提 |

### 7.2 建议新增的最小业务表

以下名称为拟定，实施时依代码惯例定稿；不能宣称这些表已存在。

| 表 | 保存内容与约束 |
|---|---|
| `fin_order_settlement` | 一条草稿／确认版本的表头：业务目标、根结单、版本序号、前版编号、客户、状态、行版本、交货版本、费用合计、免收结论、制单／确认人、时间、记账月。`目标＋版本序号` 唯一；首份正式结单另有唯一防重键 |
| `fin_order_settlement_item` | 客户收费、员工工费及调整明细，按结单版本和行号唯一。工资含员工稳定身份和来源作业，客户与员工金额字段按权限分别返回 |
| `fin_order_settlement_source` | 交货、批次、轮次、损耗依据以及旧账引用的明确关联和必要快照；不复制库存流水，不把备注文本当关联 |
| `fin_order_settlement_posting` | 明细到应收、工资、应付的入账关系；`结单版本＋明细＋账务种类` 唯一，支持历史接续及付款反查订单 |
| `fin_receipt_allocation_operation` | 已有收款后续核销／撤销核销的操作表头，保存原收款、客户、原因、操作人和请求事实；沿工作单元回放 |
| `fin_receipt_allocation_operation_line` | 后续核销的增量；撤销明确指回原分摊，禁止超过原有效核销量，不重写旧记录 |

首份确认后原版本和明细不可改写；后续调整追加新版本并链接前版。草稿可在乐观锁下更新／替换草稿明细，不能删除已确认版本。确认后的合计是当时凭据快照，不是另一套可手改的客户余额。

### 7.3 对现有表的必要扩展

- 工资行增加明确的来源模式，例如 `LEGACY`、`POST_DELIVERY`，以及稳定计酬人员标识；显示姓名继续保留快照。
- 员工应付增加稳定收款人标识、必要的调整指向。新行使用唯一的可空入账防重键；历史行不强行补造身份，也不直接把旧普通来源索引改成全局唯一。
- 应收、工资、应付与结单优先用入账关系表连接，不在母单重复维护金额。
- 新查询按目标、客户、人员、记账期和来源建立必要索引；为核销按应收行、收款单反查建立索引。列表应批量聚合，避免每行重复整表读取。
- 所有金额沿用 `DECIMAL(18,2)`、单价沿用四位小数、数量沿用三位小数的现有容量，后端统一舍入；先算行再汇总，前端不以浮点累计作为入账依据。

数据库迁移采用新的 `V{n}__m3_xxx.sql`，实施时按最新迁移索引分配编号；不在方案中占用 V77 或其他可能已被并行工作使用的编号。旧迁移、表、种子、原始金额和校验和保持原样。

## 8. 入账和月度工资如何改

### 8.1 新结单一次写入

确认首份结单时：验证客户净应收 → 正金额逐项追加原应收行 → 逐员工明细追加 `confirmed=true` 的 `POST_DELIVERY` 工资行 → 按本单、员工汇总追加工资应付 → 保存入账关系、确认版本和命令结果 → 一次提交。

客户免收及员工零工费仍保留明确凭据，但不创建可收／可付的零金额单。客户费用和员工工费两部分均完成才标记业务完成。

来源键固定为结单版本和明细身份，例如 `SETTLEMENT|结单号|行号`；确认重试回放原结果，换请求号再次确认同一基础结单由唯一约束拒绝，不依赖前端禁用按钮。

### 8.2 月度工资改为汇总

1. 新工费不调用 `FinancePayrollService.build`，不读取 `WorkerRate` 计价，不调用 `replacePayroll`。
2. 月度工资页展示已经由订单结单确认的工资行，按员工、工序、订单汇总，可追溯原结单及对应应付、付款。
3. 新行按逐单确认状态进入工资成本；旧行仍按其历史月度确认事实解释。修改报表、成本明细、月度列表时共用同一准入规则，不能只改页面。
4. 结单确认已经生成员工应付，月度查询不得再生成一次 `PAYROLL|月份|姓名` 应付。
5. 历史 `PayrollRun` 锁定保护旧账，但不阻止新模式在当前记账月继续追加订单工费。不能因为某月早期已经锁工资，就把后来交货的订单漏掉。
6. 新工资成本从工资行统计，应付只用于余额和付款，不能工资行与应付金额同时计成本。

### 8.3 既有账单更正

确认后需要改费，使用交货后结单调整版本，记录原值、新值、差额和原因；不再通过生产改单夹带金额。

- 客户增额复用正数应收，减额复用关联原行的红字，遵守剩余未核销额度。
- 员工增加工费追加工资差额和对应应付；减少工费追加负工资差额及指向原应付的抵减事实。原应付、原付款不覆盖，付款余额按原单加调整计算。
- 员工抵减不能超过原应付未付余额；负向调整行不作为独立可付款单，旧付款条件更新需按有效应付上限复核，不能继续只用原始 `amount`。
- 已收／已付部分需要减额时，不能自动伪造退款或负付款。首版拒绝超出未结余额的减额并提示待处理；退款／员工往来抵扣若纳入后续范围，须增加明确凭据和授权后再开放。
- 调整同时影响应收、工资、应付时必须原子提交，原确认版本可继续追溯。

### 8.4 财务总览和缺项提示

`FinanceReportService.operating` 当前调用 `billing.unpriced`，后者仍按母单／交工寻找协议；新模式必须改为读取真实结单缺项，不能继续对正常生产中的订单提示“没有协议／没有工价”。区分尚未交货、已交货待结单、草稿待确认、历史待核；尚未确认的金额不猜测填入收入或成本。

当前未收、员工应付未付仍按查询时点，月度收入和工资成本按入账月份；全局待结单清单不被当前月份掩盖，跨月迟填保留交货日与确认日。

`FinanceDashboardService.customerIdsInScope/customerName` 当前主要从协议和应收取客户。停用协议写入后，要改用授权范围内的客户档案、真实订单、结单及收款等必要来源，防止新客户、仅有预收客户或只有待结单业务的客户从汇总范围消失。必须保持稳定客户 ID 授权，不能用名称碰巧相同来扩大范围。

## 9. 关闭全部前期金额入口

| 入口 | 目标处理 | 防绕过要求 |
|---|---|---|
| 客户协议新增／修改 | 从日常操作移除，历史查询保留 | 新规则生效后旧写接口明确拒绝，不靠隐藏按钮 |
| 月度生成客户账单 | 移除生成动作，改查已确认结单与原账 | `billing-runs` 不得继续扫收货／交工生成费用，也不能自动给历史订单补账 |
| 员工工价新增／修改 | 从日常操作移除，历史查询保留 | 旧 `worker-rates` 写接口拒绝，不成为结单必填前置条件 |
| 工资试算／整月确认 | 改为查询订单确认结果 | 旧 `payroll-runs` 及 confirmations 不再重建或覆盖当月工资 |
| 交货前改单 | 去除客户单价、员工工费、两类差额及原应收行输入 | 服务端拒绝新提交的金额；已保存未生效旧费用申请也不能绕过 `apply` 提前入账 |
| 质检损耗 | 只登记投入／产出、标准损耗、实际损耗、责任、证据和审核结论 | 新请求不要求计件价或扣减单价，也不能接收后悄悄算工资；金额留交货后确定 |
| 原审批详情／历史试算 | 历史按原事实只读展示 | 历史试算不是新工资来源；说明文案区分“旧试算快照”与交货后正式确认 |
| 其他写应收／工资调用 | 查现有 `saveReceivable/savePayrollLine/savePayable` 生产调用点 | 在应用层和入账协调层约束来源，定向测试直接服务调用，不只测 HTTP |

改单继续复用草稿、审核、版本、执行轮次和同母单锁。首版保留现有审核职责，审核只确认业务变更，不要求提前确定费用。新增明确结论 `DEFERRED_TO_SETTLEMENT`，界面显示“费用交货后确定”，**不得用 `amountUnchanged=true` 冒充“现在没有定价”**。历史 `PENDING_FINANCE/FINANCE_CONFIRMED/APPLIED` 原值保留，新界面翻译和流程按新结论解释。

`OrderChangePostingService.post` 对新模式不写任何客户或员工金额；历史已入账结果保持查询，未入账旧申请需重新审核为费用后定或明确作废，不能发布后偷偷执行旧差额。

损耗改造继续复用原损耗计算和审批事实，新增／扩展结构化字段区分“只审实物与责任”和“旧工资试算”。旧摘要保留，但新结单不解析标题包含工序、字符串 `lossDeduction` 等方式决定扣减。审批模块不因此自动变成正式工资或付款模块。

## 10. 客户批量收款与已有预收核销

### 10.1 新收到一笔款

复用现有 `CustomerBillPanel` 和 `POST /api/finance/receipts`。同客户选择多张待收订单，展开对应应收行，输入实际到账、收款日期、分摊金额；提交仍是一张收款单及完整分摊数组，不按订单循环登记到账。

订单勾选仅是操作入口。后台核销目标仍为明确应收行，保留旧账、改单红字和结单新增行的可追溯关系。同一客户可跨月份选择；筛选月份只限制展示，不把本月新增金额当作当前未收余额。

新增余额查询返回每条应收的原金额、有效红字、有效核销和当前未收，以及订单汇总。当前 `CustomerStatement.lines.amount` 是原金额，不能直接拿它预填“剩余可收”。结清、红字、来源不明及无权限行不可选择。

分配建议可以按最早欠款排序，但提交前显示完整结果；不自动跨客户，不从勾选金额反推实际到账。实际到账大于本次分摊时，剩余继续作为预收／待分配。

### 10.2 已有款项后续关联

选择原收款单 → 读取可用未分配余额 → 选择同客户订单及应收 → 确认新增核销。只写后续核销操作及明细，不新增 `CustomerReceipt`，不增加实收，不再次计算加工收入。

撤销错配指回原核销并追加撤销记录，退回原收款可用余额；不能超过该次尚未撤销的有效金额。撤销核销不等于退钱。真实收款录错／退款处理不以此动作代替。

原收款及原始分摊保持不变，因为当前幂等比较包括原分摊。统一有效核销投影合并“原始分摊＋后续分摊－已撤销分摊”，用于客户账、订单余额、可分配预收和财务总览，不能只让新页面读新表。

原收款幂等回执继续返回原请求建立时的分摊；详情查询另外返回当前有效分摊和后续操作，二者区分字段，避免回放内容被后来核销改变。

## 11. 事务、并发与持久化边界

### 11.1 结单提交

复用 `BusinessWorkUnit` 的请求结果回放和 `WorkSession`。先以真实登录账号识别请求，再在工作会话内：锁母单／目标 → 读取当前版本与交货事实 → 锁必要库存、账务来源 → 校验 → 保存结单和三类账务 → 保存命令结果 → 提交。

现有按会话保存应收、工资、应付的方法可复用；新增保存结单、核销操作、锁定读取等会话方法。不允许会话内部调用另开连接自动提交的旧仓储方法。缺少必要装配时明确拒绝写入，不能退回不受保护路径。

仓储补充仅限实际所需：`BusinessDocumentRepository` 增加按目标／母单范围、工作会话读取出货和必要当前事实的方法；库存补充同会话的目标余额／流水及必要锁定读取；财务增加同会话的应收根行、有效核销、原收款、工资来源和应付调整读取。当前无会话的 `listOutboundOrders/listReceivables/listReceipts` 不能直接当作确认事务中的可靠当前快照，也不应为一个确认动作每次读取全部客户的整表数据。

### 11.2 同一来源必须共用保护

当前发货、客户退货及售后分流并非都已有与结单共用的母单锁和工作单元。仅在结单服务加锁不能阻止同时退货。实施时对直接影响完成判定的写入口补齐共用锁／会话边界；通用库存转移涉及该订单维度时也必须纳入校验，不能成为旁路。

统一锁顺序按关联母单编码排序，再按目标、收款单、原应收／原应付及库存维度的固定顺序加锁；多订单收款和跨单撤销尤其不能按用户勾选顺序加锁。先解析归属只用于确定锁顺序，锁后重新验证归属、回收标记和版本。

MySQL 等锁后采用当前锁定读重验完成事实、已有核销和版本，不能沿用事务开始时的旧一致性快照。发货／退货、改单生效、结单与调整之间的并发必须有目标数据库验证。

### 11.3 收款和应付

现有收款登记事务保留，但把原幂等识别放在新请求余额校验之前；原成功请求不因欠款已减少而被拒绝。新请求在同一连接内锁定相关应收根行并重算有效余额，再写到账与分摊。新增后续核销还需锁原收款余额，防止两次使用同一笔预收。

红字、后续核销、撤销核销、新收款必须采用同一余额锁口径。员工付款复用当前行锁及请求防重，增加工资应付调整后的有效上限检查。独立退款／负付款不在这条路径暗中实现。

内存实现与 JDBC 保持同一语义，新增写入都有撤销动作。现有内存工作单元全局锁和财务收款局部锁并不天然互斥；要协调同一财务来源的写锁，不能认为各处 `synchronized` 就已覆盖交叉并发。

### 11.4 幂等和版本

所有新财务命令必须带稳定请求号；同账号同内容回放原结果，不同内容或非法跨账号重放拒绝。草稿使用 `expectedVersion`，确认还使用 `deliveryRevision`，金额未变但来源变了也应要求刷新。

旧收款和付款接口中的可空幂等字段可在兼容读取中保留，但本次新客户端始终必传；新核销、结单及调整不提供无幂等写入回退。提交成功与刷新失败分别处理。

## 12. 接口、权限和界面改造清单

### 12.1 拟定接口

以下为拟定路径，实施时才更新现行契约；旧路径不能在未提示客户端的情况下悄悄换成其他业务。

| 方法／路径 | 用途与主要约束 |
|---|---|
| `GET /api/business/order-completions?targetType=&targetCode=` | 无金额交货及结单状态；沿订单数据范围，给列表／扫码共用 |
| `GET /api/finance/order-settlements` | 待填写、草稿、已确认、历史待核的分页查询，计数与列表同范围 |
| `GET /api/finance/order-settlements/{code}` | 按费用权限分别返回客户区、员工区及来源，不泄露另一分区 |
| `POST /api/finance/order-settlements/drafts` | 首建／更新草稿，交货未完成拒绝；包含请求号和预期版本 |
| `POST /api/finance/order-settlements/{code}/confirmations` | 最终确认并原子入账，双费用权限及公司范围 |
| `POST /api/finance/order-settlements/{code}/adjustments` | 新增调整版本，原确认不覆盖，按未收／未付余额约束 |
| `GET /api/finance/open-receivables?customerId=&...` | 当前未收应收及订单分组，支持跨月份，返回全量合计与分页，不由本页累加总额 |
| `POST /api/finance/receipts` | 复用新到账＋多应收分摊，补事务内余额保护 |
| `GET /api/finance/receipts/{code}/allocation-context` | 原收款、当前有效核销、可用预收和可选订单；客户范围及收款权限 |
| `POST /api/finance/receipts/{code}/allocation-operations` | 追加后续核销／撤销，不新增到账 |
| `GET /api/finance/payroll-summaries?yearMonth=&...` | 从订单已确认工资及历史账读取月汇总，不生成工资或应付 |
| `POST /api/finance/payable-payments` | 沿现有员工及其他应付付款，校验调整后余额 |

版本冲突、交货未完成、旧入口已停用、历史待核等返回明确业务错误和可操作提示。不能以返回空数组／成功零条掩盖旧客户端正在调用已关闭计费接口。

### 12.2 权限复用

| 动作／字段 | 主要权限与范围 |
|---|---|
| 查看交货、待结单、业务完成 | 现有订单可见范围；不返回钱或工资人员明细 |
| 客户费草稿／确认资格 | `FINANCE_BILLING_POST`＋真实客户范围 |
| 员工费草稿／工资明细 | `FINANCE_PAYROLL`／`FINANCE_COMPANY_READ`＋公司 `ALL` 范围 |
| 整体确认 | 同时具有加工费入账和工资核算权限＋公司范围，逐来源校验 |
| 客户账读取／批量收款 | `FINANCE_CUSTOMER_READ`／`FINANCE_RECEIPT`＋客户范围 |
| 员工应付与付款 | `FINANCE_PAYABLE`＋公司范围，不因客户收款权限开放 |

新路径必须显式加入 `PermissionGuardInterceptor`，不能依赖当前未知财务 POST 返回空权限、未知 GET 默认公司读取的兜底。服务层同样校验对象归属和字段能力。

`App.vue.canBill` 当前只检查客户账读取／收款，不代表有工资或结单权限。增加独立结单能力判断，保留现有收款判断。`OrderWorkspaceAccess` 当前只携菜单和工序，若扩展返回财务状态，需从真实会话传递有效权限或使用独立授权查询，不能只依据 `finance` 菜单。

### 12.4 附件与审计

费用凭证复用原件存储、签名预览和备份，但新增明确财务用途／阶段及结单关联，授权由结单及费用分区判断，不能挂成普通生产可读附件。上传失败只重试文件，不重做结单；选择凭证不等于已上传或已关联。客户对账输出不带员工工资。

## 13. 历史数据接续与切换

### 13.1 切换原则

新规则启用后，**所有尚未发生的客户加工费和员工工费填写／入账均遵守交货后确认**；不能给旧订单保留一条可继续提前收费的后台路径。历史事实保持原样，不批量冲销、不删工资、不伪造结单人或结单时间。

在数据库保存流程启用事实与时间，不能只靠前端版本或随重启变化的日期判断。可为每个结单目标建立迁移核对状态，区分正常新流程和历史待核；该标识不是恢复旧计价的开关。

### 13.2 分类处理

| 存量情况 | 处理方式 |
|---|---|
| 未交货且没有费用事实 | 正常进入新流程，交货前没有费用草稿 |
| 未交货但已有应收／工资 | 历史事实保留并标明旧口径；不自动撤销。交货后核对最终总额与已入账，避免重算 |
| 已交货，没有费用 | 进入待结单；不自动填零或直接标业务完成 |
| 已有客户应收，员工工资未确认 | 结单引用客户旧账；旧工资试算与已确认工费分开，不能把试算当应付或成本 |
| 已有已确认工资／月度应付 | 逐工资行接续；月度应付只引用，不为每单再生成一份同额应付 |
| 旧月度应付已付款 | 月度付款无法天然反推出每单已付。没有人工分配依据时显示“历史付款未分配”，保留公司总额，不宣称某单工资已付清 |
| 母单级旧应收与子单级新结单冲突 | 必须核对覆盖范围，建立有金额的明确接续关系；同一旧账金额不能被多个子单重复接续。无法分配时母单级人工核对，不自动均摊 |
| 已有改单收费／工资调整 | 已生效的计入历史净额；待生效的金额申请冻结旧金额入口并重新审核为费用后定，避免切换后继续入账 |
| 只有工价／协议 | 保留历史配置，不视为已有本单费用，也不作为新结单金额来源 |
| 已收／已付超过最终确认额 | 不自动减余额或伪造退款，列为待处理差额；超出未结余额的减额在首版拒绝 |
| 缺客户、重名人员、无出货台账、回收单等 | 明确历史待核，不伪造关系、不删除金额，保持原财务查询可见 |

接续计算以**明确覆盖范围的原净入账额**为基数，而不是以“尚欠多少钱”为基数。例如原应收 1,200、已收 800、最终费用 1,500，应补 300，最终未收 700；不能补 1,100 或另开全额 1,500。员工工资同理，已付款不改变原工费基数。

历史试算替换／失效须保留可追溯记录，不能借新结单调用 `replacePayroll` 清掉整个历史月份。接续调整与新结单同事务，并为引用额度防重。

### 13.3 迁移和运行准备

新增迁移包含表、可空兼容字段、新来源唯一约束和查询索引；按实际版本更新迁移索引与升级探针。不改历史 V36 等已发布脚本，也不照抄旧文档中的失效阻断判断，应以实际迁移链验证。

内存默认和 MySQL JDBC 保持一致；新增仓储沿现有 `zhubao.finance.repository` 装配。工资、结单、应收、工作单元混用内存和 JDBC 时，不允许财务确认写出跨持久化半单，启动／写入时明确拒绝不受支持的组合。

发布前在隔离数据副本中只读盘点上述分类和来源重复，不直接对业务库创建核验单据。形成待核清单后人工处理；数据库结构迁移不自动补钱、自动红字或自动标结清。

新旧版本并存时服务端关闭旧金额入口，旧客户端提示升级；不能指望只刷新网页就阻断旧 PWA／安卓请求。新增财务事实后，旧服务端不理解新核销和工资来源，不能无条件回滚旧代码；回退必须保持兼容读取／停写，并结合发布后写入处理，不清库或恢复旧备份覆盖新款项。

## 15. 最小充分验证与验收用例

本次为方案文档，只检查源码引用、方案一致性、链接和差异；**不运行业务测试、生产构建或打包**。以下是实施阶段的验证要求，不是本次已通过结果。

### 15.1 业务与入账

1. 不拆母单、拆分子单正常交齐后可填两类工费；未交齐、仅有出货记录、100% 未交工均拒绝。
2. 部分生产＋部分发货、多个材质／数量单位、未拆余量、回收子单不能被错误完结。
3. 返工／新执行轮次／退货／售后分流影响完成判定；重发不重复产生基础收费。

### 15.2 收付款与更正

9. 一笔收款结多单、跨月、同单多次部分收款、多收留预收、已有预收后续核销、错配撤销。
10. 新到账原请求带非空分摊，成功后响应丢失重试，必须返回原单；后续核销发生后仍可回放原收款原始内容。
11. 不同请求并发核销同一应收、并发使用同一预收、红字与核销竞争，不超额；失败不留半笔到账或分摊。
12. 员工部分付款和超付拒绝、费用调整与付款竞争；已收／已付部分不能直接减额，撤销核销不伪造退款。
13. 客户结清不改变员工付款状态，员工付清不改变客户欠款；两个方向均完成才可显示整体财务结束。
14. 客户账、订单、预收、未收排行、财务明细和经营汇总使用同一有效核销，不能出现页面间余额不一致。
