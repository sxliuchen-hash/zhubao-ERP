# 珠宝 ERP 项目 AI 开发规则

本文件是本项目所有 AI 助手（Kiro、Codex 等）必须遵守的开发规则，长期有效。

## 语言规范（强制）

- **所有代码注释必须使用中文。** 包括 Java Javadoc、行内注释、TypeScript/Vue 注释、SQL 注释。
- **所有文档必须使用中文。** 包括 `docs/` 下的设计与进度文档、README 的说明性文字、提交说明中的中文摘要。
- 允许保留英文的场景：代码标识符（类名、方法名、变量名、枚举值）、技术术语（如 RBAC、JDBC、HTTP、PBKDF2）、第三方 API 名称、日志中的英文关键字。
- 面向用户/评审的界面文案继续使用中文。
- Git 提交标题可用英文（遵循 conventional commits），但提交正文应包含中文说明要点。

## 多智能体并行协作（推荐）

- **鼓励派出多个子智能体（sub-agent）同时工作以提高效率。** 在遇到互不依赖的任务时优先并行，例如：多文件调研、跨模块代码分析、bug 定位、上下文收集。
- 典型并行场景：
  - 用 `context-gatherer` 在动手改动重度测试覆盖的服务前，先并行摸清调用链路和影响面。
  - 用 `general-task-execution` 并行处理独立的多文件读取或独立子任务。
- **必须串行执行的操作**（禁止并行）：Git 操作（commit / merge / branch）、同一文件的连续编辑、有前后依赖的构建与测试步骤。
- 派子智能体前先判断任务是否真正独立；简单的定向查找直接用搜索工具即可，不必派子智能体。

## 工程规范

- 严格遵循既有 DDD 分层：每个领域模块内保持 `domain / app / infra / web` 四层。
- 持久化遵循"内存默认 + JDBC 可切换"模式：`@ConditionalOnProperty` 控制，本地默认内存，MySQL profile 默认 JDBC。
- 新增可选依赖时采用"重载构造器向后兼容 + 单一 `@Autowired` 全参构造器"范式，避免破坏既有测试。
- 数据库迁移脚本 append-only，按 `V{n}__m3_xxx.sql` 递增命名，禁止修改已发布迁移。
- 每个增量按实际影响补充必要测试、执行最小充分验证，并以语义化提交独立提交。文档按变化同步：功能进度更新 `docs/14_开发进度跟踪.md`，入口或使用方式变化更新 `README.md`，交付范围或版本变化更新 `docs/23_客户交付版本记录.md`；不要求无变化的文档每轮重复改写。

## 验证策略（强制，按需执行）

**默认只做最小充分验证，不把前后端全量测试、生产构建和打包门禁作为每次改动或提交的前置条件。** 验证范围应解决本次改动的实际问题，不为形式完整反复执行。

| 改动类型 | 默认验证范围 |
|---|---|
| 文档、提示词、注释、纯说明文案 | 差异、必要链接及格式检查；不跑业务测试、不构建、不打包 |
| 局部界面、样式或交互 | 受影响组件的相关测试或定向页面检查；纯样式不强写单元测试，不联跑后端 |
| 单个后端业务或接口 | 受影响服务、接口及直接调用链的定向测试；不联跑无关前端或全部后端 |
| 库存、金额、权限、幂等或事务逻辑 | 相关业务链路的正常、失败及必要的并发/越权测试；涉及这些领域本身不等于必须全仓测试 |
| 数据库迁移 | 相关仓储、SQL/升级检查，必要时验证目标数据库；不连带打包或运行无关测试 |
| 构建配置、依赖、公共框架或广泛重构 | 根据真实影响扩大到相关类型检查、构建或对应一侧全量测试 |

### 全量测试和构建的触发条件

- 用户明确要求、正式版本发布验收，或公共改动影响广泛且定向验证无法合理覆盖时，才执行相应全量检查。
- 只影响后端时无需全量前端，反之亦然。跨端接口改动优先验证对应契约与消费方，不自动联跑全部测试。
- 生产构建用于验证实际打包、依赖或编译兼容性；局部改动优先相关测试或类型检查，不固定追加生产构建。
- 定向验证已通过且没有新的改动、失败或未解决问题时停止验证。后续纯文档调整不使已通过的代码测试失效；共享改动发生变化时只重验受影响部分。

### 打包与交付门禁的触发条件

- 仅在实际制作交付包、修改打包/部署/镜像/升级装配逻辑，或用户明确要求时，执行与之相关的包结构门禁。
- 普通功能开发、文档调整和阶段提交不生成运行包，不为了“门禁全绿”额外构建镜像、启动 Docker 或演练数据库。
- 同一代码状态的相关测试已经通过，打包可用 `-SkipTests` 避免重复执行；说明复用的验证结果，不把跳过写成重新通过。
- 包门禁使用本次实际包路径；无镜像结构验证不等于镜像安装、数据库升级或客户验收通过。

### 提交与结果记录

- 只需本次选定的必要验证通过即可提交，不以未运行无关全量检查为由阻止提交或另行请求许可。
- 相关验证失败应定位并修复；确有公共影响证据才扩大验证，不借机修复无关问题或扩大任务范围。
- 简要记录实际执行及结果；仅说明影响本次结论的重要未验证项。无需逐轮罗列未触发的 Docker、真机、全量测试等项目，不伪称已验证。
- 本节是项目统一验证策略。方案、执行提示词中的旧“每增量全量/全绿/打包”模板应按本节解释并更新，不得恢复为默认要求；明确的用户要求优先。

全量检查命令仅供触发时使用，不代表每轮必跑：

- 后端：`powershell -ExecutionPolicy Bypass -File scripts/maven.ps1 -f backend/pom.xml test`
- 前端：`pnpm --filter zhubao-erp-frontend test`
- 前端生产构建：`pnpm --filter zhubao-erp-frontend build`
- 包结构：`powershell -ExecutionPolicy Bypass -File scripts/verify-runtime-package.ps1 -PackagePath <实际运行包目录或zip>`
